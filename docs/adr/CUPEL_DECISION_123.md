# CUPEL_DECISION_123: Fact kinds join the catalog from their own payload modules

**Date:** 2026-10-18 · **Status:** accepted · **Phase:** P8.0

## Context

ADR-074 made checks and tool producers register themselves from their own modules, but left the fact catalog as hand-edited lists: `FactKind` itself, `FactKind::ALL` and `NAMES` (each an array of counted length), `FactKind::SYNTACTIC`, `pin_key`'s match, `FACT_SCHEMAS` in `cupel-core/src/schema.rs`, the plugin crate's `KINDS` table (each kind with `register_as::<T>`), `conformance::EXECUTION` in `cupel-fixtures`, and tests that spelled out every kind's name or pinned a kind's catalog position (`cupel-core/tests/{extension, schemas, footprint}.rs`). P7 added six kinds on four parallel branches; every branch appended to the same tails, and the integrator hand-resolved twelve to fourteen conflicts per merge (plan, P7 Notes "P7 — integration"). P8 and later phases will add kinds the same way. The question is how a kind joins the catalog from its payload module, what must remain a shared list, and which order the catalog has once nothing lists it.

## Options

**Registration: an `inventory` submission per payload module, the enum kept.** Each payload module submits one `FactEntry` (`inventory::submit!`), the mechanism ADR-074 chose (`inventory` 0.3.25; `linkme` is refused by the workspace's `unsafe_code = "forbid"`). The entry carries everything the tails held: kind, name, payload version, schema function, a type-erased decoder, whether the kind is syntactic, whether it has a conformance inventory, and its pin key. `FactKind` stays an enum: checks name kinds in `needs` arrays that must be constants, the scheduler and producers compare against variants, serde and `schemars` derive its spelling and its schema enum from it, and it is `Copy`, `Ord`, and `Hash` for free. The enum's declaration is then the one list a new kind edits.

**Registration: `FactKind` as a newtype over a name, with associated constants declared in each payload module** (`impl FactKind { pub const TRACES: FactKind = FactKind("traces"); }`). This removes the last list, since inherent impls may be split across a crate's modules. But every `FactKind::Symbols` in the workspace becomes `FactKind::SYMBOLS` (hundreds of sites), serde and the JSON Schema enum need hand-written impls that read the registry, a name read from JSON needs the registry to become a `&'static str`, and ordering would have to be redefined. The cost is a workspace-wide rename to save one line per kind, which `.gitattributes` makes conflict-free anyway.

**Plugin registration: a constructor the plugin crate gets from the entry.** The plugin's producer was generic (`PluginProducer<F>`), so `cupel-plugin` needed one `register_as::<T>` per kind, a table core cannot hold because `PluginProducer` lives in the plugin crate. Either core keeps a `(kind, register)` table the plugin iterates (which is the same tail moved to core), or the entry carries the one type-dependent step: decoding the plugin's JSON payload into the kind's type. The plugin's producer then becomes one non-generic `RegisteredProducer` that holds its kind's entry and calls its `decode`; core gains `ProducerRegistry::register_dyn` for producers whose type is known only at run time.

**Catalog order: `FactKind`'s declaration order, an explicit `order` in each entry, or by name.** Declaration order is what the derived `Ord`, the derived JSON Schema enum, and every existing listing already use, so no golden changes; an explicit `order` would be a second ordering two branches can both claim (the same number), and name order would reorder the published schema enum and `describe` listings. Nothing persists or hashes the ordinal (the store and serde write names; finding IDs carry no fact kind), so the choice affects only listings, which goldens capture.

**Goldens: one schema snapshot per kind, or keep the whole-catalog snapshots only.** The syntactic kinds already had `schemas__fact_<kind>.snap` each; execution kinds' schemas were pinned only through `describe` goldens of single kinds and the version-and-`$id` list in `schemas.rs`.

## Decision

1. **`FactEntry`, submitted by the payload module.** `cupel_core::FactEntry { kind, name, version, syntactic, conformance, pin_key, schema, decode }`, built by const constructors so a submission is one line: `inventory::submit!(FactEntry::execution::<Traces>("traces").with_conformance());`, `FactEntry::syntactic::<Symbols>("symbols")` (the `fact!` macro in `syntax.rs` submits each syntactic payload's entry), `.pinned_by("runner")` for a kind whose producer `[lang.<id>]` pins. `version`, `schema` (the payload's root schema with `$id` `fact/<name>.json` and `x-cupel-fact-version`), and `decode` (`serde_json::from_value::<T>` into a `Produced`) come from the payload type, so they cannot disagree with it. `FactEntry::catalog()` collects the submissions once, sorts them by kind, and panics with "fact kinds have one catalog entry each" on a duplicate (tested by submitting a second `footprint` entry in its own test binary). `FactKind::all()`, `FactKind::syntactic()`, `FactKind::entry()`, `as_str` (so `Display`), `pin_key`, `schema::fact`, `schema::fact_version`, the plugin crate's `providable_kinds`, and `cupel_fixtures::conformance::execution()` (entries with conformance that are not syntactic) are all read from the catalog. `ALL`, `NAMES`, `SYNTACTIC`, `FACT_SCHEMAS`, `KINDS`, `EXECUTION`, and `pin_key`'s match are gone.
   `fact.rs` stays a leaf of `cupel-core`'s import graph, because nearly every module imports `FactKind` and `Display` now reads the catalog: the type-erased `Produced` and `SharedFact` the decoder returns move from `producer.rs` into `fact.rs` (still re-exported at the crate root), and the root-schema helpers the entry's schema function uses (`BASE_URL`, `root`, `with_id`, `require_every_property`) move from `schema.rs` into a leaf `json_schema.rs`. Otherwise `fact.rs → producer.rs → … → error.rs → fact.rs` would be an import cycle, which the `static.deps.cycles == 0` gate refuses.
2. **The enum stays, and is the only list.** `FactKind` moves to `cupel-core/src/fact/kind.rs`, a file holding only the enum, so that file is the one place a new kind is listed. `tests/fact_catalog.rs` reads the variants from the enum's derived JSON Schema and asserts the catalog's names equal them in order: every variant has exactly one entry and every entry a variant.
3. **Catalog order is `FactKind`'s declaration order**, independent of link order because the catalog sorts by the derived `Ord`. A new kind is appended to the enum. Nothing depends on the order beyond listings: `describe` output, the language goldens' fact lists, and the schema enum, which the goldens and the two whole-schema snapshots capture.
4. **Plugins decode through the entry.** `cupel-plugin`'s producer is one `PluginProducer` implementing `RegisteredProducer`, holding its kind's `&'static FactEntry`; its output check is unchanged (one fact, the provided kind and version) and the payload is decoded by `entry.decode`, with the same error text. It registers through `ProducerRegistry::register_dyn`.
5. **Registry-derived tests.** `tests/fact_catalog.rs`: every variant has one entry in declaration order; every name is kebab case, unique, and equal to its serde spelling, `Display`, and `as_str`; every entry serves a schema at its version (at least 1) with `$id` `fact/<name>.json`; the syntactic kinds are the entries marked so and each has conformance; every entry's decoder rejects a non-payload; pin keys are unique and are what `pin_key` returns; `schema.rs` names no `FactKind` variant. `cupel-fixtures/tests/conformance.rs`: the inventories in `conformance/` are exactly the kinds whose entries have conformance, and every syntactic kind is produced by some language. `cupel-plugin`: every providable kind (every catalog kind) registers a producer of that kind, and `producer.rs` names no variant. `cupel-cli/tests/describe.rs`: `describe fact <kind>` for every catalog kind reports the entry's `syntactic`, version, and `$id`. The tests that spelled out all 29 names, listed nine execution kinds' versions, or pinned `Footprint` after `RelationResults` are removed or reduced to their own kind.
6. **One schema snapshot per kind.** `cupel-core/tests/schemas.rs` snapshots every catalog kind's schema as `schemas__fact_<kind>.snap` (the syntactic ten existed; the other nineteen are added), so a new kind adds a file and changes none. `golden/facts/<lang>/<kind>.json` is already one file per language and kind. The two whole-schema snapshots, `schemas__run_schema.snap` and `schemas__plugin_schema_describes_the_manifest.snap`, are kept: they pin the published `run` and `plugin` schemas, whose `FactKind` enum (and the plugin request's `facts` object) list every kind. They are the one remaining whole-catalog artifact, like the README's generated tables; a conflict there is resolved by rerunning `UPDATE_GOLDENS=1 INSTA_UPDATE=always cargo test -p cupel-core --test schemas`, not by hand.
7. **`.gitattributes`** gives `crates/cupel-core/src/fact/kind.rs` and `crates/cupel-core/src/lib.rs` (the payload module's `mod` line and re-export) git's `union` merge driver, as ADR-074 did for the check and producer crates' roots: two branches that each append a variant, or each add a `mod` line, merge with both.

## Consequences

- **What a new fact kind touches:** its payload module `crates/cupel-core/src/<module>.rs` with its `impl Fact` and one `inventory::submit!(FactEntry::…)`; its `mod <module>;` and `pub use` lines in `crates/cupel-core/src/lib.rs` (union-merged); its variant appended to `FactKind` in `crates/cupel-core/src/fact/kind.rs` (union-merged); its conformance inventory `crates/cupel-fixtures/conformance/<kind>.toml` if it is an execution fact with one; and its schema snapshot `crates/cupel-core/tests/snapshots/schemas__fact_<kind>.snap`, written by `UPDATE_GOLDENS=1 INSTA_UPDATE=always cargo test`, which also adds the kind's lines to the run and plugin schema snapshots. Its producers, checks, and tests are their own files, as before. A syntactic kind's payload goes in `syntax.rs` beside the other nine, through the `fact!` macro, which submits its entry.
- A payload that forgets its submission fails `fact_catalog.rs` (its variant has no entry), and every `Display` of the kind panics naming it, so the omission cannot ship silently.
- Adding a kind still requires an ADR (plan §2.5); this decision changes where the kind is registered, not that rule.
- The plugin producer no longer has a generic type parameter, so a kind needs nothing in `cupel-plugin`; the cost is that `PluginProducer` implements the type-erased `RegisteredProducer` directly, spelling out the three defaults (`estimate`, `detected`, `tool`) that `Producer` provides.
- `cupel-core` depends on `inventory` (an external crate already in the workspace, not a change to the Cupel crate graph).
- `union` applies to every conflicting hunk in `kind.rs` and core's `lib.rs`; two branches that each edit the same doc line would keep both, which review and the compiler would usually catch, as ADR-074 noted for the other roots.
