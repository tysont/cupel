# CUPEL_DECISION_137: The daemon's transport: Unix sockets, Windows named pipes behind an endpoint file, and Windows as a release target

**Date:** 2026-10-21 · **Status:** accepted; amends the Windows consequences of [124](CUPEL_DECISION_124.md) · **Phase:** P9.8

## Context

ADR-085 built the daemon on a Unix-domain socket at `<root>/.cupel/serve.sock`: the client connects when that file exists, a daemon replaces a socket file nothing answers on, ends when its file is removed or replaced (compared by inode), and makes it `0600`. The accept loop waits with `nix::poll`, and a run's hang-up is a thread reading the connection until end of file while the run writes `stderr` replies to it. None of that compiles for Windows, which is why ADR-124 left the Windows release job best-effort (`continue-on-error`), with `cupel-serve` the only crate that failed. Follow-up item 8 asks for the daemon on Windows over named pipes, `\\.\pipe\cupel-<hash of the repository path>`, chosen at compile time, the client and `CUPEL_NO_DAEMON` unchanged, the workspace compiling for `x86_64-pc-windows-msvc`, a Windows CI job, and the Windows archive a first-class release asset. Open: how a pipe, which has no file, keeps the file-based rules the client, `doctor`, and `serve --stop` rely on; how the pipe is served without an async runtime (ADR-086 §11, ADR-121); which tests the Windows job runs; and what stays unverified.

## Options

**Implementation.** (a) The `interprocess` crate's local sockets (Unix sockets and named pipes behind one type): one more dependency tree, its own naming rules for both platforms, and on Unix it would replace a transport that works and is tested. (b) `tokio`'s named pipes: an async runtime the daemon does not have. (c) `AF_UNIX` on Windows 10 (`uds_windows`): no named pipe, which the follow-up asks for, and it is unsupported on older Windows and in some containers. (d) A `transport` module in `cupel-serve` with two implementations chosen by `cfg`: Unix sockets through `std` as today, named pipes through `windows-sys` (`CreateNamedPipeW`, `ConnectNamedPipe`, `SetNamedPipeHandleState`, `PeekNamedPipe`; `windows-sys` 0.61 is already in the lock through `notify` and others), and every other line of the daemon shared. Chosen: (d).

**Where the endpoint lives.** (a) The pipe alone: the client would probe a pipe instead of a file, and `doctor`, `serve --stop`, the stale-socket rule, and "ends when its socket file is removed" would each need a second, Windows-only path. (b) The pipe plus an endpoint file at the socket path: the daemon creates the pipe, then writes the file; the client looks for the file and connects to the pipe that path names. Every rule ADR-085 states about the socket file then holds for the endpoint file unchanged. Chosen: (b).

**The pipe's name.** (a) A hash of the repository root: two daemons for one repository at different `--socket` paths would collide. (b) A hash of the endpoint file's absolute path: with the default socket the endpoint is `<root>/.cupel/serve.sock`, so the name is fixed by the repository path, and `--socket` (the parity harness's daemons) still selects its own pipe. Chosen: (b).

**Accepting without blocking past a stop.** (a) Overlapped `ConnectNamedPipe` with an event: the instance handle is then overlapped, and `std::fs::File`'s reads and writes abort the process on an operation that completes asynchronously. (b) A thread blocked in `ConnectNamedPipe`, woken at stop by connecting to the pipe itself. (c) The listening instance in nonblocking mode (`PIPE_NOWAIT`), polled every few milliseconds until the accept loop's 200 ms are up, then switched to blocking mode once a client is connected: one thread, the same loop as on Unix. Chosen: (c).

**A run's hang-up.** On a pipe handle opened for synchronous I/O, Windows serializes operations on the handle, so a thread blocked reading would hold back the run's `stderr` writes on the same connection. Unix keeps its reading thread; on Windows the thread polls `PeekNamedPipe` every 50 ms, reads only bytes already there, and reports a hang-up when the peek fails (the client closed its end).

**The Windows CI job's tests.** (a) `make test`: the integration suites drive `sh`, POSIX tools, and every language toolchain, and set file modes; most of them cannot run there. (b) `cargo test --workspace --lib`: the unit tests of `cupel-adapt`, `cupel-cli`, and `cupel-plugin` spawn processes and build `/`-separated paths, and none has been run on Windows. (c) The crates whose unit tests touch neither processes nor the file system, plus every test of `cupel-serve`, whose integration tests drive the real transport with a scripted handler: on Windows they serve real named pipes. Chosen: (c).

## Decision

1. **Transport** (`cupel_serve::transport`). `Listener` (bind, accept within a wait, whether its endpoint is still its own, remove its endpoint) and `Connection` (connect to an endpoint path; `Read` and `Write`, also through `&Connection`; `try_clone`; wait for the peer to hang up), each with a Unix and a Windows implementation chosen by `cfg(unix)` and `cfg(windows)`. The server loop, the client, and the protocol are shared and name neither. `nix` becomes a Unix-only dependency of `cupel-serve`; `windows-sys` (`Win32_Foundation`, `Win32_Security`, `Win32_Storage_FileSystem`, `Win32_System_IO`, `Win32_System_Pipes`) a Windows-only one; `blake3` names the pipe.
2. **Unix** is ADR-085 unchanged: a Unix socket at the path, `0600`, identity by inode, `poll` for 200 ms.
3. **Windows.** The pipe is `\\.\pipe\cupel-<the first 16 hex digits of BLAKE3 of the endpoint's absolute path>` (`transport::pipe_name`), created byte-mode and duplex with `PIPE_REJECT_REMOTE_CLIENTS`, the first instance with `FILE_FLAG_FIRST_PIPE_INSTANCE` (so a daemon never joins another process's pipe of the same name), and the default security descriptor (full control for the creating user, administrators, and LocalSystem; read-only for everyone else, which cannot write a request). After the pipe exists the daemon writes the endpoint file at the socket path, holding the pipe's name and a line unique to this daemon (its process ID and start time); its identity is that content, not the file's creation time, which Windows carries over to a file recreated under the same name. A connected instance is switched to blocking mode and a new listening instance is created before the connection is answered. The client connects to the pipe the endpoint path names, retrying for up to 5 s while every instance is busy; a missing pipe behind an endpoint file is a stale endpoint (`Unanswered`), as a socket file nothing answers on is.
4. **Everything above the transport is the same on both**: `.cupel/serve.sock` is where clients look, `CUPEL_NO_DAEMON=1` and the other local-run rules of ADR-085 §4, `doctor`'s three findings, `serve --stop`, `--socket PATH`, and parity.
5. **Unix-only code outside the transport** is compiled only on Unix: the integration-test files that set file modes, make symlinks, or drive POSIX tools carry `#![cfg(unix)]` (as `plugins.rs` already did), and the shared helpers that set modes are `cfg(unix)`. `cargo check --workspace --all-targets --target x86_64-pc-windows-msvc` compiles.
6. **CI.** `ci.yml` gains a `windows` job on `windows-latest`: `make windows-check` (`cargo check --workspace --all-targets`) and `make windows-test`: `cargo test --package cupel-serve` and `cargo test --lib` for `cupel-core`, `cupel-checks`, `cupel-lang`, and `cupel-mutate`. Both are Makefile targets, as every CI step is.
7. **Release.** The Windows build in `release.yml` loses `continue-on-error`: its failure fails the release like any other target's, and the archive is a first-class asset. `crates/cupel-cli/tests/release.rs` holds the workflow to that.

## Consequences

- The Windows daemon is verified by compilation here (`cargo check` for `x86_64-pc-windows-msvc`, with a stand-in C compiler, since this machine has no MSVC toolchain) and by the Windows CI job, which runs `cupel-serve`'s server tests over real named pipes. Nothing on Windows ran on the machine this was written on; until a `windows` job has passed, the named-pipe implementation is unexercised.
- The Windows job does not run `cupel-cli`'s integration suites, the golden harness, or `make parity`. ADR-124's other Windows items stay open: producers that run user commands through `sh -c`; timeouts that kill only the child, with no Job Object; `/`-separated paths in findings, scopes, and goldens; symlinks in overlays and the parity harness; and the plugin discovery's untested `not(unix)` branch. The binary is a first-class release asset; Cupel's checks on a Windows repository are as tested as those items say.
- Two endpoint paths differing only in case or in a `\\?\` prefix name different pipes; the client and daemon both derive the path from the repository root the same way, so they agree.
- The pipe gives other local users read access (the default descriptor), where the Unix socket is `0600`; they cannot send a request. A restrictive descriptor is a later change if that matters.
- Accepting polls a nonblocking instance, which Microsoft documents for compatibility; a connection waits up to a few milliseconds longer than on Unix.
