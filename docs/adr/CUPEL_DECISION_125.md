# CUPEL_DECISION_125: Installers read one release layout, and are tested against a fake release

**Date:** 2026-10-18 · **Status:** accepted · **Phase:** P8.2

## Context

Design §10 lists the distribution routes: GitHub Releases, `cargo-binstall`, a Homebrew tap, `curl -fsSL https://cupel.dev/install | sh`, and thin `npm` (`npx cupel`) and `pipx` wrappers that fetch the platform binary. Plan P8.2 asks for each installer to be tested in CI on a clean image. P8.1 builds and publishes the release archives in parallel, so the installers had to be written before any release exists, against a layout neither step had yet fixed. The questions: what a release looks like to an installer, where that is written down so the release workflow and five installers cannot drift, how each installer finds the latest release and verifies what it downloads, where the wrappers keep the binary and how they report a failure, and how all of it is tested without a real release, a registry, or a tap.

## Options

**One source of the layout: `dist/targets.toml`, or the release workflow, or each installer on its own.** Reading the workflow's YAML from a test ties the installers' tests to however P8.1 spells its matrix, and the workflow does not exist on this branch. Letting each installer carry its own names, checked only by a real release, finds a mismatch only after a tag. A small TOML file listing the five targets (triple, Rust `os` and `arch`, archive format) and the name templates (`archive`, `dir`, `checksums`) can be read by the release workflow and by the tests; the installers themselves cannot read it at run time (a piped `sh`, a published npm or PyPI package), so each embeds its table and a test compares that table with the file.

**Archive layout: the binary at the archive's root, or in one directory.** A top-level `cupel-<version>-<target>/` directory is what ripgrep and most Rust release tools publish, extracts without scattering files into the current directory, and is what Homebrew expects (it enters a lone top-level directory before `install`). It costs a `bin-dir` template in the binstall metadata and the directory name in each installer.

**Finding the latest release: the GitHub API, the `releases/latest` redirect, or `releases/latest/download/SHA256SUMS`.** The API needs JSON parsing in `sh` and is rate-limited. Reading the redirect's `Location` needs `curl -w` or `wget` header parsing, which differ. GitHub serves `releases/latest/download/<asset>` for any asset of the latest release, and `SHA256SUMS` has no version in its name while each of its lines names a versioned archive; so fetching it first gives the digest and the archive name (hence the version) in one plain download, with curl or wget alike.

**What the wrappers run: the latest release, or the release of their own version.** A wrapper that floats to the latest release makes `npx cupel@0.1.0` run something else, and a pinned project's results change under it. The package's own version is reproducible and is what a user asked for when they pinned it.

**Where the wrappers keep the binary: the package directory, or a user cache.** A global npm install or a system Python may leave the package directory unwritable, and `npx` and every pipx venv would each download their own copy. A cache keyed by version and target (`CUPEL_CACHE_DIR`, else `$XDG_CACHE_HOME/cupel` or `~/.cache/cupel`, `%LOCALAPPDATA%\cupel` on Windows) is writable, shared by both wrappers, and survives reinstalling the package.

**Testing: against a real release, or a fake one.** No release exists, and a test against GitHub needs the network and a tag. A fake release (the `cupel` binary the test crate was built with, archived under the `dist/targets.toml` names, with a `SHA256SUMS`, laid out under `download/v<version>/` and `latest/download/` as GitHub serves it) on a local HTTP server written with `std::net` exercises every installer end to end offline, needing no crate.

**Homebrew: a static formula edited per release, or a template rendered from `SHA256SUMS`.** Hand-edited digests are four values per release copied by hand. A template with `@VERSION@` and `@SHA256:<target>@` placeholders, rendered by a POSIX `sh` script from the release's own `SHA256SUMS`, fails when a target is missing rather than shipping a stale digest.

## Decision

1. **`dist/targets.toml` is the release layout.** It lists the five targets of design §10 (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin` as `tar.gz`; `x86_64-pc-windows-msvc` as `zip`), each with Rust's `os` and `arch`, and the templates `archive = "cupel-{version}-{target}.{format}"`, `dir = "cupel-{version}-{target}"` (the archive's one directory, holding `cupel` or `cupel.exe`), and `checksums = "SHA256SUMS"` (each archive's SHA-256 as `sha256sum` prints it). A release `v<version>` publishes them under `https://github.com/tysont/cupel/releases/download/v<version>/`. The release workflow is meant to read the same file.
2. **`cargo-binstall`**: `[package.metadata.binstall]` in `crates/cupel-cli/Cargo.toml` gives `pkg-url` `{ repo }/releases/download/v{ version }/cupel-{ version }-{ target }.tar.gz`, `bin-dir` `cupel-{ version }-{ target }/{ bin }{ binary-ext }`, `pkg-fmt` `tgz`, and a `zip` override for the Windows target. The extension is written out rather than `{ archive-format }`, so the rendered URL is exactly the archive's name.
3. **`dist/install.sh`** (POSIX `sh`, `set -eu`, ShellCheck-clean, everything inside `main`, called on the last line, so a truncated download runs nothing): maps `uname -s`/`uname -m` to a Linux or macOS target (Windows is not offered; the archive or a wrapper is), fetches `SHA256SUMS` from `releases/latest/download/` or, with `CUPEL_VERSION` (with or without a leading `v`), from `releases/download/v<version>/`, takes the target's line for the digest and the archive's name, downloads and checks it with `sha256sum` or `shasum -a 256` (curl or wget for the downloads), and moves the binary into `CUPEL_INSTALL_DIR` (default `~/.local/bin`) by rename. It prints `cupel install: installed cupel <version> as <path>`, and the `export PATH=…` line to add when the directory is not on `PATH`. Every failure is one `cupel install: …` line on stderr and exit 1. `CUPEL_DOWNLOAD_URL` replaces the releases URL (a mirror, and the tests). `https://cupel.dev/install` is to redirect to `https://raw.githubusercontent.com/tysont/cupel/main/dist/install.sh`; the domain is not set up, so the README gives the raw URL.
4. **Homebrew**: `dist/homebrew/cupel.rb` is a template with `on_macos`/`on_linux` × `on_arm`/`on_intel` blocks, one `url` and `sha256` each, `bin.install "cupel"`, and a `--version` test. `dist/homebrew/render.sh <version> <SHA256SUMS>` prints the formula with the version and each placeholder's digest, replacing the template's ABOUTME lines with a note of where it was rendered from, and exits 1 naming the archive when `SHA256SUMS` lacks one. The release workflow renders it and commits `Formula/cupel.rb` to `tysont/homebrew-cupel`, which does not exist yet.
5. **npm and pipx wrappers.** `dist/npm` (`package.json` name `cupel`, `bin/cupel.js`, Node 18 or newer for `fetch`) and `dist/pipx` (`pyproject.toml` with `flit_core`, one standard-library module `cupel.py` whose `main` is the `cupel` console script, Python 3.9 or newer) behave alike: the release of the package's own version (`package.json`'s `version`, `cupel.__version__`), the platform mapped to `<os>-<arch>` in Rust's spelling and looked up in a `TARGETS` table equal to `dist/targets.toml`'s, `SHA256SUMS` then the archive from `releases/download/v<version>/`, the digest checked, the archive extracted in a staging directory beside the cached binary and the binary renamed into `<cache>/<version>/<triple>/cupel` (so two first runs at once never see half a file), then run with the caller's arguments and stdio. Node uses `execFileSync` with `stdio: "inherit"` and sets its exit code to the binary's (re-raising a signal); Python `os.execv`s the binary (`subprocess.call` on Windows). A download, checksum, or start failure prints `cupel: …` and exits **3**, Cupel's environment code: an agent reading the code learns nothing was graded, which exit 1 would misreport as a failed gate. `npm` extracts with the system `tar` (bsdtar on Windows reads zip); Python with `tarfile` (the `data` filter where it exists) and `zipfile`. Only the download progress line goes to stderr, and only on first run.
6. **Tests: `crates/cupel-cli/tests/installers.rs`, against a fake release.** One `cupel` archive for the host target is built once per test binary from `CARGO_BIN_EXE_cupel` with `tar`, and served by a `std::net` HTTP server from a temporary directory laid out as GitHub's; its `SHA256SUMS` lists every target (dummy digests for the others). A second release differs only in a wrong digest. The tests: binstall's templates rendered for every target equal `dist/targets.toml`'s archive URL, binary path, and format; ShellCheck finds nothing in `install.sh` and `render.sh`; `install.sh` installs the latest release into `CUPEL_INSTALL_DIR` with the exact stdout including the `PATH` line, into `~/.local/bin` with no `PATH` line when it is on `PATH`, the `CUPEL_VERSION` release from its versioned path (and fails naming `download/v9.9.9/SHA256SUMS` for a missing one), refuses the wrong digest installing nothing, downloads each Unix target's archive under a fake `uname`, and names an unsupported platform; the formula rendered from `tests/fixtures/SHA256SUMS` has each Unix archive's URL with that archive's digest and no placeholder left, is valid Ruby (`ruby -c`), and is refused for a `SHA256SUMS` missing a target; and through each wrapper, installed as its package manager installs it (`npm pack` then `npm install --offline --prefix`; `pip install --target`), with an empty cache: the wrong digest exits 3 leaving no file in the cache, then the first `--version` downloads (exact stderr) and caches, the second downloads nothing, and a `cupel check` whose gate fails exits 1 with the envelope intact (one test over both wrappers, so the two cases are not clones of each other); each wrapper's version and `TARGETS` equal Cupel's and `dist/targets.toml`'s. A test whose tool (ShellCheck, Ruby, Node, npm, Python) is missing reports `SKIPPED`, unless `INSTALLER_TESTS_REQUIRE_TOOLS` is set, when it fails. `make installers` runs the file; `make test` includes it. `pip install` fetches `flit_core` from PyPI, the one network access.
7. **CI**: an `installers` job in `ci.yml` on `ubuntu-latest` and `macos-latest` adds only the pinned toolchain, Node 22, Python 3.12, and ShellCheck 0.11.0 to the image, runs `make installers` with `INSTALLER_TESTS_REQUIRE_TOOLS=1`, and on macOS runs `brew style` on the formula rendered from the fixture. No Windows job.

## Consequences

- A change to the release layout is a change to `dist/targets.toml` and to every installer that embeds it; the tests fail until the binstall templates, both wrappers' tables, and the formula's placeholders agree with the file, and the fake release is built from the file's names, so `install.sh`'s naming is checked through it too. The release workflow (P8.1) agrees with it only once it reads the file or a test compares them; until then a mismatch would surface at the first tag.
- The wrappers' versions are a second and third copy of the workspace version (`package.json`, `cupel.py`); a test fails when either differs from `CARGO_PKG_VERSION`, so a version bump edits three files.
- Nothing is published here. Open: the release workflow steps that publish the npm package (`npm publish dist/npm`, behind an `NPM_TOKEN` secret), the PyPI package (built from `dist/pipx`, behind trusted publishing or a `PYPI_API_TOKEN`), and the rendered formula to `tysont/homebrew-cupel` (behind a token with push access to that repository); creating that repository; the `cupel` names on npm and PyPI, which are unverified; publishing `cupel-cli` to crates.io, without which binstall needs `--git`; and pointing `cupel.dev/install` at the raw script.
- The tests prove the installers against the layout, not against a real release: an end-to-end install from GitHub after the first tag (each route on a clean image) is later work, as is `brew install` from the tap and `brew audit`.
- The Windows target is served by the archive and the wrappers only; their Windows paths (`cupel.exe`, `%LOCALAPPDATA%`, `subprocess.call`, bsdtar for zip) are untested, since CI has no Windows job.
- Exit 3 from a wrapper carries no envelope; an agent that parses stdout on exit 3 finds it empty and the reason on stderr.
