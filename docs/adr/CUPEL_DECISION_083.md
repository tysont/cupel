# CUPEL_DECISION_083: Cached per-test maps, one-run Rust measurement, and per-test selection at `standard`

**Date:** 2026-10-15 · **Status:** accepted · **Phase:** P3 follow-up (7), toward P3.6

## Context

P3.6 (a `tests.mutation.score` gate on Cupel itself) is blocked on cost: every Cupel mutant reran the whole `cargo test --workspace` suite, about 8 minutes each on top of a 6–12 minute floor (P3 Notes, "P3.6 — measurement"). nextest can narrow a run to the tests that cover a mutant (`-E` filterset), but only with a `PerTestMap`, and ADR-080 §2 makes a want only when its producer costs no more than the run's depth: the per-test producers cost `deep`, so `standard` never had a map. They cost `deep` because `tool.llvm-cov-per-test` ran `cargo llvm-cov nextest` once per test (over 20 minutes on Cupel's ~1250 tests before the first mutant, "P3.4 — timing"), and because nothing was cached (follow-up (7)): every `tests --impacted` and every `deep` mutation run measured every test again. ADR-077 and ADR-080 left open how a map is cached, when a cached map is still good, how a stale one is brought up to date, and whether Rust needs one run per test at all.

## Options

**Rust measurement.** (a) One `cargo llvm-cov nextest` run per test (ADR-077 §2): attribution is trivial, cost is N runs. (b) One run with `LLVM_PROFILE_FILE` containing `%p` (cargo-llvm-cov already uses `<target>/<name>-%p-%8m.profraw`): every nextest test is its own process, so each test's profile is a file of its own, but nothing in nextest's output maps a process ID to a test. (c) One run through a nextest wrapper script (experimental, needs a nextest configuration in the repository). (d) One run through a **cargo target runner** (`CARGO_TARGET_<HOST>_RUNNER`, which nextest honours and cargo-llvm-cov passes through): nextest runs every test binary through it with `NEXTEST_TEST_PHASE`, `NEXTEST_BINARY_ID`, and `NEXTEST_TEST_NAME` in the environment, so a shell script can give each test process a profile directory of its own (named by its process ID, inherited by the processes the test starts, such as the `cupel` binary a CLI test runs) and record which test it is; afterwards each directory's profiles are merged (`llvm-profdata merge -sparse`) and exported for that test's binary alone (`llvm-cov export -format=lcov`). Measured on this machine (8 cores, Apple silicon, cargo-nextest 0.9.148, cargo-llvm-cov 0.9.1): on Cupel, (d) took 336 s for the instrumented build and the whole suite and 13 s to export all 1278 test processes' coverage (258 MB of profiles, 38 tests with child processes), against more than 20 minutes for (a) before it was stopped; on the per-test fixture it agrees with (a) line for line (`adds` executes lines 4–6 and 18–20, `scales` 9–11 and 23–25).

**Caching.** (a) The `facts` table in the store: keyed by content hashes of every input, but the store has no notion of "the tests whose inputs changed", so any change rebuilds the whole map. (b) A cache entry per producer and project root beside the coverage reports (`.cupel/cache/<kind>/<producer>/<hash of the root>/{report, sources.json}`, ADR-079), with the same record of every file's BLAKE3 hash: freshness is the same rule, a committed or copied entry works on another machine, and the record says *which* files changed, so a refresh can be partial.

**What a change makes stale.** (a) Lines: re-measure only tests that executed a changed line; needs the old text of every file (or per-line hashes) to diff, and kept tests' line numbers must be shifted. (b) Files: a test is stale when it covers a changed or removed file, or owns one (its own test file; for Go, any `_test.go` of its package, since Go profiles never include test files); new tests are found by measuring every test not kept; a change to build or test configuration (`Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain*`; `go.mod`, `go.sum`, `go.work`; `conftest.py`, `pyproject.toml`, `setup.cfg`, `setup.py`, `pytest.ini`, `tox.ini`) makes every test stale.

**When a map is affordable at `standard`.** (a) Lower the producers' cost class to `standard`: a cold Rust or Python measurement is one instrumented suite run, the same class as a coverage report, but every `standard` mutation run on a repository with no cache would pay it for an optional fact, including runs whose baseline runner cannot use the map. (b) Keep `deep` and let a producer estimate its cost *here and now*: `standard` when it holds a cache entry and refreshing it is cheap.

## Decision

1. **Rust measures in one run** (option (d)). `tool.llvm-cov-per-test` writes a target runner script into its cache entry, runs `cargo llvm-cov nextest --no-report --workspace --no-fail-fast --no-tests=pass` with `CARGO_TARGET_<HOST>_RUNNER` pointing at it (`<HOST>` from `rustc -vV`), then merges and exports each test process's profiles on as many threads as there are cores, with `LLVM_PROFDATA`/`LLVM_COV` or the toolchain's `llvm-tools` (as cargo-llvm-cov finds them). A process that started children is exported with every executable the build made beside the test binary as extra objects. The script unsets the runner variable, so cargo runs inside tests (Cupel's fixtures) do not go through it. `--no-report` keeps the instrumented build, so a refresh builds incrementally. A run that started no test process and exited non-zero failed. IDs are nextest's, as before. Go keeps one `go test -coverprofile` per test; Python keeps one pytest-cov run with test contexts.
2. **Cache.** Each per-test producer keeps one entry per project root: `.cupel/cache/per-test/<producer>/<first 16 hex of BLAKE3 of the root path>/report` (JSON `{version, tests}`, the root's tests relative to the root) and `sources.json` (ADR-079's record: the root, where the tool ran, the report's hash, every file's hash, skipping hidden entries, `.gitignore`d paths inside the root, `ProjectInfo`'s `skip_dirs`, the tools' outputs such as `target`, and `[scope] exclude`). Freshness is ADR-079's rule, shared in `cupel-adapt/src/fresh.rs`; the record is made after measuring, and any file whose hash changed while the tools ran is recorded as changed. A cached map holds paths relative to the root, so an entry made on another machine is read through the tree it sits in. Another entry version, root, or report hash reads as no cache.
3. **Refresh** (option (b), files). Unchanged: the cached tests, nothing run. Changed: stale tests (as above) are measured again with every test the cache does not hold, gone tests are dropped (Go and Python list their tests; Rust runs `-E 'not (<kept tests>)'`, so a test that is not kept, or new, is measured), and the rest are kept as cached. A change in no covered file, owned file, or file that may hold a test (by extension) measures nothing and only rewrites the record. `PerTestMap` (version 2) gains `measured` and `reused`: how many tests the production measured, and how many came from the cache.
4. **Estimate.** `Producer::estimate(ctx) -> Estimate { cost, note }` (default: the cost class, no note) is what producing here would cost now; the scheduler makes a want when the *estimate* is within the run's depth (refining ADR-080 §2). The per-test producers keep cost `deep`; their estimate is `standard` when every cache entry they hold reads back and refreshing is cheap: always for a producer that measures in one suite run (Rust, Python: at most one instrumented suite run, a coverage report's cost), and at most 32 stale tests for one that runs each test alone (Go: about a second per test). With no entry, or more stale tests, it is `deep`. Notes: `cached` (nothing to measure) or `refresh N stale`.
5. **Dry runs.** A planned check's `needs` list each want of its needs' producers that the run would not simply make: with the producer's note (`per-test-map(cached)`, `per-test-map(refresh 3 stale)`) or, when its estimate is beyond the run's depth, with that cost (`per-test-map(deep)`: left out).
6. **Per-test selection at `standard`** follows: with a fresh or cheaply refreshed cache, the mutation engine gets the map at `standard` and each mutant runs only its covering tests, through the baseline's runner when the map is that runner's (ADR-080 §7, unchanged; the engine is not edited). Reuse keys (ADR-080 §10) are unchanged: a selected mutant's suite hash is its covering tests' IDs and their files' content.
7. **`tests --impacted`** reports, per language with a map, `measured` and `reused` (null on a fallback); the text renders `per-test map from <producer> (cached)` or `(N measured, M cached)`.
8. **Cupel's own runner** is nextest: `[lang.rust] runner = "cargo-nextest"` in the root `cupel.toml`, so its mutants can be narrowed. `make test` keeps `cargo test --workspace`.

## Consequences

- The Rust per-test map costs about what a coverage report costs (one instrumented suite run, plus seconds to export), not one run per test. Its producer could be `standard` outright; it stays `deep` so that a `standard` run never pays a cold measurement for an optional fact, and a refresh is what `standard` pays.
- A whole re-measure is needed only for a change to build or test configuration, a producer's cache version, or a root with no entry. Everything else is incremental by file: a one-function change re-measures every test that covers its file, not only those that ran the function (on Cupel, 101 tests cover `crates/cupel-checks/src/metrics.rs`; check modules registered with `inventory` are covered by about 225 tests each).
- Known holes, all of which leave the cached map naming too few tests for some line rather than too many: a change to a file no test's coverage names (fixture data, a `const` or type definition without counters, a new module registered through `inventory`) re-measures nothing, though it can change what other tests execute. A mutant whose covered line the map names no test for still runs the whole suite (ADR-080 §7), so the risk is a false survivor where the map names some but not all covering tests. Deleting the cache directory measures from scratch.
- The waste case: a Rust repository whose baseline runner is `cargo test` but which holds a nextest map cache refreshes it at `standard` and the engine discards it (ADR-080 §7). Only `tests --impacted` or a `deep` run makes such a cache.
- The target runner replaces any `target.<host>.runner` the repository configures for the measurement run, and needs a Unix shell (`sh`); elsewhere the Rust producer fails and `tests --impacted` falls back.
- `TestResults` is still not cached (the other half of follow-up (7)): a baseline is a test *run*, and reusing one would need the same freshness record over every input of the suite; left for later.
- Measured on Cupel (P3 Notes, "P3 — per-test map cache: measurement"): cold 542 s, cached 2 s, and a mutation run selecting 16 tests per mutant instead of the whole suite, but no faster per mutant (562 s each), because a Cupel mutant's cost is then its rebuild (schemata, P4.1) and the `cupel-fixtures::matrix` tests that every check module's mutants select. Selection is necessary for P3.6 but not sufficient.
- The configured coverage command (`cargo llvm-cov`) cleans `target/llvm-cov-target`, which the Rust per-test build shares, so a refresh after a coverage run rebuilds the instrumented workspace; a target directory of its own would keep refreshes incremental.
- The cache does not travel: CI starts without one unless it restores `.cupel/cache/per-test` (or runs `tests --impacted`, or a `deep` run, first).
