# CUPEL_DECISION_116: Trace validation: a JSON-lines logging convention, the `Traces` fact, TLC as the validator, and `spec.trace`

**Date:** 2026-10-17 · **Status:** accepted · **Phase:** P7.2

## Context

Design §5.5: `spec.trace` — "implementation emits trace; validated as a behavior of a TLA+/Quint/P spec (TLC/Apalache)", kind `trace.diverged` (step, state, spec action), cost `exhaustive`, tier 5, wrap. §6.5: a `spec.trace` result against an unverified oracle "is capped at tier 3 and carries `warn: oracle.unverified`". §8.3.2 names `Traces` among the P7 facts without a shape. Design open question 4 asks whether the instrumentation API is "an attribute/macro per language versus a logging convention; decide when P7 starts"; plan §2.5 reserved ADR-007 for that question at P7.2, and the P7 heading still says "`spec.trace` (ADR-007)", but no ADR-007 was ever written: the reference is stale, and this ADR is where the question is decided. ADR-090 made spec oracles (`kind = "spec"`, `spec`, `lang`) whose `verify` runs the language's parser (`sany` for TLA+) and left "model-checking a trivial behavior" to P7; ADR-091 gave checks `uses_oracle`, the run's oracle selection, and the cap applied when the envelope is graded; ADR-093 hands the run's oracle to producers (`ProduceCtx::oracle`).

Still open: how a project gets a trace out of its implementation, what a trace is, who runs the tests that write it, how a trace is checked against a spec (TLC checks specs, not traces), what `Traces` holds, and which languages `spec.trace` supports.

## Options

**Instrumentation.** (a) An attribute or macro per language (`#[cupel::trace]`, a Python decorator, a Java annotation) that logs a function's effect: a library to ship and version per ecosystem, a build step in compiled languages, and seven implementations of one idea — and the attribute still cannot know which spec variables a function changes. (b) A logging convention: the implementation writes its own steps as JSON lines into a directory Cupel names in an environment variable. No library, no build step, any language that can write a file; the implementation decides what a step is, which is knowledge only it has. (b), the lean of the brief.

**Who runs the tests.** (a) A configured command that writes the traces: one more `[lang.*]` key per language and a second test command. (b) The trace file paths named in configuration, written by whatever ran last: stale files validate old behavior, and a cached `TestResults` means no test ran. (c) The producer needs the baseline `TestResults` (green, ADR-076), reruns the baseline's runner once through `ProduceCtx::runners` with `CUPEL_TRACE_DIR` set to a fresh directory, as the flake engine reruns it (ADR-078), and reads what appeared there. (c): nothing to configure, never stale, and the recording run is a scheduled process like every other.

**Checking a trace with TLC.** (a) Ask the user for a trace spec (the TLA+ community's pattern: a module that reads the trace with the `Json`/`IOUtils` community modules and constrains the spec's actions): correct and flexible, but every project writes and maintains one more spec, and it needs the community modules' jar. (b) Generate the trace spec: a module that `EXTENDS` the spec, adds a step counter, holds the logged states as a sequence of records, starts from the spec's `Init` constrained to the first logged state, and allows from each state only the spec's next-state relation (or the action the step named) to the next logged state, on the variables the step logged. TLC then explores exactly the behaviors of the spec that match the trace; with the invariant `cupel_step < Len(trace)`, a violation means the whole trace matched, and a search that ends without one stopped at the deepest matched step. (b): no extra spec, no extra jar, partial states are free (an unlogged variable is left to the spec), and nondeterminism in the spec is explored rather than guessed.

**Apalache, Quint, P.** Apalache checks TLA+ symbolically and would validate the same generated module, but needs its own JVM distribution and a typed spec (type annotations on every variable); Quint's simulator and P's checker read their own languages. A second validator is one more `Traces` producer reading the same convention; none is needed to make the check work.

**Languages.** The convention is a file format and the recording run uses whichever runner the baseline used, so the producer serves every language (`Langs::Any`), as the flake engine does; restricting it would be a list to maintain, not a capability.

## Decision

1. **The logging convention.** When `CUPEL_TRACE_DIR` is set, a test that exercises the implementation writes each behavior to its own `<name>.jsonl` file in that directory (subdirectories allowed); when it is unset, nothing is written. Each non-empty line is one step: `{"state": {...}, "action": "Name", "file": "src/x.rs", "line": 12}`. `state` (required) maps spec variables to their values after the step; a variable left out is unconstrained there. `action` (optional) names a zero-argument action of the spec the step took. `file` and `line` (optional) say where it was logged, relative to the repository root or absolute. Unknown keys, non-objects, a `state` that is not an object, and a non-positive `line` make the trace unreadable. The first line is the initial state.

2. **`Traces` v1** (`cupel-core/src/trace.rs`): `{tool, spec?: {oracle, file, lang}, problem?, traces: [{name, steps, status: conforms|diverged|failed, detail?, divergence?: {step, action?, state, previous?, location?}}]}`, traces by name. `step` counts the initial state as 1; `state` and `previous` are the logged JSON; `previous` is the last state the spec allows (null at step 1). `problem` says why traces were not (all) validated: no oracle, an oracle that is not a spec, a spec in a language the validator does not read, no baseline, a recording run that did not pass, or no trace recorded. Its conformance inventory `conformance/traces.toml` (`conforms`, `diverged`, `diverged-at-start`, `unreadable`) is the first execution-fact inventory: `cupel_fixtures::conformance::EXECUTION` names the execution facts, and each tool producer's real-tool test checks its own fact with `unexhibited` (a construct the tool cannot exhibit is named with its reason), since no language exhibits these constructs.

3. **`tool.tlc`** (`cupel-adapt/src/trace/`): `Langs::Any`, needs `TestResults`, cost `exhaustive`, ready when `tlc` is on `PATH` (the launcher script tla-bin and the TLA+ tools' users install; the hint says how to make one). It reads the run's oracle; for a `tla+` spec it records (decision 1, through the baseline's runner, seeded so `go test` does not serve a cached result) into `.cupel/cache/trace/<runner>/`, reads each trace, and validates it in `.cupel/cache/trace/tlc/<name>/`, holding copies of the spec directory's `.tla` files, the generated `CupelTrace.tla`, and `CupelTrace.cfg` (`INIT CupelTraceInit`, `NEXT CupelTraceNext`, `INVARIANT CupelTraceUnmatched`, and the `CONSTANT`/`CONSTANTS` sections of the spec's own `.cfg`, whose `INIT`/`NEXT` names replace `Init`/`Next`), with `tlc -deadlock -workers 1 -metadir … -config CupelTrace.cfg CupelTrace.tla` and `JAVA_TOOL_OPTIONS` naming a JVM temporary directory inside that directory (SANY writes the standard modules there; in the shared one, concurrent runs overwrite each other's copies). JSON maps to TLA+ as integers, strings, booleans, sequences (arrays), and records (objects); `{"$tla": "<expr>"}` is any TLA+ expression (a set, a model value); a float, `null`, or a name that is not a TLA+ identifier fails the trace. TLC's output reads: `Invariant CupelTraceUnmatched is violated` → conforms; `No error has been found` → diverged after `depth` matched steps (0 when no initial state matched); anything else → failed with the parser's errors or TLC's `Error:` lines. A trace whose steps were all logged in files outside the scope is dropped; one placed nowhere is kept.

4. **`spec.trace`** (`cupel-checks/src/spec_trace.rs`): tier 5, `exhaustive`, needs `Traces`, no settings, `uses_oracle`. One `trace.diverged` per diverged trace (`fail`, `fix_bug`, confidence 1) at the logged `file:line`, titled with the step, action, state, and previous state (or "starts at … which is not an initial state"), evidence `{tool, oracle, spec, trace, steps, step, action, state, previous}`, subject `name|action|state`, repro `cupel check --only spec.trace --oracle NAME [--paths FILE]`. Score `diverged` over validated traces; metrics `traces`, `diverged`, `unvalidated`, only when some trace was validated; notes for `problem` and each failed trace. Combined by sum.

5. **The oracle and the tier.** The run's oracle is chosen as for every check that uses one (ADR-091 §2); a fixture or project with oracles of several kinds names the spec with `--oracle`. Verification stays ADR-090's (the spec parses); a result against a spec that is not verified now is capped at tier 3 with `oracle.unverified` when graded, with no code in the check.

## Consequences

- Open question 4 is closed: a logging convention, with no per-language library; any language can adopt it, and the support matrix shows `spec.trace` supported wherever a runner is.
- The suite runs once more for each language with a spec oracle; tests that do not log are unaffected, and a test that logs when the variable is unset breaks the convention.
- Actions with parameters cannot be named in `action` (the step is then checked against `Next`); naming one fails the trace through TLC's parser error. Records with non-identifier keys, functions keyed by values, and sets need `$tla`.
- A trace is checked as a finite prefix of a behavior: liveness and the spec's invariants are not re-checked (the spec's own model checking is the user's).
- Deferred: **Apalache** (its own JVM distribution, ~200 MB, and a typed spec; the generated module would serve it unchanged), **Quint** (`quint run` validates no given trace; a Quint spec would need translation or Apalache), and **P** (`p check` explores the P program's own schedules, it reads no external trace). A spec oracle in those languages gives a result with `problem` saying `tool.tlc` does not read it. `oracle verify` still only parses a TLA+ spec; model-checking a trivial behavior there remains open.
- One oracle per run (ADR-091): a run with `gen.differential` and `spec.trace` together compares both against one oracle, and the one that does not fit reports it.
