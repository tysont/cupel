# CUPEL_DECISION_084: One suite run for `TestResults`, `CoverageMap`, and `PerTestMap`; a cached baseline; staleness by function

**Date:** 2026-10-15 · **Status:** accepted; §6 (a cached red baseline is returned as recorded) amended by [141](CUPEL_DECISION_141.md) §2 (only a green run is cached); §6 (any change under the root reruns the suite) and §8 (the dry run's suite entries) amended by [149](CUPEL_DECISION_149.md) (an incremental run on a range scope) · **Phase:** P4.4

## Context

A changed `check` on Cupel spends its first 15–20 minutes running the same suite three times, each with its own build, before the first mutant (P3 Notes, "P3.6 — measurement with schemata and the cached map"): the baseline (`tool.cargo-nextest`, ADR-076), the coverage report (`tool.cargo-llvm-cov`, ADR-079, stale after any edit), and the per-test refresh (`tool.llvm-cov-per-test`, ADR-083: 129 tests stale after a one-function edit, because staleness is by file). Where the runner and the coverage tool are one toolchain, one instrumented run already holds all three: the per-test producer's run reports every test's outcome, and its profiles together are the coverage report. The design and ADRs 076–083 give every fact exactly one producer and one production per (kind, language); none says how one production can make several facts, when the scheduler should prefer that to separate ones, or how a baseline is cached. ADR-083 left two items this step closes: staleness by function (open item (1)) and a target directory of the per-test build's own (open item (3)). ADR-083's consequences also left `TestResults` uncached (follow-up (7), second half).

## Options

**How one run makes several facts.** (a) A new fact kind holding the three: every consumer would change, and a check would see how its facts were made. (b) Let any `Producer<F>` also return extra facts: every producer kind is a candidate for its own fact, so the per-test producer would compete with the runners for `TestResults` in `candidates`, pins (`runner = "cargo-nextest"`) would no longer name what runs, and the support matrix would change for every repository with the tools. (c) A separate kind of producer, a **joint producer**, kept beside the per-kind producers: it names each fact it makes and the per-kind producer it stands in for, and is used only where the scheduler would have chosen exactly those producers. Candidates, pins, detection, and the support matrix are untouched; the joint is an optimization of a plan the registry already made.

**When the scheduler prefers the joint run.** (a) Always, when it is ready: a run that needs only `TestResults` (`tests.flaky`) would pay an instrumented build it does not need, and a run that needs only coverage would replace the configured command with another. (b) When it saves a run: the run needs at least two of its facts that would each be produced by a run of its own, or the joint holds a fresh cache and runs nothing.

**Which coverage command the joint may replace.** The `[lang.<id>] coverage` command is free text (ADR-079). (a) Replace whatever is configured: a command with other flags (`--cov-branch`, `-coverpkg`, `--ignore-filename-regex`) would silently measure something else. (b) Replace only the toolchain table's default command for the coverage producer, which the joint reproduces exactly; any other command keeps its own run.

**Caching `TestResults`.** (a) In every runner: every runner test and fixture run would become a cache hit in a reused directory, and a flaky or environment-dependent suite could be hidden for every language at once. (b) In the joint's cache entry, under the ADR-079 record that already decides whether coverage and the per-test map describe the tree: a baseline whose sources are unchanged is not rerun, wherever the joint applies.

**What a change makes stale** (ADR-083 §3 decided files). (a) Files, as today. (b) Functions: compare the changed file with what the cache measured and re-measure only tests that ran a line of a changed function. This needs the measured file's old lines (ADR-083 rejected storing them only because file staleness did not need them) and the current functions (`Symbols`).

## Decision

1. **Joint producers** (`cupel_core::JointProducer`, registered with `ProducerRegistry::register_joint`, listed by `joints_for(lang)`; kept apart from the per-kind lists, so `candidates`, pins, `describe`, and `SupportMatrix` never see them). A joint has an ID, languages, `needs` (made first, as for any producer), `makes()` — each fact kind it makes with the producer ID it stands in for — `availability`, `estimate`, and `produce(ctx, scope, sink) -> Vec<Produced>`, which may make fewer kinds than it names (a failed build makes `TestResults` alone). No fact kind is added; checks and the per-kind producers are unchanged.

   | Joint | Language | Makes (stands in for) | One run |
   |---|---|---|---|
   | `tool.llvm-cov-nextest` | Rust | `TestResults` (`tool.cargo-nextest`), `CoverageMap` (`tool.cargo-llvm-cov`), `PerTestMap` (`tool.llvm-cov-per-test`) | `cargo llvm-cov nextest --no-report` with ADR-083's target runner and nextest's `cupel` JUnit profile |
   | `tool.pytest-cov-contexts` | Python | `TestResults` (`tool.pytest`), `CoverageMap` (`tool.pytest-cov`), `PerTestMap` (`tool.pytest-cov-per-test`) | `pytest --cov --cov-context=test --cov-report=lcov:… --junitxml=…` |
   | `tool.go-test-cover` | Go | `TestResults` (`tool.go-test`), `CoverageMap` (`tool.go-coverprofile`) | `go test -json -coverprofile=… <packages>`; the per-test map stays one run per test (ADR-083), refreshed by its own producer |

2. **When the fact store uses a joint** for `(kind, lang)` (`FactStore`, `joint.rs` in `cupel-core`): the kind is one it makes; it is `Ready`; for every kind it makes, the producer the store would choose (the first `Ready` candidate, after pins and detection) is the one it stands in for; its estimate is within the run's depth; and it saves a run — its estimate's note is `cached`, or at least two of its kinds are *reached* by the run and would each run on their own (not yet made, and their chosen producer's estimate has no `cached` note). *Reached* is the closure of the selected tasks' needs through every producer's needs and, within the depth, wants (`Scheduler::run` computes it per language before the baseline); a verb's `Production` (`tests --impacted`) reaches nothing, so it uses a joint only from its cache. Every fact the joint makes is kept as if produced on its own; `TestResults` passes the exit-4 gate as before (ADR-076 §5). A joint that fails, or does not make the kind asked for, leaves that kind to its per-kind producer; it is tried once per language. A want already made counts as affordable (`ensure_wants`), so the engine gets the joint's per-test map at `standard` even without a cache.
3. **Which coverage command.** A joint is `Unconfigured` (`lang.<id>.coverage`) unless the configured coverage command is the table's default for the producer it stands in for, compared word by word with the launcher (`<m>`) and package patterns (`<packages>`) free: `cargo llvm-cov --lcov --output-path {out}`; `[<launcher> -m] pytest --cov --cov-report=lcov:{out}`; `go test -coverprofile={out} <patterns>`. Any other command keeps its own run, so the shared fixture repositories (whose mutation fixtures configure `--cov-branch` or a committed report) keep their goldens.
4. **Rust.** The instrumented build has a target directory of its own, `target/cupel-llvm-cov` (`CARGO_LLVM_COV_TARGET_DIR`), which `tool.llvm-cov-per-test` uses too, so the configured `cargo llvm-cov`'s clean of `target/llvm-cov-target` no longer discards it (ADR-083 open item (3)). Before a run, the directory's `*.profraw` are removed (`--no-report` never cleans). `TestResults` come from nextest's JUnit report (`target/nextest/cupel/junit.xml`, as `tool.cargo-nextest` reads it, IDs nextest's, `runner = tool.cargo-nextest`); the `PerTestMap` from each test process's profiles (ADR-083 §1); the `CoverageMap` from `cargo llvm-cov report --lcov` after every test process's profiles are linked into the target directory, so it is the report `cargo llvm-cov` itself makes of the same run. Line hits are a nextest run's (one process per test), so code that runs once per process (a `LazyLock`, `inventory` collection) counts once per test, not once per test binary as under `cargo test`; which lines ran is the same, and every consumer reads only whether a line ran.
5. **Python.** One run with `COVERAGE_FILE` under `.cupel/` (the user's coverage configuration still applies, unlike the per-test producer's own rc file), then `coverage json --show-contexts` for the per-test lines (ADR-077's `tests_of`). **Go.** One `go test -json -coverprofile` run; `TestResults` from test2json, the profile through `go.mod` as `tool.go-coverprofile` reads it.
6. **Cache and the baseline** (follow-up (7), second half). Each joint keeps one entry per project root, `.cupel/cache/suite/<joint>/<root>/` with `report` (`{version, results, coverage}`, relative to the root) and ADR-079's `sources.json`; a joint that makes the per-test map also writes the per-test producer's entry (ADR-083) with the same record. The joint is *cached* when its entries read back and nothing under the root changed; then it makes its facts from them and runs nothing. A cached red baseline is returned as recorded and refuses the run (exit 4) exactly as a fresh one; a run with an incomplete invocation (a build failure, a crash) is not cached. Any change under the root reruns the suite: the mutation and flake engines always get a real baseline of the tree they mutate.
7. **Staleness by function** (refining ADR-083 §3; `per_test/functions.rs`). A per-test cache entry also stores, for every file some test covers, a 64-bit hash of each line as measured (`lines`). A changed file is compared line by line with them (Myers' diff on the hashes); each hunk must lie inside one function of the current `Symbols` (the innermost whose span holds it) that has at least one unchanged line; the function's old span is its current span mapped back through the diff, and the tests stale for that file are those that executed a line of an old span. Kept tests' lines in the file move with the diff. The file rule applies instead when a hunk lies outside every function (a new or deleted top-level function, imports, constants, type definitions, doc comments above a function), touches a function with no unchanged line (new, or rewritten whole), when the file has no `Symbols` in the run's scope, when there are no stored lines for it, or when its lines did not change at all though its hash did (edited while measuring). Owned files, whole-suite files, and new tests are unchanged from ADR-083. The per-test producers want `Symbols`; `Producer::estimate` takes the producer's needs and wants already made (`&Upstream`), so the estimate and the dry run count stale tests by the same rule.
8. **Dry runs.** A planned check's `needs` gain, per language, the suite facts it reaches: one entry for a joint run naming its kinds, `test-results+coverage-map+per-test-map(one run)` or `(cached)` (Go: `test-results+coverage-map(one run)`), else one entry per fact that runs on its own, `test-results(run)`, `coverage-map(run)` or `coverage-map(cached)`, beside ADR-083's `per-test-map(…)` entries, which a joint's entry replaces.

## Consequences

- A changed run on a repository whose runner and coverage tool are one toolchain runs its suite once before the first mutant, and an unchanged one not at all. The floor of P3.6 becomes one instrumented suite run.
- A cold run on Cupel now gets a per-test map at `standard` from the joint run, so mutants are narrowed on the first run too.
- The joint applies only where the registry already chose its producers and the coverage command is the default; a customized command, a `cargo test` baseline, or a pinned `unittest` keeps separate runs, as before. Making the joint recognize more commands is a table change in its module.
- Plain runners do not cache: a `tests.flaky`-only run on a repository without a joint (JavaScript, TypeScript, `cargo test`, `unittest`) still runs its baseline every time.
- Rust hit counts differ from `cargo test`'s for once-per-process code (rule 4); a `CoverageMap` compared byte for byte with `cargo llvm-cov` under `cargo test` can differ there, never in which lines ran.
- Staleness by function names fewer tests than the file rule, and inherits its holes (ADR-083): a change outside every function falls back to the file, so the new holes are only those of a function's own lines — a change inside one function that changes what *another* function executes without that one running (a `const fn` evaluated at compile time, a closure stored and called later by a test that did not run the function) keeps a test that is now stale. A mutant whose covered line the map names no test for still runs the whole suite (ADR-080 §7).
- Storing line hashes grows a per-test entry by about 20 bytes per covered line (about 2 MB on Cupel).
- The joint's runs need a Unix shell for Rust (ADR-083) and `coverage` beside `pytest` for Python; without them the joint is `MissingTool` and the separate producers run.
