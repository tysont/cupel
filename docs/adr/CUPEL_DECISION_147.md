# CUPEL_DECISION_147: A hard cap on a mutant's run, and slow tests left out of whole-suite mutant runs

**Date:** 2026-10-24 · **Status:** accepted; §1 amended by [148](CUPEL_DECISION_148.md) (a mutant's run is bounded in memory as well as time, and the slots share the cores) · **Phase:** P9.F6

## Context

A mutant's run gets `max(2 s, timeout_factor × reference)` (ADR-080 §9, ADR-082 §6), where the reference is the unmutated file's tests timed in the slot, rebuild included. Nothing bounds it from above. Group 1's full-tree deep run on serde_json (P9.9) held the machine for five hours: a mutant that turns a parser's loop into one that never ends makes `cargo test`'s integration binary (one process holding every test of `tests/test.rs`) run until the limit, and with that binary's long reference each such mutant cost about nine minutes. Per-test selection (ADR-083) narrows a mutant's run to the tests a per-test map says cover its site, but only for a runner that has a map and can run one test alone; every other mutant runs the whole suite, and a test that is slow in the baseline is then paid in full by every mutant whatever it mutated. The owner's ruling of 2026-10-24 (plan, P9 Notes): `max_mutant_timeout` (default 120 s) under `[checks."tests.mutation"]` caps a mutant's run above `timeout_factor`; a test no runner can narrow whose baseline exceeds 60 s is left out of mutant runs with an `info` finding `mutant.slow-test-excluded`; which tests each runner can narrow is documented.

Three things the ruling leaves open. (1) The design says "a producer never reads `[checks.*]`" (§6.7, plan §2.8): the engine, a producer, reads only `[lang.<id>] mutation = {...}`, and the check, which owns `[checks."tests.mutation"]`, only scores outcomes after the time is spent. The `[checks.<id>]` table itself exists (ADR-017, ADR-111: declared settings, per-language overrides, `describe <check>`, the README's generated settings table); what is missing is a way for a check's setting to reach the producer of a fact it needs. (2) "Cannot be narrowed" needs a definition per runner and per run. (3) How a test is left out of a run.

## Options

**Reaching the engine.** (a) Put the cap in `[lang.<id>] mutation = { max_mutant_timeout }` beside `timeout_factor`: no new mechanism, but not what the owner ruled, and a cap on wall time is a policy of the check (how long a mutant may cost the run), not a tool choice. (b) Let the CLI, which knows both, copy `[checks."tests.mutation"].max_mutant_timeout` into the engine's `[lang.*]` table: the CLI names a check and the engine's key, a special case nothing else follows. (c) A setting a check declares can say which fact it configures (`SettingSpec::configures`); the scheduler hands the configured values of every registered check's settings for a fact to that fact's producers, for the language being produced (`ProduceCtx::settings`). The producer still names no check and never sees a check's table, only named values a check declared for its fact; the check validates them, `describe` lists them, and the per-language override works as for any setting. Chosen: (c).

**What "cannot be narrowed" means.** (a) Per runner only: a runner that can run one test by name narrows every test. But nextest, pytest, and `go test` can each run one test, and their mutants still run the whole suite whenever there is no per-test map for them (at `standard` without a cache, or for a site the map names no test for), so a slow test there costs every mutant as much as under `cargo test`. (b) Per mutant run: a test is in a mutant's run either because per-test selection chose it (the map says it executes the mutated site) or because nothing narrowed the run. A chosen test stays, since it is the test most likely to kill the mutant and the cap bounds it. A test that is there only because the run was not narrowed is a candidate. Chosen: (b), with what each runner can narrow documented below, since that decides which mutants run the whole suite.

**Leaving a test out.** (a) Drop it from the selection by running every other test by name: only for runners that narrow to tests, and a command line as long as the suite. (b) A selection of its own, `TestSelection::Except(ids)`, which a runner turns into the flag that deselects tests where it has one: `cargo nextest` `-E 'not (…)'`, `pytest` `--deselect`, `go test` `-skip` (Go 1.20 or newer). A runner with no such flag cannot take it, the slow test stays in, and the cap bounds it.

## Decision

1. **The cap.** `tests.mutation` declares `max_mutant_timeout`, a duration (`TimeLimit`: `90s`, `2m`, `250ms`), default `120s`, under `[checks."tests.mutation"]` with per-language overrides `[checks."tests.mutation".lang.<id>]`. A mutant's run gets `min(max_mutant_timeout, max(2 s, timeout_factor × reference))`; a run that reaches it is `timeout` as before. `[lang.<id>] mutation = { operators, jobs, timeout_factor, strategy }` stays where it is. A value that is not a duration is a configuration error at plan time (`ConfigError::CheckSetting`, as every check setting). The cap is not part of a mutant's cache key, as `timeout_factor` is not: a stored `timeout` is reused under a larger cap until its function, tests, or toolchain change.
2. **Settings for a fact.** `SettingSpec` gains `configures: Option<FactKind>` (absent from JSON when `None`). The fact store gives each producer of a kind, as `ProduceCtx::settings`, the value of every setting a registered check declares for that kind, as `[checks."<id>"]` and its override for the language configure it; an unconfigured setting is absent and the producer applies its own default, which `tests.mutation`'s declared default matches (a test holds them equal). Two checks declaring one name for one kind: the first by check ID wins. Only `max_mutant_timeout` configures a fact today. Design §6.7's "a producer never reads `[checks.*]`" becomes "a producer never reads a check's table; it reads the settings a check declares for the fact it makes". Joint producers (ADR-084) get none.
3. **Slow tests.** A test of the baseline `TestResults` whose `duration_ms` is over **60 000** is slow. When the engine runs a covered mutant over the whole suite (no per-test selection for it) and the runner can leave tests out (it gives a command for `Except`), every slow test is left out of that mutant's run, and of the reference and schemata validation runs of the files whose mutants run the whole suite, so the timeout is measured on what the mutants run. Mutants whose tests a per-test map selected run them all, slow or not. The suite hash a whole-suite mutant's cache key holds becomes the baseline's suite hash with the left-out IDs when any is left out, so a test becoming slow or fast reruns those mutants; with none left out it is the baseline's as before, and stored outcomes stay valid.
4. **The fact and the finding.** `MutationOutcomes` gains `excluded: [{id, file, baseline_ms}]`, the slow tests left out of whole-suite runs (absent from JSON when empty; an optional field, so the fact's version stays 2). `tests.mutation` emits one `mutant.slow-test-excluded` (`info`, action `review`, evidence `{test, file, baseline_ms}`) per entry, naming the test and its baseline duration. The score counts the mutants as before, over the tests that ran (ADR-141 unchanged).
5. **What each runner can narrow** (ADR-077 §3, ADR-083; a mutant is narrowed only with a per-test map from the baseline's runner, which exists for `cargo-nextest`, `go test`, and `pytest`):

   | Runner | Runs one test alone | Per-test map | Leaves a test out |
   |---|---|---|---|
   | `cargo-nextest` | every test (its own process; a `trybuild` test is one test whose cases it cannot split) | yes | `-E 'not (…)'` |
   | `cargo-test` | none (the whole workspace; an integration binary runs whole) | no | no (libtest reports no durations on stable Rust, so no test is known slow) |
   | `go test` | each `Test` function (`-run` per package, by name) | yes | `-skip` (by name, in every package) |
   | `pytest` | each node ID and file | yes | `--deselect` |
   | `unittest` | each dotted ID | no | no |
   | `jest`, `vitest` | test files only | no | no |
   | Surefire (`maven`, `gradle`) | classes and methods (`-Dtest`, `--tests`) | no | no |
   | `clojure.test` (Cupel's runner script) | each var and file | no | no |

   A runner without a map runs every mutant over the whole suite; one that cannot leave a test out keeps its slow tests in every such run, and the cap bounds each.

## Consequences

- A mutant that loops costs at most two minutes by default, whatever the suite's length; on serde_json each looping mutant falls from about nine minutes to two. A suite whose honest mutant runs exceed the cap reports them as `timeout` (left out of the score); raising `max_mutant_timeout` is the remedy, and the finding's text says the tests ran past their timeout.
- With `cargo test`, the integration binary of the defect is still run whole by every mutant: libtest gives no per-test durations and `cargo test` cannot leave a binary out without listing every other target, so only the cap applies. `cargo-nextest` as the runner (`[lang.rust] runner = "cargo-nextest"`) gets durations, per-test selection, and exclusion.
- A slow test that is the only one to kill some mutant makes it survive in a whole-suite run; the finding names the test, so the survivor can be read with it. A per-test map (cached, or `--depth deep`) runs such a test for the mutants it covers.
- `go test -skip` and `-run` match by name in every package of a root, so a slow `TestX` leaves out every `TestX` of that root.
- A check can now configure a fact's producer through a declared setting; the next such setting needs only `configures` on its spec. A plugin check may declare one too, and a plugin producer receives none (the plugin protocol carries no `settings`).
