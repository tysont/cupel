# CUPEL_DECISION_089: Running plugins: requests, fact files, validation, budget, and errors

**Date:** 2026-10-16 · **Status:** accepted · **Phase:** P5.1

## Context

Design §8.6 fixes the three subcommands (`describe`, `plan < RunRequest`, `run < RunRequest`), lists what a `RunRequest` carries, and states four host duties: validate the manifest, enforce the budget with SIGTERM then SIGKILL, reject findings of undeclared kinds and facts that fail schema validation, and turn a non-zero exit without a `result`/`fact` event into `status: error`. It leaves open: what "validated against the schema" means for a manifest and a fact; the exact shape of the manifest's `kind` and of the `result` and `fact` events; how a check plugin receives facts "as JSON files" and a producer plugin its upstream facts; what a check plugin's `plan` failing does to the run (a native plan error aborts the scheduler); what the host does with other events, extra output, and a plugin that exits non-zero after reporting; how the budget is computed and how long SIGTERM is given; and what a request carries where `CheckCtx` has no seed or depth.

## Options

**Schema validation.** (a) A full JSON Schema validator against the published schemas: a large dependency (ADR-043 declined it) for documents whose published schema is generated from Rust types anyway. (b) Deserialize into the very types the schema is generated from, then check what types cannot say (ID shapes, version equality, unique finding kinds). Serde ignores unknown fields, so a newer plugin's extra keys pass; a missing or mistyped field fails with serde's message naming it.

**When to deliver findings.** (a) Stream each event to the run as it arrives: a later protocol violation would leave findings from a run the host then calls an error. (b) Read the whole output, validate everything, then emit: a plugin's findings reach the envelope only from a run the host accepted.

**A failing `plan`.** (a) Propagate the error: one broken plugin aborts every check of the run, against ADR-041 (one check's failure must not stop the others). (b) Fall back to the cost-class estimate (`Plan::estimate(cost, files)`), so the run proceeds and the plugin's `run` reports its own failure as `error`.

## Decision

1. **Manifests.** `describe` prints one JSON object: a check's `Manifest` (ADR-012, unchanged) with `"kind": "check"`, or a `ProducerManifest` `{kind: "producer", id, version, provides: {kind, version}, languages: [lang], needs, wants, cost, stability, summary}`. The host deserializes it into `PluginManifest` and then requires: a check ID of the form `<group>.<name>`; at least one finding kind, each unique, namespaced (`<group>.<name>`), with an evidence schema that is an object; metric names unique; `version ≥ 1`; for a producer, an ID starting with `plugin.`, at least one language, a provided kind with a payload type, and `provides.version` equal to that kind's current version (`schema::fact_version`). A language the binary does not register is refused too (a typo would otherwise make the producer silently serve nothing).
2. **Requests.** `RunRequest` = `{protocol: 1, root, scope: {files, symbols}, depth, budget_ms, seed, config, facts: {kind: path}, scratch, toolchain: {cupel}, write}`. `scope.files` are the language's files in scope, relative to `root`; `scope.symbols` is `null` (every symbol in the files) or the selected symbols' `{file, line, col}` keys, which is what a scope carries; hashes and spans are in the `symbols` fact for a plugin that declares it. A check plugin's `config` is its resolved `[checks."<id>"]` slice with the language override merged; a producer plugin's is its language's `[lang.<id>]` table (design §6.7: checks never read `[lang.*]`, producers never `[checks.*]`). `seed` and `depth` are the run's for a producer and `null` for a check, whose context carries neither (ADR-078 gives seeds to producers only); `budget_ms` is the time left before the run's cancellation fires (`--timeout`, `--budget`, or a daemon client's hang-up), `null` without a deadline. `write` is `false`: no plugin is permitted writes outside its `scratch` directory in this step.
3. **Fact files.** A check plugin's `run` gets one file per declared kind the run produced, `<scratch>/<kind>.json`, where `scratch` is `.cupel/work/<run>/plugins/<check-id>/`; a kind the run could not produce (a want) is absent from `facts`. A producer plugin gets its needs and the wants that were made, under `.cupel/work/plugins/<producer-id>/`. Files hold the fact exactly as it serializes (`Facts::json`, `Upstream::json`). `plan` gets the same request with `facts` empty.
4. **Events.** `run` prints JSON lines; blank lines are ignored. A check plugin may print `finding` (a `Finding`, design §7.2), `progress` (design §7.4), and exactly one `result` `{ev: "result", status, score, metrics, notes}` with `status` one of `pass | fail | partial | error`; the host fills `id`, `tier`, `cost`, and the finding count from the manifest and the events. A producer plugin prints exactly one `fact` `{ev: "fact", kind, version, payload}` and nothing else. Any other line, event, or count is a protocol error.
5. **Validation.** A finding must name the plugin's check, a kind its manifest declares, and evidence valid under that kind's schema (`cupel_plugin::evidence`, ADR-043's subset; a schema keyword outside it is an error, not a pass). `metrics` must be declared scope metrics. A fact must have the provided kind and version, and its payload must deserialize into the kind's type. The host reads the whole output, validates everything, and only then emits the findings and progress, in order, to the run.
6. **Exit status.** A plugin that exits non-zero or is ended by a signal without a valid `result`/`fact` is an `Error::Plugin` naming the plugin, the exit, and the last lines of its standard error; the scheduler records it as the check's `status: error` with that note (or, for a producer, as an absent fact, so the checks that need it are `error`), never `pass`. A plugin that reports a valid `result`/`fact` and then exits non-zero is accepted, with a note naming the exit code on a check's result. Any protocol violation is an `Error::Plugin` the same way.
7. **Budget.** Every plugin process runs in its own process group under the run's `Cancellation` (`Process`, ADR-076 §3); `describe` and `plan` also under a 10-second child limit. When the cancellation fires, the host sends SIGTERM to the group, gives it 2 seconds to exit, then sends SIGKILL; the call ends with `Error::Cancelled`, which the scheduler reports as a native check's cut-short run (`partial`, `timeout`/`budget` skips, exit 5). `Process::terminate(grace)` adds this to the one way Cupel runs programs; native producers keep the immediate kill.
8. **A failing `plan`** falls back to `Plan::estimate(manifest.cost, files in scope)`; `run` still runs and reports for itself.
9. **Combination.** A plugin check's per-language results combine by the `Check` trait's defaults (weighted mean score, largest metric value, ADR-041, ADR-060); it is never family-wide (ADR-051) and reads no base side (ADR-056). Manifest fields for these wait for a plugin that needs them.

## Consequences

- A plugin's protocol mistakes are visible as `error` results with a note that says what was wrong, and never as a passing check or a fact a check silently misreads.
- A plugin in any language needs only a JSON library; the Rust, Python, and TypeScript reference plugins use their standard library or `serde_json` alone.
- Facts reach plugins as files Cupel writes under `.cupel/work/`, which is gitignored; large facts cost a serialization per run.
- A plugin that prints megabytes of findings is held in memory until it exits, as every native producer's tool output is.
