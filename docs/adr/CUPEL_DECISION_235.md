# CUPEL_DECISION_235: npm and PyPI publish through trusted publishing, the tap through a deploy key, each turned on by the owner after registering

**Date:** 2026-11-14 · **Status:** accepted · **Phase:** v0.3.0, item publishing · Amends [128](CUPEL_DECISION_128.md)

## Context

ADR-128 gated each publish job on a long-lived repository secret (`NPM_TOKEN`, `PYPI_API_TOKEN`, `HOMEBREW_TAP_TOKEN`, `CARGO_REGISTRY_TOKEN`) probed by a `secrets` job; ADR-146 named the packages `cupel-cli` and kept `publish-crates` a clean skip while `cupel-core` on crates.io belongs to another project. No secret or variable has been set on `tysont/cupel`, so every release so far (through v0.2.9) skipped all four. On 2026-11-14 `cupel-cli` answered 404 on both `registry.npmjs.org` and `pypi.org/pypi/cupel-cli/json`, and `tysont/homebrew-cupel` was public with no commits.

The owner's ruling, verbatim: "Configure trusted publishing via GitHub OIDC for npm (cupel-cli) and PyPI (cupel-cli) in release.yml — no long-lived tokens. Publish the Homebrew formula to tysont/homebrew-cupel from the release workflow. crates.io stays skipped per ADR-146. Each publish job skips cleanly until its registry has the trusted publisher registered. Write docs/release/PUBLISHING.md with the exact one-time steps I must do on npmjs.com and pypi.org (package name, repository, workflow file name, environment name)."

What the registries require, as documented on 2026-11-14:

- **npm** ([trusted publishers](https://docs.npmjs.com/trusted-publishers), [`npm trust`](https://docs.npmjs.com/cli/v11/commands/npm-trust)): npm CLI 11.5.1 or later and Node 22.14.0 or later; `id-token: write`; GitHub-hosted runners only. The publisher names the user (`tysont`), the repository (`cupel`), the workflow file name only (`release.yml`), and optionally an environment. Provenance is generated automatically for a public package published by OIDC from a public repository; `--provenance` is not needed. `package.json`'s `repository.url` must match the repository (`git+https://github.com/tysont/cupel.git` does). Configurations created after 2026-09-03 allow only `npm stage publish` unless "npm publish" is also ticked. **"The package you're configuring must already exist on the npm registry"**, and **"a newly created trusted publisher configuration must complete its first successful publish within 2 days"**, or it expires and can be neither used nor edited. npm does not check the configuration when it is saved.
- **PyPI** ([creating a project through OIDC](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/), [adding a publisher](https://docs.pypi.org/trusted-publishers/adding-a-publisher/), [pypa/gh-action-pypi-publish](https://github.com/pypa/gh-action-pypi-publish)): a *pending publisher* registered from the account's Publishing page (`https://pypi.org/manage/account/publishing/`) creates the project on its first use, so no project need exist; it "does not create a project or reserve a project's name until it is actually used to publish". The fields are the project name, owner, repository, workflow file name, and an environment ("optional but strongly recommended"). The action needs `id-token: write`, runs only on Linux, generates attestations by default, and advises building in a separate job so the job holding the OIDC token runs nothing else.

The questions:

1. How a publish job "skips cleanly until its registry has the trusted publisher registered", when nothing in a workflow can ask a registry whether it trusts the workflow without trying to publish.
2. How npm's first publish happens, since npm cannot trust a workflow for a package that does not exist.
3. What credential lets the release workflow push to another repository, the tap.
4. How the job handles a tap with no branch.

## Options

**1. The gate.** (a) Attempt the publish and treat an authentication failure as a skip: indistinguishable from a broken configuration, which must fail the run, and npm's OIDC failure surfaces as a generic `ENEEDAUTH`/404. (b) Probe the registry's API for a configured publisher: npm's `npm trust list` needs the owner's 2FA session, and PyPI exposes publishers only to the project's owners. (c) A repository variable the owner sets once the publisher is registered, `NPM_TRUSTED_PUBLISHING` and `PYPI_TRUSTED_PUBLISHING`, read by the probe job as ADR-128's secrets are, with the same notice and step-summary line when it is not `true`. Variables hold no secret, so this adds no credential; the owner's act of registering and the act of turning the job on stay one step apart and both are written down. Chosen: (c). A job-level `if` can read `vars` directly, but going through the probe keeps one place that writes every skip reason and one shape for every publish job (`needs: publishers`, `if: needs.publishers.outputs.<registry> == 'true'`). The probe job is renamed `publishers`, since it no longer reads only secrets.

**2. npm's first publish.** (a) A granular access token stored as a secret for the first release: a long-lived token, against the ruling. (b) The owner publishes the first version by hand from a checkout of an already-released tag, signed in with `npm login`, which since 2025-12-09 issues a short-lived session token (two hours at launch, [GitHub changelog](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/)) rather than a long-lived one, then registers the trusted publisher and sets the variable. (c) `npm stage publish` from the workflow: staging also needs a trusted publisher, so it also needs the package. Chosen: (b), with the version of the latest release (the wrapper downloads its own version's binary, so `cupel-cli@0.2.9` from tag `v0.2.9` works the moment it is published). Because the configuration expires two days after it is created unless used, the owner registers it within two days before pushing the next tag. PyPI needs no bootstrap: its pending publisher is used by the first tag after the variable is set.

**3. The tap credential.** `GITHUB_TOKEN` cannot push to another repository. (a) A fine-grained personal access token scoped to the tap: long-lived (up to a year or unlimited) and tied to the owner's account. (b) A GitHub App installed on the tap, its private key as a secret, minting a one-hour installation token per run: least standing privilege, but an App to create and an extra action (`actions/create-github-app-token`) to pin, for one repository. (c) An SSH deploy key with write access on `tysont/homebrew-cupel` only, its private half a repository secret `HOMEBREW_TAP_DEPLOY_KEY`: it can reach exactly one repository, belongs to no user account, needs no new action, and is revoked by deleting it from the tap. Chosen: (c). The job pins github.com's published Ed25519 host key (`gh api meta`) into a known-hosts file and pushes with `StrictHostKeyChecking=yes`, so the key is never offered to a host that is not GitHub. The secret's probe stays as ADR-128 wrote it.

**4. The empty tap, and where the push logic lives.** Inline YAML cannot be tested against a repository. A script beside `render.sh`, `dist/homebrew/publish.sh <tag> <SHA256SUMS> <tap-url>`, clones the tap (an empty clone has an unborn branch), renders `Formula/cupel.rb`, writes a `README.md` only when the tap has none, commits as `github-actions[bot]` when anything changed, and pushes `HEAD:main`, which creates `main` on the first run. Tests drive it against a local bare repository.

## Decision

1. **`publishers` job** (was `secrets`): `needs: release`, tag pushes only; `variable npm NPM_TRUSTED_PUBLISHING`, `variable pypi PYPI_TRUSTED_PUBLISHING`, `secret homebrew HOMEBREW_TAP_DEPLOY_KEY`, `secret crates CARGO_REGISTRY_TOKEN`. A variable gate is open only when its value is exactly `true`; a secret gate when the secret is non-empty. Each closed gate writes `::notice title=publish-<registry>::skipped: <reason>` and the same line to the step summary.
2. **`publish-npm`**: `environment: npm`; `permissions: contents: read, id-token: write`; `actions/setup-node` v7.1.0 pinned by SHA with Node 24.22.1 (npm 11.19.1); `npm publish ./dist/npm --access public`. No token, no `.npmrc`; provenance comes with OIDC.
3. **`pypi-build`** (gated like `publish-pypi`, no extra permissions): `build` 1.6.1 in a venv builds `dist/pipx` and uploads the sdist and wheel as the `pypi-dists` artifact. **`publish-pypi`**: `needs: [publishers, pypi-build]`, `environment: pypi`, `permissions: contents: read, id-token: write`; downloads the artifact and runs `pypa/gh-action-pypi-publish` v1.14.3 pinned by SHA, which uploads with attestations. `twine` and `PYPI_API_TOKEN` are gone.
4. **`publish-homebrew`**: writes the deploy key and github.com's host key under `$RUNNER_TEMP`, sets `GIT_SSH_COMMAND`, downloads the published `SHA256SUMS`, and runs `dist/homebrew/publish.sh "$GITHUB_REF_NAME" "$RUNNER_TEMP/SHA256SUMS" git@github.com:tysont/homebrew-cupel.git`. `HOMEBREW_TAP_TOKEN` is gone.
5. **`publish-crates`** is unchanged (ADR-146), gated on `needs.publishers.outputs.crates`.
6. **Only `publish-npm` and `publish-pypi` hold `id-token: write`**; the workflow's default stays `contents: read`. The environments' names are the ones the registries' publishers name; restricting each to `v*` tags is a recommended owner step, not something the workflow can require.
7. **`docs/release/PUBLISHING.md`** lists the owner's one-time steps: GitHub environments and variables, npm's hand-published first version and its trusted publisher, PyPI's pending publisher, the deploy key, how to verify after a tag, and how to roll back.
8. **Tests**: `crates/cupel-cli/tests/release.rs` checks the probe's gates, that every publish job is gated on its output, that only the Homebrew and crates jobs read a secret, that only the npm and PyPI jobs hold an OIDC token and each names its environment, that no registry token name appears in the workflow, that the PyPI build is apart from the upload, the deploy-key push, and the pinned action list; `crates/cupel-cli/tests/installers.rs` drives `publish.sh` against an empty tap, an unchanged formula, a tap with its own README, and an incomplete `SHA256SUMS`, and shellchecks it.

## Consequences

- A tag pushed before the owner does anything still succeeds, with `publishers` writing four skip notices (npm and PyPI: variable not `true`; Homebrew and crates.io: secret not set) and every publish job skipped, as ADR-128's runs did.
- Setting a variable without registering the publisher fails `publish-npm` or `publish-pypi`, as a set secret with a bad token failed in ADR-128: an attempted publish that cannot authenticate is an error.
- The install routes (`routes.rs`) stay pending: flipping npm, pipx, or Homebrew live is still ADR-128's code change after the package exists.
- npm's configuration expires two days after creation if unused, so registering early and tagging late leaves `publish-npm` failing on a dead configuration; PUBLISHING.md says to register within two days of the tag, and to delete and re-create an expired one.
- PyPI's pending publisher reserves nothing: if another account publishes `cupel-cli` first, the pending publisher is invalidated and the name is lost, as ADR-146's names always could be.
- `brew style` on a formula rendered for v0.2.9 in a scratch tap reported no offenses; `brew audit --strict` could not run on this machine (Homebrew 7.0.13 refused: Command Line Tools too old). Homebrew 7 also refuses to load formulae from an untrusted third-party tap (`brew trust`), which may add a step to `brew install tysont/cupel/cupel`; that is checked when the first formula is published.
- None of the three publishes has run: OIDC exchange, provenance, attestations, and the SSH push are verified only after the first tag with the gates open.
