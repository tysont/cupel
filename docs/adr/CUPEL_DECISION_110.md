# CUPEL_DECISION_110: Adding Java and Clojure as the test of the extension model: the files it touched, the defects it found, and the PIT plugin

**Date:** 2026-10-17 · **Status:** accepted · **Phase:** P6.4

## Context

Design §8.4.4 promises that a language is added with no change to `cupel-core`, `cupel-checks`, or the CLI: a grammar dependency, `langs/<id>/`, a fixture repository with its inventory, a toolchain-table row, and goldens. P6.4 adds Java and Clojure by that checklist as the proof that the promise holds, and the plan asks for the exact set of files touched outside `langs/`, `cupel-fixtures/`, `cupel-adapt`'s toolchain table, and the PIT plugin, with zero as the target; anything else is an extension-model defect, to be fixed or recorded. It also says Java's `MutationOutcomes` come from a PIT producer plugin, leaving its shape and home open, and ADR-088 left the plugin unable to displace a working native producer for any kind but `TestResults`.

## Options

**For each file outside the set**, three answers: fix the model so the next language does not touch it (derive the list from the registry, move the knowledge into the language), keep the touch as intended (a pin that is supposed to change when the registry changes), or record the defect with a proposed fix when the fix is a design change.

**Selecting PIT.** (a) Leave the native engine (`Langs::Any`) and the plugin both registered and let registration order decide: the engine always wins. (b) Remove Java from the engine's languages: a change to `cupel-mutate` that names a language, which the facts model forbids. (c) Grow `FactKind::pin_key`, as ADR-088's Consequences anticipated: `[lang.java] <key> = "plugin.pit"`.

**The plugin's language and home.** A Rust binary in a new crate (typed, linted, but a crate-graph change, and fixtures could not name the built binary portably), a single-file Java program run by `java` (no JSON library, a second of compile per `describe`), or a Python script using the standard library like the reference plugins (ADR-092), run as `python3 <file>`. Its home: under `cupel-fixtures/plugins/` (where the reference plugins live, but those are test material the dogfood skips), or a top-level `plugins/` directory for plugins Cupel ships.

## Decision

1. **Files touched outside the expected set** (the P6.5 ADR-104 format). The expected set: `Cargo.toml`/`Cargo.lock` and `crates/cupel-lang/Cargo.toml` (the two grammar dependencies), `crates/cupel-lang/src/langs/{java,clojure}/`, the registration lines in `langs/mod.rs`, `crates/cupel-fixtures/` (repositories, captures, goldens, tests), `crates/cupel-adapt/src/toolchain.toml` with the producers and parsers its rows name and their tests, `plugins/pit/`, `.github/workflows/ci.yml` (tool pins), `README.md`, and `docs/`.

   | File | Why it changed | Model status |
   |---|---|---|
   | `crates/cupel-lang/src/langs/ecosystems.rs` | The Maven/Gradle and `deps.edn` ecosystems moved into `langs/java/project.rs` and `langs/clojure/project.rs`; `KNOWN`, the list every project-root walk skips the generated directories of, names each language's ecosystem, so a language is registered in two lists | **Defect, recorded**: the second list is the registry's job. Proposed fix: `LanguageRegistry` collects each language's `Ecosystem` (a `Language::ecosystem()` or a registration-time argument) and hands the walk the list, so `KNOWN` disappears; it changes the closed `Language` trait or the `ProjectRoots` constructor, which is a design decision for the integrator. `UNREGISTERED` (ADR-038's recognized-but-unregistered ecosystems) is now empty and stays for the next language detected before it is registered |
   | `crates/cupel-lang/tests/spec.rs` | Its grammar paths and query directories were hand-written per language, so a new language's queries were neither compiled against its grammar nor checked for being embedded until the lists were edited | **Fixed**: both lists are derived, the paths from each language's extensions, the directories from `src/langs/` and the registry; the framework assertion checks every language names one |
   | `crates/cupel-lang/tests/project.rs` | `maven_gradle_and_deps_edn_roots_are_unregistered` pinned ADR-038's transition; the `ProjectInfo`-producer test listed the five languages | **Fixed / intended**: the producer list is derived from the registry; the transition test became the registered behavior (Maven and Gradle roots with members are `java`, `deps.edn` roots `clojure`, nothing unregistered) |
   | `crates/cupel-lang/tests/languages.rs` | Pins the registered languages, their families, and every claimed extension | **Intended**: the test is the registry's golden, and a new language is meant to change it |
   | `crates/cupel-core/src/fact.rs`, `crates/cupel-core/tests/baseline.rs` | `FactKind::pin_key` names `mutator` for `MutationOutcomes`, so `[lang.java] mutator = "plugin.pit"` selects PIT over the native engine | **Fixed** (the model growth ADR-088 deferred): one arm and its test; `mutation` was taken by the engine's settings table |
   | `crates/cupel-cli/tests/init.rs`, `crates/cupel-cli/tests/config.rs`, `crates/cupel-cli/tests/describe.rs` and their snapshots | Tests pinned the transitional `init.unsupported-root` behavior for Java and Clojure, an unknown-language check that used `java`, and lists of languages per fact | **Intended** for the transitional pins (ADR-038 said P6 would change them by registering); the per-language lists are recorded below |
   | `crates/cupel-adapt/src/runner.rs`, `crates/cupel-adapt/src/pytest.rs` | `runner::tests_or_files`, the `select` of runners taking test IDs and files alike, shared by pytest and the Clojure runner instead of a copy | **Tool-layer refactor**, within `cupel-adapt`; no model change |
   | `crates/cupel-adapt/tests/{runners,coverage_producers,toolchain,reports}.rs` | Tool-layer tests list the runners and coverage producers per language in table order | **Recorded**: these are the toolchain table's own pins, changed with its rows; deriving them from the table would only restate it |

   No check, no `cupel-checks` file, no CLI source file, and no other language's producer changed. The `cupel-cli` tests listed are tests, not code: every one changed because a list of languages or the transitional ADR-038 behavior is spelled out in it.
2. **The pin key.** `FactKind::MutationOutcomes.pin_key()` is `Some("mutator")`; with it, `ProducerRegistry::candidates` keeps only the named producer (`plugin.pit`, `engine.mutation`), as `runner` does for `TestResults` (ADR-076). Without a pin the native engine serves Java and Clojure.
3. **The PIT plugin** is `plugins/pit/cupel_produce_pit.py`, a Python 3 standard-library script configured as `[plugins] pit = ["python3", "plugins/pit/cupel_produce_pit.py"]` (a top-level `plugins/` holds plugins Cupel ships; the dogfood grades it). Manifest: producer `plugin.pit`, provides `mutation-outcomes` v2 for `java`, needs `symbols`, `norm-tree`, `mutation-sites`, cost `standard`. `run`: copy the project (without `.git`, `.cupel`, `target`, `build`, `.gradle`, `node_modules`) into the request's scratch directory, run `[lang.java] pit` there (default by build tool: Maven `test-compile org.pitest:pitest-maven:mutationCoverage -DoutputFormats=XML -DtimestampedReports=false -DfullMutationMatrix=true`, Gradle `gradle pitest`) within the run's budget, read `pit_report` (default `target/pit-reports/mutations.xml` or `build/reports/pitest/mutations.xml`), remove the copy, and emit one fact; `pit_report_ready = true` reads the report in the tree instead. Each PIT mutation is placed on a Cupel site: its file is the mutated class's package path and source file; its mutator maps to Cupel operators (boundary → relational; negate → equality, else relational, else negation; math → add/sub or mul/div by its description; increments and inverted negations → add/sub; void calls → statement deletion; the return mutators → return value; removed conditionals → negation), and the k-th PIT mutation of one mutator on a line takes the k-th matching site on that line. A placed mutant takes the site's hash, span, text, and symbol (and the symbol's `norm-tree` hash), with Cupel's replacement where PIT's is the one Cupel's tables name and PIT's description otherwise; an unplaced one sits on its line in the innermost symbol, its hash a digest of PIT's class, method, descriptor, mutator, and indexes, its text the line. Statuses map `KILLED`→killed, `SURVIVED`→survived, `NO_COVERAGE`→uncovered, `TIMED_OUT`→timeout, `MEMORY_ERROR`/`RUN_ERROR`/`NON_VIABLE`→unviable; tests are PIT's killing and succeeding tests as Maven runner IDs (`<class>#<method>`). `engine` and `runner` are `plugin.pit`, `per_test` is true (PIT runs the covering tests), nothing is reused, and no mutant is called equivalent.
4. **Go schemata** (ADR-005) stay deferred. ADR-005 measured the rebuild a schemata build saves for Go at under a tenth of a second per mutant and found that a type-safe rewrite needs a `go/types` helper; P6.4's purpose is to add languages without touching other axes, and `cupel-mutate` is outside its set. Revisit only with a Go module whose incremental builds are slow.

## Consequences

- The extension model held for every check and every other language: adding two languages changed no check, no other language, and no CLI code. Two real defects surfaced and one was fixed: hand-written per-language lists in the language tests (fixed) and the ecosystem list (recorded with its fix); the third change, the `mutator` pin key, is the growth ADR-088 planned.
- PIT's mutators and Cupel's operator tables are different vocabularies, so a PIT run reports what PIT mutates (bytecode-level returns of primitives, negated conditions) and the placement is a best effort by line; `tests.mutation` scores them like any mutant.
- The PIT plugin needs `python3` beside the JDK; the matrix test and the plugin tests report `SKIPPED` without it.
- A future language follows the same path; until the ecosystem fix lands it edits `ecosystems.rs` too.
- The ecosystem defect is fixed by [ADR-112](CUPEL_DECISION_112.md): `Language::ecosystem`, collected by the registry; `KNOWN` is gone.
