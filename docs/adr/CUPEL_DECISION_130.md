# CUPEL_DECISION_130: Gate rules against `base`, the metric's value in the reference run

**Date:** 2026-10-19 · **Status:** accepted · **Phase:** P9.1

## Context

A gate rule (design §6.7, ADR-017, ADR-060) compares a metric with a literal (`"static.clones.pairs" = "<= 169"`) or states presence (`none`, `no-breaking`). A ratchet written as a literal must be edited by hand every time the number improves, and between edits it admits any regression down to the old number: Cupel's own `[gate.tree]` holds `static.clones.pairs <= 169` while the tree has 166. The owner's P9 ruling asks for rules relative to the reference the run compares against: `"<= base"`, `">= base - 0.02"`, and the other comparisons, where `base` is the metric's value at the baseline (ADR-046) or, for `--changed`/`--base`, at the range's base, stored or recomputed; a rule with no reference value is skipped with a reason, never a pass.

ADR-046 already resolves a reference run for deltas: `--against baseline|REF|run:ID`, or the `default` baseline when set, and "nothing is ever re-run". What it leaves open for a gate:

1. The grammar: which offsets, whether `%` applies, how errors read.
2. Which run `base` names for each scope, and what "recomputed" means for a range when no stored run fits.
3. What a rule's result records: the value compared with, and why a rule was not evaluated.
4. What `next_actions` says about a rule with no reference.

## Options

**Grammar: `base` with an optional signed offset, a relative factor (`base * 0.98`), or a percentage (`base - 2%`).** An offset in the metric's own unit covers both ratchets (`<= base`) and tolerances (`>= base - 0.02`). A factor reads oddly for counts and adds an operator. `%` already means "divided by 100" for literals (`< 5%` is 0.05), so `base - 2%` would be read by some as 0.02 and by others as 2 % of the base; refusing it with the rewritten offset (`write base - 0.02`) removes the ambiguity. The offset is written unsigned after `+`/`-`; `base - -1` is refused so each rule has one spelling.

**Representation: extend `Threshold` with a `base` flag, or a new `GateCondition::Relative { op, offset }`.** A flag would make every literal comparison carry a meaningless offset and every reader branch on it. A variant keeps literal rules unchanged and lets the evaluator and the config's `needs_reference` test match on it.

**The reference for a tree scope: the default baseline, `--against`, or the previous commit.** The baseline is what ADR-046 already compares a tree run with, and `--against` overrides it; the previous commit would need a stored run there, which a fresh CI checkout does not have either. So a tree rule uses `--against` when given, else the `default` baseline, else it has no reference.

**The reference for a range: the default baseline, a stored run at the base commit, or the base recomputed.** The baseline is usually a whole-tree run from some other time, so comparing a change's metric with it compares different scopes. A stored run at the base commit (ADR-046's ref resolution) is whatever was last run there, at any scope: a tree run's `tests.mutation.score` is not the same measurement as one change's. The base recomputed over the same files is the like-for-like value: the checks the `base` rules name, run with the current configuration over the base versions of the range's changed files. It costs one more run of those checks (for `tests.mutation`, the base's suite and mutants), and only when a `[gate.changed]` rule names `base`. `--against` still names a stored run explicitly, for when the caller wants one.

**Where the base copy lives: the run's scratch area under `.cupel/work/`, a `git worktree`, or a temporary directory.** A copy under `.cupel/` sits inside the repository, so the walk applies the repository's ignore files to it and `.cupel/` hides every file (found by the first test). `git worktree add` registers the copy in the repository's `.git` and must be removed even after a crash. `git read-tree` and `git checkout-index --prefix` through a private `GIT_INDEX_FILE` write a commit's files anywhere without touching the index, the work tree, or `.git`; a temporary directory outside the repository, removed when the run ends, keeps the walk clean.

**Result fields: reuse `actual` and the rule text, or add `bound` and `reason`.** `<= base` does not say what it was compared with, so the resolved bound must be recorded for an agent to know how far it is from passing. A skipped rule today carries nothing but `skipped`, which conflates "the check did not run", "the metric was not reported", and "no reference"; a reason string distinguishes them for agents and people alike.

## Decision

1. **Grammar.** After any comparison operator, the operand is a number (optionally `%`) or `base`, optionally followed by `+ <number>` or `- <number>` with a non-negative, finite number in the metric's unit; whitespace is optional throughout (`>=base-0.5`). `base` is a word: `baseline` is an operand error. Errors name the fix: `` `base` takes an offset written `base + <number>` or `base - <number>` ``, `` an offset from `base` is a number in the metric's unit, not a percentage: write `base - 0.02` `` (the percentage divided by 100), `` `base -` expects a non-negative number, such as `base - 0.02` ``, and for any other operand `` `>=` expects a number (optionally with a `%` suffix) or `base` (optionally `base + <number>` or `base - <number>`) ``. A `base` rule needs a metric, like any comparison. `GateCondition::Relative { op, offset }` displays as `<= base`, `>= base - 0.02`, `> base + 1` (a zero offset is not written), and parses back to itself. The config schema's rule pattern and description include the form, so `describe schema config` documents it.
2. **Reference.** `cupel-cli/src/reference.rs` resolves `base` only when the evaluated gate table has a `Relative` rule (`cupel_core::needs_reference`): `--against`, when given, is the reference (ADR-046 §5's resolution, reused: `against::compare` now returns the run it compared with); otherwise a range scope (`--changed`, `--base`) recomputes its base; otherwise the `default` baseline, when set. With none: `no baseline is set`.
3. **Recomputing a range's base.** The scope is resolved again; the changed files that existed at the base and that a language owns (ADR-056's base files) are the base run's `--paths`; the checks the `base` rules name are its `--only`; `--jobs` carries over; nothing is installed. `Git::export` writes the base commit into a temporary directory outside the repository (`cupel-base-*`, removed after the run), and `check::run` runs there with the current configuration, the same run ID, session caches, and plugins, and no events. A range whose changed files are all new has no reference (`none of the range's files existed at its base`); a base run that fails (a red base suite is exit 4 there) gives `the run at the base <sha12> failed: <why>`. The base run's envelope is not stored.
4. **Evaluation.** `evaluate_gate(evaluated, rules, envelope, reference: &GateReference)`, where `GateReference` is `Run(&Envelope)` or `Missing(why)`. A `Relative` rule whose check completed and reported the metric compares it with the reference run's value of the same metric (from a completed entry of the same check) plus the offset. Without that value the rule is `skipped` with `actual` still set and reason `no reference: <why>`, which fails the gate (ADR-060 §6: only `pass` passes); a reference run that lacks the metric gives `no reference: the reference run did not report `<key>``. An empty scope still passes every rule vacuously.
5. **Result.** `summary.gate.rules[]` gains `bound` (the value `actual` was compared with: the threshold with `%` applied, the reference value plus the offset, or 0 for `none`/`no-breaking`; null when the rule was not evaluated) and `reason` (why a `skipped` rule was not evaluated: `` `<check>` did not run to completion ``, `` `<check>` did not report `<metric>` ``, or `no reference: …`; null otherwise). The text renderer prints the reason, and the bound for a rule against `base`.
6. **Actions.** A rule skipped for no reference ranks in the gate band as a `configure` action: "Give the gate rule `<rule>` a reference (<reason>): set a baseline with `cupel baseline set --write`, or pass --against REF|run:ID.", command `cupel baseline set --write`. Other skipped rules keep their `rerun` action.
7. **ADR-046 §5** ("Nothing is ever re-run") still holds for deltas, `baseline diff`, and `explain`; it is narrowed for gate rules against `base` on a range, which re-run their checks at the base.

## Consequences

- A ratchet is written once (`"static.clones.pairs" = "<= base"`) and tightens whenever the baseline is reset after an improvement; a tolerance (`">= base - 0.02"`) admits noise without a hand-edited floor.
- On a range, the base value is of the same files, not of the same lines: the current side of a range scores what the range touched (for `tests.mutation`, the mutants on changed lines), the base side scores the base versions of those files whole. A change to an untested function in a well-tested file fails `tests.mutation.score >= base - 0.02` (the tested fixture: 0.0 against 0.73); a change confined to well-tested lines passes easily. Comparing changed lines with their base counterparts needs the base side of each hunk; it is not done.
- A `[gate.changed]` rule against `base` costs a second run of its checks on every `--changed` check that changes a file the base had. The copy keeps no store and no build directory, so every base run is cold: for `tests.mutation` that is a second suite and mutant run from scratch, which can dominate a deep run. `--against` with a stored run avoids it; keeping the base run's results in the repository's store, keyed by base commit and files, would make a repeated base free and is not done.
- A tree rule against `base` needs a baseline in the store. A fresh CI checkout has none, so the rule is skipped and the gate fails until the job restores a store or imports a committed baseline (`cupel baseline import FILE --write`). Cupel's own clone ratchets therefore stay literals until CI keeps a baseline (P9 Notes).
- `bound` and `reason` are additive fields of the run schema; stored runs without them read back as null.
- A metric whose value is legitimately absent at the base (a check that skips there) cannot be ratcheted on a range; the rule says so instead of passing.
