# CUPEL_DECISION_128: Publish jobs that skip without their secrets, and install routes with their liveness in one place

**Date:** 2026-10-19 · **Status:** accepted; the npm and pipx package names of §4 and the `publish-crates` steps of §2 amended by [146](CUPEL_DECISION_146.md) · **Phase:** P8.5

## Context

ADR-124's release workflow builds the archives and publishes the GitHub Release on a `v*` tag; ADR-125 wrote the installers (`dist/install.sh`, the Homebrew formula template and `render.sh`, the npm and pipx wrappers, binstall metadata) and left publishing them open. The owner's ruling: GitHub Releases only for now; npm, PyPI, Homebrew, and crates.io publishing stay disabled until their secrets exist, each publish job must skip cleanly (not fail) without its secret, and `doctor`'s install-route descriptions must say which routes are live. The tap repository `tysont/homebrew-cupel` exists and is empty. The first tag, `v0.1.0`, is cut right after this step merges; from then the release archive, `install.sh` from its raw GitHub URL, `cargo binstall --git`, and a source build work, and Homebrew, npm, pipx, crates.io, and `cupel.dev/install` do not until something is published or served.

Three places said which routes work, by hand: the README's route table (an "Available" column), `doctor.version-unsatisfied`'s fix ("Install a cupel matching `<req>`, or change required_version.", which names no route), and the plan's notes. The fix is what an agent reads when its binary is too old, so it is where a route has to be named. The questions:

1. How a publish job skips without its secret, given that a job-level `if` cannot read the `secrets` context.
2. How each registry is published, and in what order the workspace's crates go to crates.io.
3. Where the list of install routes lives, how it is exposed, and how the README and `doctor` follow it.

## Options

**Skipping: `if: env.TOKEN != ''` on every step, a first step whose output gates the rest, or a probe job.** Step-level conditions keep each job self-contained but leave the job green with every step skipped, so a skipped publish and a successful one look the same in `gh run view`, and every step added later must remember the condition. A first step writing an output has the same appearance. A `secrets` job that reads all four secrets through `env` and writes one boolean output per registry lets each publish job carry a single job-level `if: needs.secrets.outputs.<registry> == 'true'`; an unset secret shows the job as skipped, and the probe writes `skipped: secret X not set` as a notice and to the step summary. The probe job sees all four secrets, but only tests whether each is empty.

**Which events publish.** On `workflow_dispatch` (ADR-124's dry run) nothing may be published; the probe job runs only on a tag push, after `release`, and every publish job needs it, so on a dry run all five are skipped and on a tag none starts before the GitHub Release exists (the wrappers and the formula download from it).

**npm: `actions/setup-node` with `registry-url`, or the runner's npm with an auth token set by `npm config`.** `ubuntu-latest` carries Node and npm; `npm config set //registry.npmjs.org/:_authToken` does what `setup-node` writes to `.npmrc`, without a new action to pin. `npm publish dist/npm` reads `dist/npm` as the GitHub repository of that name (found by `npm publish --dry-run` here), so the path is `./dist/npm`.

**PyPI: trusted publishing or an API token.** Trusted publishing needs the project configured on PyPI first and `id-token: write`; the owner named a secret, `PYPI_API_TOKEN`. The runner's Python is externally managed (PEP 668), so `build` 1.6.1 and `twine` 7.0.0 go into a venv in `$RUNNER_TEMP`.

**Homebrew: the release artifact or the published `SHA256SUMS`.** The `release` job's artifact holds the same file, but the formula must match what users download, so the job fetches `SHA256SUMS` from the published release with `gh release download`, renders `Formula/cupel.rb` with `render.sh` (which strips the tag's `v`), and commits it to the tap's `main`, cloning with the token. The tap is empty, so the first push creates `main`; a rerun with an identical formula commits nothing and the push is a no-op.

**crates.io order: by hand, a script, or `cargo publish --workspace`.** `cupel-cli` depends on seven workspace crates, which depend on each other. Cargo 1.90 stabilized `cargo publish --workspace`, which publishes in dependency order, waits for each crate to appear in the index before its dependents, and leaves out `publish = false` crates (`cupel-fixtures`); the pinned toolchain is 1.92. A hand-written order would drift as crates are added. `cargo publish --workspace --dry-run --no-verify` here ordered them `cupel-core`, `cupel-adapt`, `cupel-checks`, `cupel-lang`, `cupel-plugin`, `cupel-serve`, `cupel-store`, `cupel-mutate`, `cupel-cli`.

**Routes: `dist/routes.toml` read with `include_str!`, or a module in `cupel-cli`.** A TOML file beside `targets.toml` would be readable by the shell and wrapper installers, but none of them needs the list, and parsing it in the binary adds a failure path for data that never changes at run time. A Rust table is checked by the compiler, and the binary is the one consumer the README and `doctor` both read from.

**Exposing routes: a new `describe` subject, or a field on the CLI description.** A subject (`describe install`) adds a `Description` variant, a text renderer, an MCP enum value, and a usage error listing. A field on `CliDescription`, which already gathers what is true of the binary as a whole (verbs, exit codes, schemas, configuration precedence), reaches `describe` and `describe --all` with one type and one text section.

**Liveness: a boolean, a reason, or both.** A boolean alone loses why a route is not live; a reason alone makes an agent test for null. Both, with the reason null exactly when the route is live, are derived from one `Option` in the table so they cannot disagree.

## Decision

1. **`secrets` job** in `release.yml`: `needs: release`, `if: github.event_name == 'push' && github.ref_type == 'tag'`, `env` maps `NPM_TOKEN`, `PYPI_API_TOKEN`, `HOMEBREW_TAP_TOKEN`, and `CARGO_REGISTRY_TOKEN` from `secrets`, and a `probe <output> <secret>` shell function writes `npm`, `pypi`, `homebrew`, and `crates` outputs (`true` or `false`), with `::notice title=publish-<output>::skipped: secret <SECRET> not set` and a step-summary line for each unset one.
2. **Four publish jobs**, each `needs: secrets` and `if: needs.secrets.outputs.<output> == 'true'`, each reading only its own secret, all pinned to the `actions/checkout` commit ADR-124 already uses (no new actions): `publish-npm` (`npm config set` then `npm publish ./dist/npm --access public`), `publish-pypi` (venv; `python -m build dist/pipx`; `twine upload` with `__token__`), `publish-homebrew` (`gh release download <tag> --pattern SHA256SUMS`; clone `tysont/homebrew-cupel` with the token; `render.sh <tag> SHA256SUMS > Formula/cupel.rb`; commit as `github-actions[bot]` when changed; `git push origin HEAD:main`), `publish-crates` (pinned toolchain; `cargo publish --workspace --locked`).
3. **Tests** in `crates/cupel-cli/tests/release.rs` read the workflow's jobs by indentation: the `secrets` job runs on a tag after `release`, maps and probes each secret, and writes the skip notice; each publish job needs `secrets` and is gated on its output and reads its secret; no other job reads any secret. The pin test is unchanged (no new action). `actionlint` 1.7.12, with ShellCheck, reports nothing.
4. **`crates/cupel-cli/src/routes.rs`** holds the routes, live first: Install script (`curl -fsSL https://raw.githubusercontent.com/tysont/cupel/main/dist/install.sh | sh`), cargo-binstall (`cargo binstall --git https://github.com/tysont/cupel cupel-cli`), Release archive (`gh release download --repo tysont/cupel --pattern SHA256SUMS --pattern 'cupel-*-<target>.tar.gz'`), From source (`cargo install --locked --git https://github.com/tysont/cupel cupel-cli`); then, each with what it waits for, Homebrew (`brew install tysont/cupel/cupel`), npm (`npx cupel`), pipx (`pipx install cupel`), crates.io (`cargo install --locked cupel-cli`), and cupel.dev (`curl -fsSL https://cupel.dev/install | sh`). Every route serves `linux` and `macos` (Windows has no working build, ADR-124).
5. **`describe`**: `CliDescription.install_routes`, a list of `InstallRoute { name, command, platforms, live, pending, stability }` in `cupel-core`; the text rendering ends with an `install routes` section (name, command, platforms, and the reason when pending).
6. **`doctor.version-unsatisfied`'s fix**, which is also the `install_tool` action's summary and the refusal every grading verb returns (ADR-126): "Install a cupel matching `<req>`, or change required_version. Live install routes: `<command>`; …", naming every live route's command and no other.
7. **README**: the Install section's hand-written table becomes the generated section `install-routes` (Route, Command, Platforms, Available: `now` or the reason), rendered by `readme.rs` from `describe` like the other eight; "From a release archive" and "From source" are unchanged.

## Consequences

- The README, `describe`, and the finding cannot disagree about what is live: all three come from `routes.rs`, and the README staleness test fails when the table changes without `make readme`.
- Flipping a route live is a code change and a release: once its registry has the package (or the domain serves the script), `pending` becomes `None` in `routes.rs`, the README is regenerated, and binaries from the next tag name it. Binaries already released keep saying it is not live, which errs toward routes that work. Between this step's merge and the `v0.1.0` tag the four live routes are described as live a little early.
- Publishing turns on by adding a repository secret; nothing in the workflow changes. A set secret whose job fails (a taken name, a bad token) fails the run, as it should; an unset one never does.
- After the `v0.1.0` tag, `gh run view <run>` should show `secrets` green with four `skipped: secret … not set` notices and `publish-npm`, `publish-pypi`, `publish-homebrew`, and `publish-crates` skipped, and the run successful.
- Publishing is not live-tested here: the jobs have never run. Verified locally: `npm publish ./dist/npm --dry-run` packs `cupel@0.1.0`; `python -m build dist/pipx` with build 1.6.1 builds the sdist and wheel and `twine check` passes them; `cargo publish --workspace --dry-run --no-verify` orders the crates as above.
- Two names block their registries. On PyPI, `cupel` is another project's (version 0.1.88, `tolitius/cupel`), so `publish-pypi` would be refused and `pipx install cupel` installs that project today; on crates.io, `cupel-core` is another project's (and `cupel` a third's), so `cargo publish --workspace` fails at its first crate, and `cargo package --workspace` here resolved `cupel-core 0.1.0` from crates.io and failed to verify `cupel-adapt` against it. Publishing to either needs a rename decided by the owner. crates.io also needs a `version` on each `[workspace.dependencies]` path entry (`cargo publish` refuses path-only dependencies), which is left out until the names are settled, since a version requirement there must be bumped with every release. npm's `cupel` is free.
- `cupel.dev` remains unserved; its route flips when the domain serves `dist/install.sh`.
