# CUPEL_DECISION_085: The daemon: one crate generic over a handler, what it holds, when the CLI uses it, and its lifetime

**Date:** 2026-10-15 · **Status:** accepted · **Phase:** P4.2

## Context

Design §6.5 and §8.10 specify `cupel serve [--socket PATH] [--mcp] [--watch]`: a long-lived process holding parsed trees (keyed by content hash), the fact-store connection, the coverage map, and the last plan; a `notify` watcher that reparses changed files; CLI invocations that auto-connect over `.cupel/serve.sock` unless `CUPEL_NO_DAEMON=1`; and output byte-identical to a cold run (§9.5). ADR-009 fixes the wire format. Everything else is open: where the code lives in the crate graph (plan §2.1 lists `cupel-serve` but not its edges, and a graph change needs an ADR), how a daemon runs a request so that its output cannot drift from a cold run's, which of the listed caches are worth holding, when a client uses the daemon and what it does when it cannot, how a daemon and a client of different builds or environments meet, how concurrent clients and `--events` behave, how a run is cancelled, and how the daemon starts and ends.

## Options

**Running a request.** (a) Reimplement the verbs' dispatch in the daemon: two code paths that must be kept identical by tests alone. (b) The daemon calls the very function a cold process calls: `cupel_cli::run(&Environment) -> Output` already takes everything an invocation reads from its process as data (ADR-076 §8), so the daemon rebuilds the client's `Environment` and calls it; parity then rests on that function reading nothing else from the process.

**Where the daemon lives.** (a) In `cupel-cli`: the server, protocol, and watcher would sit beside the verbs. (b) A `cupel-serve` crate that `cupel-cli` depends on, holding the transport (protocol, server loop, client, watcher) generic over a `Handler` the CLI implements with its `run`; it needs only `cupel-core` (for `Cancellation`). (c) `cupel-serve` depending on `cupel-cli` to call `run`: a cycle, since the binary is `cupel-cli`'s.

**What to hold.** Parsed trees: parsing is most of a static run's cost (below). The store connection: `Store::open` is a SQLite open plus a schema-version read, under a millisecond to a few, and five call sites in two crates open their own. The coverage and per-test maps: their producers (`cupel-adapt`, owned by P4.4's work) re-read cached reports and decide freshness by hashing every file under the root on every run; holding a decoded map would still need that freshness check, which is the cost. The last plan: nothing reads it yet; P4.3's budget scheduler would be its consumer.

**Concurrency.** (a) One request at a time: simple, but one long `--depth deep` run blocks every other client, which cold processes never do. (b) Each connection on its own thread, runs concurrent as separate processes are; the store's writer lock already orders concurrent writers (ADR-045).

## Decision

1. **Crate graph.** A new crate `cupel-serve` → `cupel-core` (plus `serde`, `serde_json`, `notify`, `nix`). `cupel-cli` → `cupel-serve`. `cupel-fixtures` → `cupel-serve` (the parity harness speaks the protocol, §11). `cupel-serve` names no language, check, or producer; `serve --mcp` (P7.7) will add its transport there.
2. **The daemon runs the cold code.** `cupel-cli`'s handler turns a request's invocation into an `Environment` and calls the same `run` a cold process calls. `Environment` gains three members a cold process fills from itself: `stderr` (where `--events stderr` and `serve`'s own notices go as they are written), `session` (what outlives one invocation), and `cancel` (a token the run's own cancellation sits under), plus `path` (the process's `PATH`, which only the client reads).
3. **What it holds.** The `Session` holds the parse cache: trees by content hash and grammar, shared by every request (`LanguageRegistry::with_cache`). Every request still reads and hashes every file it parses, so a tree is used only for identical content and the watcher is never needed for correctness. After each request the cache sweeps trees no existing file last parsed to (base-tree copies of a range run, old contents). The store connection, the coverage and per-test maps, and the last plan are not held, for the reasons and measurements above and in the P4 Notes; holding the maps needs a producer-side hook in `cupel-adapt` (an open item).
4. **When the client uses the daemon.** Before running, `cupel` resolves the repository root as the run would (`--cwd`, read from the raw arguments, against the working directory) and connects to `<root>/.cupel/serve.sock` if that file exists. It runs locally, without a word, when `CUPEL_NO_DAEMON=1`, when the verb is `serve`, when an argument is not UTF-8, when the run could ask a question on the terminal (stdout is a terminal and neither `--install` nor `--no-install` is given, ADR-081: a daemon has no terminal), when `--jobs` is given (a process sizes its thread pool once, ADR-086 §11), when there is no socket file, or when nothing answers on it (a stale socket). Builds: every request carries the client's version and a fingerprint of its executable (size and modification time), so a rebuilt `cupel` of the same version is another build; a daemon refuses a `run` from another build or protocol. A refusal, a malformed reply, or a connection that ends before the final reply makes the client run locally and add one line to stderr (unless `--quiet`): `cupel: ran without the daemon: <reason>`. Lines the daemon already streamed are not taken back.
5. **Environment.** The daemon runs tools with its own process environment. The invocation carries the working directory, the arguments, whether stdout is a terminal, the `CUPEL_*` variables, and `NO_COLOR`; a `run` whose client has another `PATH` is refused (§4), since `PATH` decides which tools run. Other variables (`HOME`, `CARGO_HOME`, `VIRTUAL_ENV`) are the daemon's; start the daemon from the environment the agent runs in.
6. **Streams.** `--events stderr` lines reach the client as `stderr` replies in the order they are written, each complete line as soon as it is written; the final reply carries the rest of stderr, which a cold process writes at the end too. `--events PATH` is written by the daemon process, under the same `Writer` rules.
7. **Cancellation.** A client that hangs up before its final reply cancels its run (as killing a cold process stops it); the run finishes as `partial` and still writes its run record, which a killed process would not. `--timeout` works as in a cold run, counted from when the daemon starts the request.
8. **Concurrency.** Each connection is answered on its own thread, and runs proceed concurrently, as separate processes would. `status` and `stop` are answered even while runs are in flight.
9. **Lifetime.** `cupel serve` runs in the foreground and prints one line to stderr when it accepts connections (unless `--quiet`). It ends on `cupel serve --stop` (a `stop` request; `--stop` is a new switch), on `--timeout`, on SIGINT or SIGTERM (which leave the socket file behind, a stale socket clients ignore), or when its socket file is removed or replaced (checked every 200 ms), and has no idle exit. Runs in flight when it stops are cancelled and answered (`partial`, exit 5) before it exits. Its envelope then reports `serve.stopped` (info) with the number of requests served; `serve --stop` reports `serve.stopped` or, with nothing answering, `serve.not-running` (info), both exit 0. Starting where a daemon already answers is exit 3 with `serve.running` (fail); a stale socket file is replaced. The socket is created with mode `0600`.
10. **Flags.** `--watch` runs the watcher: each burst of changes under the root hands its paths to the session, which reparses every file it has parsed before from that file's previous tree (one tree-sitter edit spanning what differs, then an incremental parse) and caches the new tree, so the next request finds it; files never parsed are left to the next request. `--socket PATH` listens at `PATH` instead of `.cupel/serve.sock`; clients look only at `.cupel/serve.sock`, so a daemon elsewhere serves tools that speak ADR-009 themselves (the parity harness, §11). `--mcp` stays pending (P7.7).
11. **`doctor`** reports the daemon at `.cupel/serve.sock`: `doctor.daemon-running` (info, with its version, process ID, and whether it watches), `doctor.daemon-mismatch` (warn, another build, with the restart command), or `doctor.daemon-stale` (warn, a socket file nothing answers on); without a socket file it reports nothing. **Parity proof:** with `DAEMON_PARITY=1`, the golden harness (`cupel_fixtures::run_cupel`) runs every invocation twice: cold in its directory, and through a fresh `cupel serve --socket` (outside the copy, so the run sees no daemon of its own) on an identical copy, after first serving the same command as a `--dry-run` so the second request meets warm trees; exit code, redacted stdout, and stderr must be identical. `make parity` runs the fixture suite this way; CI runs it.

## Consequences

- Parity is structural: there is one `run`, and anything it reads from the process that the invocation does not carry (today: tool lookups through the daemon's environment, §5) is the whole surface for drift. A future verb that reads process state directly must route it through `Environment`.
- A warm `check --depth quick` saves the parse; what is left is walking, hashing, the checks themselves, and git (P4 Notes, "P4.2 — measurement").
- Rebuilding `cupel` makes every client fall back, with a one-line note, until the daemon is restarted; a stale daemon can never answer for a newer binary.
- Tool-backed facts (coverage, per-test maps) cost the same through the daemon as cold until their producers can keep a decoded map with its freshness record.
- The test harness and anyone else can drive a daemon over the socket without the CLI client; MCP (P7.7) will be one more transport over the same handler.
