# CUPEL_DECISION_156: Agent checkouts: per-checkout builds, half the cores, the heavy lock around the check's build

**Date:** 2026-10-30 · **Status:** accepted · **Phase:** B.2

## Context

P10 Notes "P10 — machine load": three agents and the integrator's chains at once drove the load average past 300 on the eight-core machine and filled the volume twice. `scripts/heavy.sh` serialized only dogfoods and measurements; `make check`, golden regenerations, and builds used every core outside it, and each agent worktree held its own 15 to 30 GB build. The owner's ruling: agent builds across worktrees share one `CARGO_TARGET_DIR` per machine, so cargo's lock serializes them and disk is held once; `-j` capped at cores/2 for agent-driven builds; `make check` takes the heavy lock only around its build step; removing a worktree cleans any per-worktree target directory. The integrator added: CI and a single human checkout keep working unchanged; the integrator needs a command to create and remove worktrees in place of `git worktree add`/`remove --force`; a `make check` inside a `make dogfood` that holds the lock must not deadlock.

What was measured before deciding (cargo 1.92.0, the pinned toolchain):

1. **cargo's lock covers the build, not the run.** A `cargo build` in the same target directory proceeds at once while `cargo test`'s test binaries are running (a probe crate whose test sleeps 8 s: the build waited 0 s).
2. **Artifact names do not depend on the checkout's path.** Two copies of a crate at different paths built into one target directory produce the same `deps/<name>-<hash>` files; `CARGO_BIN_EXE_<bin>` (and `assert_cmd::cargo_bin`, which Cupel's tests use) is the uplifted `<target>/debug/<bin>`, one path for every checkout. Cargo hashes a path package by its path relative to the workspace root, and its fingerprint records that relative path and the source files' modification times.
3. **So a checkout can be judged fresh with another checkout's code.** Probe: `q1` and `q2`, the same crate printing `from q1` and `from q2`, `q2` edited before `q1` was built, one `CARGO_TARGET_DIR`: built and run alternately `q1, q2, q1, q2`, every run printed `from q1`; `q2` never compiled. Cargo's freshness compares the recorded sources' modification times with the artifact's, and `q2`'s sources were older than `q1`'s build.
4. **The same on Cupel itself** (the real two-worktree run, 2026-10-30 18:22, `~/.cache/cupel/target` as the one `CARGO_TARGET_DIR`, `CARGO_BUILD_JOBS=4`): this worktree and a second at e73408b whose `cli.rs` said `version = "shared-probe"`, both `cargo build -p cupel-cli` started 2 s apart. The second printed `Blocking waiting for file lock on build directory` at 18:22:13 and waited until the first finished at 18:23:02 (51.5 s, 114 units); it compiled **nothing** and finished with it. The shared directory held 1.7 GB, once. Then each built again, alternately, twice: every build `Finished` in under a second, and the second worktree's `cupel --version` printed `cupel 0.2.1`, the first worktree's code, every time, never `cupel shared-probe`.

The ruling's mechanism works as the owner described (cargo's lock serialized the two builds; the disk was held once) and builds the wrong program. A branch whose edits are older than another branch's last build runs that branch's code in its tests, with no error. Separately, (1) and (2) mean that even a correct rebuild by one worktree replaces the test binaries and the `cupel` binary another worktree's `cargo test` is in the middle of running.

## Options

**One target directory for every agent checkout** (the ruling): rejected on the measurements above; stale builds are silent, and a gate that passes on another branch's code is worse than a slow machine. Variants considered: (a) taking the heavy lock across build and test does not help; the stale build in (3) and (4) is sequential, with no concurrency; (b) forcing a rebuild when the last builder was another checkout (`cargo clean -p` of every workspace member, or touching every source, before each build) needs a hook before every cargo invocation, which a by-hand `cargo` never runs; (c) cargo's content-hash freshness (`-Zchecksum-freshness`) is nightly only, and still leaves the test-run overwrite of (1); (d) `build.build-dir` (stable since 1.91) shared with a per-checkout `target-dir` keeps the same fingerprints and test binaries in the shared part, and `assert_cmd::cargo_bin` then looks for `cupel` in the build directory, where it is not.

**How the shared directory would reach cargo, had it been sound** (recorded because it constrains any successor): not as `CARGO_TARGET_DIR` in `make dev-env`'s environment. That variable reaches every process the tests start: Cupel's tests run `cupel` on fixture projects in temporary directories, `cupel` runs cargo and nextest there, and those builds would land in the shared directory while Cupel reads `<root>/target/nextest/cupel/junit.xml` (`cargo_nextest.rs`) and the tests assert on `<fixture>/target/debug`. Not as a `.cargo/config.toml` inside the checkout either: the mutation engine mirrors ignored entries into its slots as symlinks (ADR-080 §8), so every slot would build into it. Only a cargo config at an ancestor of the worktrees (`.claude/worktrees/.cargo/config.toml`) reaches the in-tree cargo invocations and nothing else.

**Which checkouts are agents' (the opt-in).** (a) An environment variable the agent sets: each agent would have to remember it, which is the step ADR-139 found forgotten. (b) A marker file the worktree command writes. (c) **A linked git worktree** (`git rev-parse --absolute-git-dir` differs from `--git-common-dir`): every agent works in one, created by the harness or the integrator; the integrator's main checkout, a human's single clone, CI's checkout, and `make inner-loop`'s fresh clones are not. No setup, nothing to forget, and nothing in CI changes.

**The cap.** `CARGO_BUILD_JOBS` (cargo), `NEXTEST_TEST_THREADS` (nextest), and `RUST_TEST_THREADS` (libtest, since `make test` is `cargo test`) are read from the environment by every build and test run, including those Cupel's tests and Cupel itself start, which is where a check of Cupel fans out (P10 Notes). An explicit `--build-jobs` or `--test-threads` Cupel passes still wins. A cargo config `[build] jobs` would cap only in-tree cargo.

**The check's build step under the lock.** `make check` compiles in three places: clippy (`lint`), the test binaries (`test`), and rustdoc (`doc`). Locking each separately interleaves another checkout's dogfood between them; one locked step that compiles all three (`make check-build`: clippy with `-D warnings`, `cargo test --workspace --no-run`, rustdoc with `-D warnings`), after which `lint`, `test`, and `doc` run outside the lock and find everything fresh, takes the lock once. With per-checkout target directories the tests running outside the lock read only their own checkout's binaries, so the ruling's "only around its build step" is safe.

**Re-entry.** `heavy.sh` called under a command that already holds the lock (`heavy.sh make check` in a chain, or a check inside a dogfood) would wait forever on its own holder: `flock` on a second open of the file conflicts with the first. The holder exports the lock's path; a nested call naming the same lock runs its command at once.

## Decision

1. **Each checkout builds into its own `target/`**, as today; there is no shared target directory. The owner's "one `CARGO_TARGET_DIR` per machine" is not adopted, on the measurements in Context (3) and (4); disk is bounded instead by removing worktrees with §5 and by `make reclaim`. The ruling's other parts are adopted as below.
2. **An agent checkout is a linked git worktree.** `scripts/dev-env.sh` gains `cupel_dev_agent` (true in a linked worktree) and `cupel_dev_cap`, which prints `CARGO_BUILD_JOBS`, `NEXTEST_TEST_THREADS`, and `RUST_TEST_THREADS`, each half the online cores (`getconf _NPROCESSORS_ONLN`, at least 1), in an agent checkout and nothing elsewhere; `cupel_dev_env` prints them whether or not the tools directory exists. So every `make` target in an agent worktree runs capped, `eval "$(make -s dev-env)"` gives a by-hand shell the same cap, and the integrator's checkout, a human's clone, and CI keep every core.
3. **`make check` in an agent checkout runs `scripts/heavy.sh $(MAKE) check-build` first**, at the caller's priority (a merge chain's `CUPEL_HEAVY_PRIORITY=first` passes through), then `lint test doc` outside the lock as before, then `clean-check`. Elsewhere `make check` is unchanged. `make check-build` is the target that compiles everything `make check` runs. A dogfood waiting behind a check's build step takes the lock in the same turnstile order as behind any heavy command; a prioritized chain still goes first. `heavy.sh` and its 40 GB floor now also guard an agent's check.
4. **`scripts/heavy.sh` is re-entrant per lock.** It exports `CUPEL_HEAVY_HELD=<lock path>` to the command it runs; a call whose lock is the one named there runs its command at once, without the floor check, the turnstile, or the wait. A call naming another lock waits as before.
5. **`scripts/worktree.sh` creates and removes agent worktrees** (also `make worktree NAME=<name> [BASE=<ref>]` and `make worktree-remove NAME=<name>`). `add` runs `git worktree add` at `<main checkout>/.claude/worktrees/<name>` on branch `<name>`, created from `BASE` (default `main`) unless it exists. `remove` deletes the slots the mutation engine keeps for that worktree under `$TMPDIR/cupel-mutate` (each slot directory names its repository in its `repository` file, ADR-141 §3; slot 0 holds a whole build of the workspace, 15 GB after a dogfood), then `git worktree remove --force`, which deletes the worktree with its ignored files: its `target/`, the coverage build under it, and `.cupel/`. The branch stays. `remove` refuses to run from inside the worktree it removes.
6. **The coverage build and the mutation slots stay per checkout.** `target/cupel-llvm-cov` is under the checkout's `target/` (ADR-084 §4, ADR-155 §2) and goes with the worktree; the slots are per repository path (ADR-080 §8) and go with §5. `make reclaim`'s paths and `heavy.sh`'s floor are unchanged and still describe where the bytes are.

## Consequences

- An agent's `make check` waits for any running dogfood or other agent's build step, then runs its tests beside other work at half the cores; two agents' builds no longer compete for the cores, and a check's tests still run in parallel with another checkout's.
- Disk is not held once: each live worktree still holds its own build (15 to 30 GB, double after a coverage run). Removing merged worktrees with `scripts/worktree.sh remove` is what bounds it, and it no longer leaves a 15 GB slot build behind in `$TMPDIR`.
- Halving the test threads lengthens an agent's `make check`; the integrator's checkout and CI are unaffected.
- `heavy.sh` exports one more `CUPEL_*` variable; the fixture harness already strips `CUPEL_*` from every `cupel` it runs, and `cupel` reads only the names it knows.
- A successor that wants disk held once needs a content-addressed cache of compiled units (a compiler cache keyed by inputs, not by modification times), not a shared target directory; the measurements in Context are its acceptance test: a second worktree with an older edit must build its own code.
