# CUPEL_DECISION_139: The development tool environment is installed by the repository

**Date:** 2026-10-19 · **Status:** accepted · **Phase:** P9

## Context

Cupel's tests drive real tools: test runners, coverage tools, property frameworks, analyzers, race detectors, fuzzers, bench tools, JVM build tools, a model checker, a verifier, and a contract library. The goldens hold their messages and versions, and a golden regeneration keeps the old golden for any pair whose tool is missing. Until now the tools a merge needed lived in session scratch directories under `/private/tmp`, installed by hand from versions copied out of `ci.yml`. macOS's periodic cleanup deleted them mid-run on 2026-10-19, and earlier merges had regenerated goldens with a tool missing or at another version than CI (an unpinned vitest, Go 1.27 in place of 1.23), each costing a red CI run. Several of CI's own installs were unpinned (cargo-nextest, cargo-llvm-cov, pytest, pytest-cov, vitest, @vitest/coverage-v8, jest, the Node and Python patch releases), so even a careful local install could not match CI exactly. The owner's ruling: add `make dev-setup`, which installs or verifies every tool the merge procedure needs, with pinned versions; nothing that gates a merge lives outside the repository again.

The questions:

1. Where the tools are installed, and how the Makefile's targets find them.
2. How the local pins and CI's pins stay the same.
3. How installing stays safe while other agents are running tests with the same tools.
4. What the JVMs on the owner's Mac need to reach Maven Central.

## Options

**Location: inside the tree, a per-worktree directory, or one shared directory outside the tree.** A directory under `target/` is ignored by git and disappears with `cargo clean`, and each worktree would install its own JDK, Node, Python, and Kani bundle (several GB). A directory outside the tree, `${CUPEL_DEV_TOOLS:-$HOME/.cache/cupel/dev-tools}`, leaves `make clean-check` unaffected, survives `cargo clean`, is shared by every worktree, and is outside `/private/tmp`. The repository holds what is installed and how (`scripts/dev-setup.sh`), which is what the ruling asks for; the bytes stay in a cache.

**Finding the tools: a script to source by hand, or the Makefile exporting the environment.** Sourcing by hand is the step that was forgotten. The Makefile runs `scripts/dev-env.sh`'s `cupel_dev_env`, which prints `NAME=VALUE` lines, and exports each, so `make check`, `make test` (and a golden regeneration through it), `make parity`, `make dogfood`, and `make dist` all see the tools; sourcing `scripts/dev-env.sh` or `eval "$(make -s dev-env)"` gives a shell the same environment from the same function, so the two cannot drift. Without the tools directory it prints nothing, so on a CI runner the Makefile changes neither `PATH` nor the `JAVA_HOME` `setup-java` set. `CUPEL_DEV_TOOLS` is a make variable and is not exported, since Cupel reads `CUPEL_*` variables from its environment.

**Sources: Homebrew, or the pinned upstream releases.** Homebrew moves a keg to its newest release on any `brew upgrade`, and its kegs name a minor release, not a patch (this machine's `go@1.23` is 1.23.2, CI's `1.23` is 1.23.12). Every tool but one is downloaded at its exact release: ShellCheck, actionlint, zig, Dafny, Go, Node, the TLA+ tools, Maven, Gradle, and the Clojure CLI from their release URLs (the same URLs `ci.yml` uses where it downloads), CPython from python-build-standalone, the Python packages into one venv with `pip`, the npm packages into the Node install's own global prefix (as `setup-node`'s is) with Jazzer.js in a prefix of its own (`ci.yml` says why), and the cargo tools with `cargo install --locked` under the repository's pinned toolchain, as CI's steps run. The JDK is Temurin's archive (the distribution `setup-java` installs), except that Homebrew's `openjdk@21` keg is used when it is exactly the pinned release, 21.0.12.1 (the OpenJDK release Temurin's 21.0.12.1+1 builds), for the network reason below; it is linked by its versioned Cellar path, so a `brew upgrade` leaves the link dangling and the setup's report fails rather than drifting. Rust toolchains, components, and targets stay with rustup.

**Keeping the pins equal: a shared pin file read by both, or a test.** GitHub Actions cannot read versions from a file without extra steps in every job, and `ci.yml` stays the record of what CI runs. `crates/cupel-cli/tests/dev_setup.rs` reads every version `ci.yml` and the Linux and macOS steps of `release.yml`'s `build` job pin (`pkg==X`, `pkg@X`, `--version X`, `<tool>-version: 'X'`, `toolchain install X`, and version segments of URL paths) and fails while any is missing from `scripts/dev-setup.sh`. A second test fails while `ci.yml` installs a package or tool by name without a version, or names Node or Python without a patch release. The Windows-only `choco install make` step and the publish jobs (build and twine) are not mirrored: no local route runs them.

**Pins added to `ci.yml`**, at what CI resolved on 2026-10-19 so no golden moves: `cargo-nextest@0.9.148`, `cargo-llvm-cov@0.9.1`, `pytest==9.1.1`, `pytest-cov==7.1.0`, `vitest@5.0.5`, `@vitest/coverage-v8@5.0.5`, `jest@30.5.2`, Node `22.23.3`, and Python `3.12.10`. Python is 3.12.10 rather than the newest 3.12 because `actions/python-versions` has no macOS build after 3.12.10 (later 3.12 releases are source-only), so 3.12.10 is the newest release `setup-python` installs on both the Linux and the macOS runners; the macOS runner was already resolving `3.12` to it. Go's `1.23` and the JDK's `21` stay as they are: `1.23` resolves to 1.23.12, the final 1.23 release, and the script names that; the script names release 21.0.12.1, which `21` resolves to today (Temurin 21.0.12.1+1).

**Concurrency: replace in place, or install beside and switch.** Agents run tests from several worktrees at once with these tools. Each tool installs into a directory named for its version (`node-22.23.3-<hash of the npm pins>`, `venv-3.12.10-<hash of the Python pins>`, `go-1.23.12`), staged under `.staging-<pid>` and renamed into place once complete (the venv and the Clojure CLI, whose files record their own path, are built in their final directory instead); nothing uses that directory until a stable link (`node`, `venv`, `jdk`, `bin/<program>`) is switched to it, so a running test sees the old version or the new one, never half of one. A `.installed` marker in each directory makes a second run a pure verification. A lock directory serializes concurrent `dev-setup.sh` runs and is taken over when its holder has died.

**The pinned nightly.** `ci.yml` links `nightly-2026-03-26` as the toolchain `nightly`, which the race detectors and cargo-fuzz ask rustup for. This machine had a real `nightly` toolchain (a 2026-03-26 build, `rustc 1.96.0-nightly (23903d01c 2026-03-26)`, which is the 2026-03-27 nightly, not the pin), so `cargo +nightly` locally was not CI's compiler. The script replaces a real `nightly` with the link, saying so, as CI's runner has it.

## Decision

1. **`scripts/dev-setup.sh`** (`make dev-setup`) installs, under `CUPEL_DEV_TOOLS`, every tool `ci.yml`'s `check`, `dogfood`, and `installers` jobs install, at their pins; zig 0.16.0 and cargo-zigbuild 0.23.4 from `release.yml` with the other release targets added to the pinned toolchain; and actionlint 1.7.12 for linting the workflows. It adds `llvm-tools-preview`, installs the pinned nightly with Miri and `rust-src` and links it as `nightly`, runs `cargo +nightly miri setup`, and runs `cargo kani setup` with `KANI_HOME` under the tools directory. It ends with one line per tool and the version found, and fails when any is missing or at another version.
2. **`scripts/dev-env.sh`** is the one source of the environment: `PATH` with each installed tool directory in front, `JAVA_HOME`, `MAVEN_ARGS=-Dmaven.repo.local=…`, `GRADLE_USER_HOME`, `CLJ_CONFIG` (whose `deps.edn`, written by the setup script, points the Clojure CLI at the same local Maven repository), `CLJ_CACHE`, and `KANI_HOME`. The Makefile exports them for every target; `make dev-env` prints them as `export` lines.
3. **The pins are tied by `crates/cupel-cli/tests/dev_setup.rs`**, which also ShellChecks both scripts and checks what `make dev-env` exports with and without a tools directory.
4. **The JVM network finding: a per-application firewall, not the network; no proxy.** An earlier session found that JVMs on the owner's Mac could not reach Maven Central and routed them through a local HTTP CONNECT proxy. The cause is LuLu, the per-application outbound firewall installed there, which keeps allow rules by executable path: it holds one for Homebrew's `openjdk@21/21.0.12.1` java and none for a JDK unpacked anywhere else. On 2026-10-19, with no proxy variables and no system proxy (`scutil --proxy` shows HTTP and HTTPS proxies disabled), `curl` over IPv4 and IPv6 and the Homebrew keg's java fetched `https://repo.maven.apache.org/maven2/` with status 200, while the same request from the freshly downloaded Temurin 21.0.12.1+1 timed out, and Maven under it failed the JaCoCo coverage test with "No route to host". The scratch JDKs earlier sessions used were in the same position, which a proxy run by an allowed Python worked around. The script therefore links the Homebrew keg when it is the pinned release, and sets no proxy, `JAVA_TOOL_OPTIONS`, or proxy properties (a JVM that prints `Picked up JAVA_TOOL_OPTIONS` would change the output the goldens hold). Maven, Gradle, and the Clojure CLI then filled their caches under the tools directory directly while the fixture tests ran. On a machine without that keg the Temurin JDK is installed, and a firewall like LuLu must be told to allow it once.

## Consequences

- A fresh machine, or one whose tools were deleted, is one `make dev-setup` from a golden regeneration that matches CI; a missing or drifted tool fails the setup's report rather than silently leaving a golden stale.
- Changing a tool's version is a change to `ci.yml` and `scripts/dev-setup.sh` together; the test fails until both agree, and the next `make dev-setup` installs the new version beside the old one.
- The tools directory grows with each version change, since an old version may be in use by another worktree's run; deleting a version that nothing links to is safe at any quiet moment.
- The script supports macOS on arm64 and x86_64 and Linux on x86_64, the platforms CI runs on; Dafny publishes no Linux arm64 build.
- Rust toolchains, components, the Miri sysroot, and Kani's nightly stay in rustup's and Miri's own directories, which are not under `/private/tmp`.
- atheris is not installed, as in CI: `gen.fuzz` stays `unavailable` for Python.
