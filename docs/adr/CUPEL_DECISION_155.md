# CUPEL_DECISION_155: The instrumented suite run's phase breakdown and its cost

**Date:** 2026-10-30 · **Status:** proposed · **Phase:** B.1

## Context

On Cupel's own repository the warm one-function `standard` run (`make inner-loop`, P10 Notes "P10 — the final measurement") takes 342 s on `main` at 8bfd45d, and 270 s of it is the Rust suite joint (`tool.llvm-cov-nextest`, ADR-084), which reran 18 of 2 818 tests (ADR-149). P10.2 and P10.3 both inferred that most of those 270 s are the coverage-instrumented rebuild, the per-test profile export (ADR-083 §1), and the whole report (`cargo llvm-cov report --lcov`, ADR-084 §4), not the tests, but nothing measured it: the store's `durations` (ADR-086 §2) hold one row for the joint's production. The owner's ruling for v0.2.2 (plan, B.1) is to give the instrumented build its own incrementally compiled target directory, keep it warm from the daemon, and bring the warm run under 180 s. Whether the existing `target/cupel-llvm-cov` (ADR-084 §4) already compiles incrementally, and which phase dominates, decide what to change, so the breakdown is decided first, as ADR-150 did for the mutation engine.

What is known before measuring: `cargo llvm-cov` 0.9.1 never sets `CARGO_INCREMENTAL`, and Cupel's workspace sets no `incremental` in its profiles, so a local instrumented build of the workspace's own crates is incremental (cargo's default for the `dev`/`test` profile); CI sets `CARGO_PROFILE_DEV_DEBUG=0` and nothing about incremental. `target/cupel-llvm-cov` is already a target directory of its own, kept between runs by `--no-report`, outside the clean of `target/llvm-cov-target`, and removed by `make reclaim`.

## Options

**Where the breakdown lives.** (a) Rows the scheduler records: it times productions as a whole and knows no producer's phases (rejected in ADR-150 for the same reason). (b) In the fact, as ADR-150 did for `MutationOutcomes`: the joint's `TestResults.reuse` (`SuiteReuse`, ADR-149 §5), which says how the joint obtained its results, gains the phases the run went through, and the CLI records each phase's total in `durations` beside the production's own row. `SuiteReuse` is also the envelope's `run.suite` (ADR-149 §5), so `--format json` shows where a suite run's time went; the goldens redact every `duration_ms`.

**How to time the build apart from the tests.** (a) Two invocations, the compile alone first, then the run as before. `cargo llvm-cov nextest --no-run` is not nextest's flag but `cargo llvm-cov`'s own (deprecated: "report without running") and refuses `--no-report`; nextest's way to build without running is a filterset that matches no test, `-E 'none()'`, which builds every test binary and skips them all without listing them (probed on Cupel: `Starting 0 tests across 0 binaries (272 binaries skipped)`, 0.002 s after the build). The second invocation costs one more cargo start and fingerprint check. (b) One invocation, as now, split by cargo's own report of its build: cargo always ends a build with `Finished … target(s) in <time>` on standard error (`0.35s`, `1m 56s`), even when it compiled nothing; the build is that time and the tests are the rest of the invocation (nextest's listing, its runs, and cargo's start). No process is added and nothing about the run changes; a build that fails prints no such line, and then the invocation was its build.

## Decision## Decision

1. **The phases.** `SuiteReuse` gains `joint` (the joint's producer ID, absent in a fact written before it) and `phases: Vec<SuitePhaseDuration>`, absent from JSON when empty (`TestResults` stays version 2):

   ```text
   SuitePhaseDuration {
     phase: build | test | export | report,
     dir: String,            // the project root the phase ran in, relative to the repository root
     duration_ms: u64,
   }
   ```

   `build` is the instrumented compile of the suite; `test` is the run of the tests that are not kept (ADR-149 §1), with cargo's fingerprint check and nextest's listing of the test binaries; `export` is every test process's profiles merged and exported alone (ADR-083 §1); `report` is the whole run's `cargo llvm-cov report --lcov` (ADR-084 §4). A joint records the phases it runs, one row per phase per root, in the order they ended; a root served from the cache records none, and a joint that times nothing (Python's, Go's) records none.
2. **The Rust joint's build is read from cargo's report** (option (b)): `build` is the time on cargo's `Finished … target(s) in <time>` line in the run's standard error, at most the invocation's; `test` is the rest of the invocation. An invocation with no such line (a build that failed) records `build` alone, the whole invocation. The run's command, its environment, and what it reports are unchanged. `tool.llvm-cov-per-test`'s own run (ADR-083) shares the code.
3. **The store.** When a run is recorded, each language's `TestResults` whose `reuse` names a joint and holds phases adds one `durations` row per phase present, kind `producer`, task `<joint>.<phase>` (`tool.llvm-cov-nextest.build`), class `run`, with the phase's total over its roots, beside the production's own row. `scripts/inner_loop.sh`'s durations query lists them; the budget reads no such shape.
4. **What the breakdown showed** (2026-10-30, the release binary at d56fb89 on the clone `make inner-loop LABEL=b1-before` left after its warm run, `main` at 12c5a6c: a further comment inside `metrics::cyclomatic`, committed, then `cupel check --changed --depth standard --no-gate --jobs 4`, no daemon, AC power). The suite run took 329 s and reran the same 18 tests the inner loop's warm run did: **`build` 75.0 s, `test` 244.8 s, `export` 0.3 s, `report` 7.6 s.** The 18 tests themselves take 2–3 s (nextest's own summary, `Summary [ 2.813s] 18 tests run`); the rest of `test` is nextest listing every test binary of the workspace to evaluate the filterset `not (<the 2 801 kept tests>)`: 272 binaries, about 200 of them relinked by the build. On macOS the first execution of a freshly linked executable is scanned before it runs (`XprotectService` at 40–60 % CPU throughout the phase), so the first listing after the build took **255 s** and the same listing again **4 s** (by hand in the same clone: a build with `-E 'none()'`, 75 s, then `-E 'test(=no_such_test)'` twice). Incremental compilation was already on: `cargo llvm-cov` 0.9.1 never sets `CARGO_INCREMENTAL`, the workspace's profiles leave it on, and `target/cupel-llvm-cov/debug/incremental` held 5.9 GB; the build's 75 s is about 200 relinks of instrumented test binaries (cargo's `--timings`: 210 units, 658 s of CPU, each test binary 3–8 s), not recompilation. The export (one merge and export per rerun test) and the report are not where the time goes.

## Options (the listing)

(a) **Keep every binary listed and pay the scan ahead of the run** (the daemon lists after it builds): the cost moves out of the check only where a daemon watches, and the inner loop runs without one. (b) **List only the binaries that can hold a test the run runs.** nextest evaluates a filterset's binary-level predicates (`binary_id`, `package`, `kind`, `binary`) before it lists a binary and never executes a binary they exclude (probed: `(binary_id(=cupel-checks::static_crap) | binary_id(=cupel-fixtures::matrix) | (package(=cupel-checks) & (kind(lib) | kind(bin) | kind(proc-macro)))) & not (<kept>)` ran the same 18 tests with `269 binaries skipped`, in 4 s). An incremental run runs the stale tests and any test the cache does not hold; a test the cache does not hold can only be in a changed source file (an added one makes the run whole, ADR-149 §2), so the binaries that can hold one are the stale tests' binaries and the binaries a changed source file is compiled into. (c) **Build only those binaries too**: fewer relinks (most of `build`), but tests that spawn the workspace's own executables (`assert_cmd::cargo_bin("cupel")` from `cupel-fixtures`) find them beside the test binary, where only a build of the package that owns them refreshes them, so a narrowed build would run a stale `cupel` and report its coverage (ADR-150's first option, open since). Not here.

## Decision (continued)

5. **An incremental Rust run lists only the binaries that can hold a test it runs** (option (b)). The joint's run gets, beside the tests it keeps, the stale tests (the cached tests it does not keep) and the changed files (ADR-149 §1). With tests kept, the filterset is `(<binaries>) & not (<kept>)`, `<binaries>` the union of `binary_id(=<b>)` for each stale test's binary (the part of its ID before the first space) and, for each changed `.rs` file, the targets it is compiled into, by the nearest enclosing directory whose `Cargo.toml` names a `[package]` `P`: below `src/`, `package(=P) & (kind(lib) | kind(bin) | kind(proc-macro))`; below `tests/`, `package(=P) & kind(test)`; anywhere else in the package (`benches/`, `examples/`), `package(=P)`. A changed `.rs` file in no package lists every binary, as before. A run with nothing kept (whole, ADR-149 §2) lists every binary, as before. The build is unchanged: every test binary is still built, so the run's tests and the per-test map are exactly what they were.
6. **The daemon keeps the build warm.** `JointProducer` gains `warm(ctx, changed) -> Result<bool>`: build ahead of a run what the next run would build first, when one of `changed` (paths under the repository) is a file its runs depend on, and say whether it built. The Rust joint does when a changed path is a `.rs` file or one of ADR-083's whole-suite files (`Cargo.toml`, `Cargo.lock`, …) outside the root's build outputs (`target/`), and builds with the run's own arguments, environment, and target directory and the filterset `none()`, which builds every test binary and lists none; the Python and Go joints build nothing ahead of their runs. `cupel serve --watch` warms after the watcher's changes: once they settle (2 s with no further change), when no request is running, at most one warm at a time, never while the machine-wide heavy-command lock (`CUPEL_HEAVY_LOCK`, `/tmp/cupel-heavy.lock` by default, the lock `scripts/heavy.sh` takes) is held or its priority turnstile is pending, and holding that lock while it builds, so a heavy command waits for it as for any other; it is cancelled when the daemon stops. A request that starts while a warm builds waits on cargo's own lock of the target directory and finds the build done. Without `--watch` the daemon warms nothing.
