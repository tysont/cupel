# CUPEL_DECISION_099: `--format sarif`: rules, results, the run's metadata, and what rides in `properties`

**Date:** 2026-10-16 · **Status:** accepted · **Phase:** P6.1

## Context

Design §7.3 fixes the outline of the SARIF rendering: SARIF 2.1.0, one `rule` per finding kind, `level` from severity, `partialFingerprints.cupel/findingId`, `fixes` empty, and properties carrying tier, confidence, and action. It does not say which rules a log lists, what a rule's text is, where a finding's location, symbol, evidence, repro, and suppression go, how the run's metadata (git revision, start, exit code, scope, toolchain, configuration) is shown, what becomes of the rest of the envelope (`checks`, `summary`, `next_actions`, and the verb payloads of `describe`, `explain`, `survey`, `tests`, `oracle`, and dry runs), or how a SARIF consumer finds the files a relative path names. SARIF has a place for some of these and none for the rest; every verb prints an envelope, so every verb must have a SARIF rendering. `--format sarif` has parsed since P0.3 and exited 2 as not implemented (ADR-018 §4).

## Options

**Which rules.** (a) Only the kinds the findings have: a clean run lists no rules, so a consumer cannot tell "ran and found nothing" from "did not run". (b) Every kind of every registered check: hundreds of rules in every log, most of them for checks that did not run. (c) Every kind the checks in the envelope's `checks` declare, then any other kind a finding has (a CLI, doctor, suppression, oracle, or plugin finding): the rules are what ran.

**Where Cupel's own data goes.** (a) Only what SARIF has a place for: the evidence, repro, action, scope, gate, and verb payloads are lost, and SARIF stops being a rendering of the envelope (design §6.1 rule 1). (b) The envelope whole in the run's properties and each finding whole in its result's: lossless but every mapped field twice. (c) SARIF's places filled, and in `properties` exactly what has none: lossless with little repetition, at the price of a mapping to document.

**Locating files.** (a) Bare relative URIs: valid, but SARIF leaves their base to the consumer. (b) Absolute `file://` URIs per result: the log depends on the checkout's path in every result. (c) Relative URIs with `uriBaseId: SRCROOT`, and `originalUriBaseIds.SRCROOT` the repository root's `file://` URI once, which SARIF §3.14.14 defines for exactly this. The root is known to the CLI once it has resolved `--cwd`, not to the envelope, so the renderer takes it as an argument.

**The git revision.** `versionControlProvenance` requires a `repositoryUri`. The envelope has no remote URL, and reading one would add run metadata the JSON envelope does not carry. The local repository's own `file://` URI is a valid repository URI (git accepts it), and it is the same root (c) above names.

## Decision

1. **A log** is `{"$schema": <the OASIS schema URL>, "version": "2.1.0", "runs": [one run]}`, pretty-printed with a trailing newline, from `cupel-cli/src/render/sarif.rs` (`Rendering::Sarif`). Every verb renders it, errors included; the exit code is the envelope's.

2. **`tool.driver`**: `name: "cupel"`, `version` and `semanticVersion` the envelope's `cupel.version`, and `rules` per option (c): the declared kinds of each check in `checks`, in that order, then every other finding kind in order of first appearance, each kind once. A rule is `{id: <kind>, shortDescription: <the kind's summary>, fullDescription: <the check's summary>, help: <summary, "Action: <kind>.", and the `cupel describe finding <kind>`, `cupel describe <check>`, and `cupel explain <finding-id>` commands>, properties: {check, action, tier, cost, stability}}`, from the built-in catalog (`Catalog::finding`, the data of `describe finding`). A kind the built-in catalog does not know (a plugin's, the CLI's own) gets `shortDescription` "A `<kind>` finding of <check>.", the same help commands, no `fullDescription`, and `properties: {check}`.

3. **One result per finding**, in envelope order (after paging, as every renderer): `ruleId` the kind and `ruleIndex` its rule; `level` `error`, `warning`, `note` for `fail`, `warn`, `info`; `message.text` the title, then a blank line and the detail when there is one; `locations: [{physicalLocation: {artifactLocation: {uri, uriBaseId: "SRCROOT"}, region: {startLine, startColumn?, endLine, endColumn?}}, logicalLocations: [{fullyQualifiedName: <symbol display>, kind: "function"}]}]` with whichever of the two the finding has (none, no `locations`); the path percent-encoded except unreserved characters and `/`; Cupel's columns are already 1-based with the end one past the last character, as SARIF's are; `partialFingerprints: {"cupel/findingId": id, "cupel/symbolHash": hash}` (the hash when there is a symbol); `suppressions: [{kind: "external", status: "accepted"}]` for a suppressed finding (the suppression lives in `.cupel/suppressions.toml`, outside the source) and `[]` otherwise, so "not suppressed" is stated rather than unknown; `baselineState` `new` or `unchanged` from `new_since_baseline`, only when the run had a baseline; `fixes: []`.

4. **What has no SARIF home rides in `properties`**: a result's properties are the finding without the fields rendered above (`id`, `severity`, `title`, `detail`, `location`, `suppressed`), that is `check`, `kind`, `confidence`, `tier`, `symbol`, `evidence`, `action` (kind, priority, summary, hints), `repro`, `suppress`, and `new_since_baseline`. The one invocation's `properties` are the envelope's `run` whole (ID, verb, start, duration, git, scope, depth, budget, seed, toolchain, configuration, baseline). The run's `properties` are the envelope without `run` and `findings`: `cupel` (version and schema), `status`, `exit_code`, `checks`, `summary` (counts, gate), `next_actions`, `description`, `plan`, `explanation`, `rankings`, `tests`, `oracles`, `truncated`, and `total_findings`. So the envelope can be rebuilt from a log.

5. **The invocation**: `executionSuccessful` true for status `pass`, `fail`, and `plan` (the tool did its work; a failed gate is a result, not a failure) and false for `error` and `partial`; `exitCode` and `exitCodeDescription` the exit code and its name (`fail`); `startTimeUtc` `run.started`. No `endTimeUtc` (Cupel has no date arithmetic; the duration is in `properties.duration_ms`), and no `commandLine` (the envelope does not record the arguments).

6. **The run's identity and place**: `automationDetails.id` is `cupel/<verb>/<run-id>` (`cupel/<run-id>` when no verb parsed), so a consumer keeps one category per verb and the run ID is SARIF's. When the CLI resolved the repository root, `originalUriBaseIds: {SRCROOT: {uri: "file://<root>/"}}`, and, in a git repository, `versionControlProvenance: [{repositoryUri: <the same URI>, revisionId: git.sha, branch?, mappedTo: {uriBaseId: "SRCROOT"}}]`; `git.dirty` and `git.base` are in the invocation's properties.

7. **The schema test.** The OASIS schema (2.1.0 Errata 01, draft 4) is vendored unmodified at `crates/cupel-fixtures/schemas/sarif-schema-2.1.0.json` and checked with the `jsonschema` crate (formats included) by `cupel_fixtures::sarif_problems`; the renderer's unit tests, the CLI's every-verb test, and the golden `golden/cli/sarif-check.json` all validate with it. The golden harness recognizes a SARIF log (`sarif_log`), and `redact_sarif` masks it as `redact` masks an envelope, so `make parity` compares SARIF through the daemon too.

## Consequences

- SARIF consumers (code-scanning uploads, IDE viewers) see Cupel's findings at their lines, deduplicated by finding ID across runs, with suppressed findings marked; agents keep reading the JSON envelope, which remains the contract.
- The SARIF log, unlike the envelope, holds the absolute repository root (twice). That is what SARIF's base URIs are for; redaction masks it in goldens and parity.
- A plugin check's kinds have bare rules: the renderer reads only the built-in catalog, because the plugins the run loaded are not passed to rendering. Passing them is the follow-up if plugin rules need text.
- Cupel's columns are UTF-8 byte columns (tree-sitter's), and SARIF's are UTF-16 code units or code points; `columnKind` is left unset. On a line with non-ASCII text before the site, a consumer's column is off by the extra bytes.
- `toolExecutionNotifications` are not used: a check that errored or was skipped is in the run's `properties.checks` with its reason. Mapping those to notifications is additive.
- Adding a field to the envelope or a finding puts it in the SARIF `properties` without a renderer change, since those are the serialized envelope and finding less the mapped fields.
