# CUPEL_DECISION_149: The suite joint's incremental run on a range scope

**Date:** 2026-10-28 · **Status:** accepted · **Phase:** P10.1

## Context

`cupel check --changed --depth standard` on a one-function change in Cupel's own repository takes 1 172 s warm, of which the suite joint `tool.llvm-cov-nextest` is 886 s (P4 Notes, "P4 — Definition of Done, remeasured"): ADR-084 §6 reruns the whole workspace under instrumentation on any change under the root, so that the mutation and flake engines always start from a real baseline of the tree. The per-test cache the same run writes already knows, per test, which lines of which files it executed, and ADR-084 §7 already says which tests a changed function makes stale; the joint does not use either to run fewer tests. ADR-083 §3 refreshes the per-test map incrementally (`-E 'not (<kept tests>)'`), but only for `tool.llvm-cov-per-test` on its own, and only for the map: the baseline and the coverage report have no incremental form. The owner's P10 ruling (plan, P10.1): on a `--changed` or `--base` scope, run only the tests `tests --impacted` would select, under instrumentation, and merge their results and per-test coverage with the stored ones of every unselected test, keyed by the test's structural hash plus the hashes of the files the test covers; invalidate per test, not per suite; a full instrumented run only when the store has no baseline for the current toolchain or at `--depth deep`; the envelope reports how many tests were rerun and reused.

## Options

**What "the hashes of the files that test covers" means.** (a) A file-level key: a test is stale when any file it covers changed. On Cupel, 101 tests cover `crates/cupel-checks/src/metrics.rs` and every check module registered through `inventory` is covered by about 225 tests (ADR-083 consequences): a one-function change would rerun a fifth of the suite, which is the per-test producer's refresh today and not the inner loop P10 wants. (b) ADR-084 §7's function-level comparison: the changed file is diffed line by line against the lines as measured, each hunk placed in the innermost current function, and only the tests that executed a line of that function's measured span are stale; the file rule stands where §7 falls back (a change outside every function, a function with no unchanged line, no `Symbols` for the file, no stored lines). The key is still the files' content, read at the resolution of the functions the test actually ran.

**The test's own structural hash.** (a) Leave it to §7: a test that executes its own lines (Rust and Python test bodies are instrumented) is stale when its body changes, since its body is a changed function it ran. (b) Record the hash too: the `NormTree` hash of the symbol holding the test's case (`TestFrames`, matched by case name as `tests --impacted` matches, ADR-077 §5), compared when the test's file changed. It adds staleness only where §7 misses the test's own change: a test whose body is not in its own coverage (a macro-generated body, a test the coverage tool attributes to no line) or a rename that §7 reads as a change but the hash does not. The rule is additive to §7, never a reason to keep a test §7 marks stale.

**What the coverage map of a merged run is.** (a) The cached map, kept as it was: wrong for the changed files, whose instrumented lines moved and whose hits the stale tests must re-measure. (b) The incremental run's report, which `cargo llvm-cov report` makes over every object the instrumented build made, so it holds the current instrumented line set of the whole root with hits from the measured tests only, plus one hit for every kept test on every line it executed, moved through the diff as §7 moves kept tests' lines. Every consumer reads only whether a line ran (ADR-084 §4); the per-test map does not keep counts, so a kept test counts one. (c) The union of the cached map's unchanged files and the report's changed files: two sources of instrumented lines that can disagree after a rebuild (a removed function in an unchanged file's inlined callers).

**When the run is incremental.** (a) Whenever the entry reads back and something changed: a tree run would then measure a change's effect only where the staleness rule places it, and the engines' baseline would be partly cached; ADR-084's reason for a full rerun (a real baseline of the tree they mutate) stands for the tree gate. (b) Only on a range scope (`Focus::changed`), below `deep`: the inner loop, where the user's change is the range and the mutants are its functions, whose covering tests are the stale ones.

**The toolchain.** A cached entry measured by another compiler or interpreter can differ in every count and in which lines are instrumented. (a) Trust the file record alone, as today. (b) Record the toolchain the entry was measured with (`rustc -vV`'s `release` and `host`; the Python interpreter's version and pytest's) and read an entry from another as no cache, on the cached path as on the incremental one.

**Where the envelope says what ran.** (a) Only `PerTestMap.measured`/`reused` (ADR-083 §3), which `tests --impacted` reports; `check` does not. (b) A field on `TestResults` saying how the baseline was obtained, so the fact that is cached says it was, and the run envelope's `run` block, where the toolchain and scope already are, repeats it per language.

## Decision

1. **The incremental run** (options b throughout). On a range scope (`Focus::changed` is set) below `deep`, a joint that makes the per-test map (`tool.llvm-cov-nextest`, `tool.pytest-cov-contexts`) whose entry for the root reads back, records the current toolchain, and whose per-test entry reads back too, computes the stale tests of the root with the per-test producer's rule (ADR-083 §3 as refined by ADR-084 §7: whole-suite files, owned files, changed functions the test ran, the file rule where §7 falls back) *and* the structural rule of §3 below, runs only the tests that are not kept (the stale tests and any the entry does not hold, through nextest's `-E 'not (<kept>)'` or pytest's `--deselect` per kept test), and merges: `TestResults` are the kept tests' recorded results plus the run's, the run's replacing a kept test of the same ID; the per-test map is the kept tests, their lines moved through the diff, plus the measured ones (`per_test::merged`); the `CoverageMap` is the run's report with one hit added for every kept test on every line it executed that the report instruments. The merged run is cached as the entry when it is green and whole (ADR-141 §2), with the record of the tree after the run, so the next change compares with it. The envelope's `tests.coverage` value on an unchanged function is unchanged. Go's joint has no per-test map and always runs whole.
2. **A whole run** happens as today on a tree scope, at `--depth deep`, with no entry, an entry of another version or toolchain, an incomplete or red one (never written, ADR-141 §2), or a change the rule cannot place: a changed whole-suite file (`Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain*`; `conftest.py`, `pyproject.toml`, `setup.cfg`, `setup.py`, `pytest.ini`, `tox.ini`) makes every test stale, and an added file that may hold a test (by extension) runs the whole suite, since nothing recorded says what it changes. An unchanged tree is served from the entry, as today.
3. **The structural rule.** The entry records, per test, the `NormTree` hash of the innermost `Symbols` function holding its test case, where the run's `TestFrames` name exactly one case of that name (the case name is the ID's last `::`-, `/`-, or space-separated part, as `tests --impacted` reads it); a kept test keeps its recorded hash, a measured test in scope gets a new one. A test whose case's file changed and whose recorded and current hashes are both known is stale when they differ. The joint wants `Symbols`, `NormTree`, and `TestFrames` for it (`JointProducer::wants`, made within the depth before the run as a producer's wants are); on a range scope they cover the changed files, which are the files whose tests the rule compares.
4. **The toolchain record.** The suite entry (`report`, version 3) holds `toolchain`: for Rust, `rustc -vV`'s `release` and `host`; for Python, `python3 --version` (or `python`) and `pytest --version`; for Go, `go version`. An entry from another toolchain reads as no cache on every path. The probe runs once per root and process.
5. **The envelope.** `TestResults` gains `reuse` (fact version 2): null for a runner that reruns its suite every time; for a joint, `{ mode, rerun, reused }` with `mode` one of `full` (every test ran), `incremental` (the stale and new tests ran, the rest were kept), or `cached` (nothing ran). The run envelope's `run.suite` maps each language whose baseline a joint made to the same object, empty when none did; the text renderer's `run` block prints `suite: rust incremental · 1 rerun · 3 reused`. `cupel describe schema run` shows both. `tests --impacted` keeps reporting `measured`/`reused` from the per-test map.
6. **Estimate and dry run.** `JointProducer::estimate` takes the run's `Focus` beside the context and upstream facts, so it can say what the run would do: `cached` when nothing changed, `incremental: N stale` on a range below `deep` with an entry of this toolchain, else `one run`. A planned check's `needs` entry reads `test-results+coverage-map+per-test-map(incremental: N stale)` beside ADR-084 §8's `(one run)` and `(cached)`. The fact store's rule for using a joint (ADR-084 §2) is unchanged: `cached`, or at least two of its facts would each run.

## Consequences

- A one-function change on a repository with a green suite entry reruns the tests that ran the function, builds the instrumented workspace incrementally in its own target directory (ADR-084 §4), exports those tests' profiles, and makes the report once; the suite cost of the inner loop becomes a function of the change, not of the suite. Measured in P10 Notes "P10.1 — measurement".
- The mutation and flake engines get a baseline that is partly recorded on a range scope: a kept test's result is the one measured on a tree whose files that test ran have not changed since (at the function level), plus ADR-083's and ADR-084 §7's holes (a change to a file no test's coverage names, a `const fn`, a closure stored and called by a test that did not run the function). A tree run and `--depth deep` keep the real baseline.
- A kept test is green by construction (ADR-141 §2 caches only green runs), so refusal (exit 4) comes from a measured test alone; a red incremental run is not cached and the next run recomputes the same stale set.
- Hit counts of a merged map are one per kept test on each of its lines, plus the measured tests' counts; a count is not a run's count anywhere a consumer reads one, and none does (ADR-084 §4).
- An added source file runs the whole suite under the joint, though the per-test producer's own refresh (ADR-083 §3) measures only the tests it does not hold; the two rules differ by design, and the per-test producer's is unchanged.
- The structural rule needs three language facts the joint did not want before; on a range they are made for the changed files, in milliseconds. Without them (a producer that fails, a file the queries do not cover) only §7 and the file rule apply.
- `rustc -vV`, `python3 --version`, `pytest --version`, or `go version` runs once per root per process; a toolchain change reruns the suite once, on the cached path too, where today an unchanged tree would be served by an entry another compiler measured.
- `TestResults` version 2 and the suite entry version 3 read older rows and entries as absent: one whole run after this change.
