# CUPEL_DECISION_148: A memory budget for mutant runs, and the slots' share of the test threads

**Date:** 2026-10-25 · **Status:** accepted; §3 amended on 2026-10-25 (P9.9 group 1): a run's budget and kill cover every descendant, whichever process group it is in; §3 amended on 2026-10-28: the resident set is read from a sample taken since the spawn returned · **Phase:** P9.F7

## Context

On 2026-10-24 the development machine (eight cores, 24 GB) panicked while group 1's external dogfood (P9.9) ran mutants on serde_json: `watchdog timeout: no checkins from watchdogd in 92 seconds`, with the kernel's compressor at 100% of its limit and five swap files in use. The threads busiest at the panic belonged to serde_json's `regression` and `test` integration binaries, run by the mutation engine. Two earlier unplanned reboots that week (2026-10-19, 2026-10-22) fall in the same work. The cap of ADR-147 was merged two hours before the panic and did not prevent it: it bounds a mutant's time, and a mutant that makes a parser loop while allocating holds gigabytes well within 120 s.

Two things multiply. First, the engine runs up to four slots at once (ADR-080 §8, ADR-141 §3) and hands each run to the runner with no parallelism of its own (`RunOptions::parallelism` is `None`), so each slot's `cargo nextest run` starts as many test processes as the machine has cores: four slots on eight cores run up to thirty-two test processes, each able to hold a runaway mutant. Second, nothing bounds what a mutant's run may hold in memory. The timeout is enforced by `Process` through the run's `Cancellation` (ADR-076 §3), which kills the child's process group; nothing watches the group's memory.

## Options

**Bounding concurrency.** (a) Leave each slot's run at the runner's default, and lower `jobs` by hand where it matters: the default stays unsafe on every machine with more than two cores. (b) The engine hands every run of a production (the reference and validation runs as well as the mutants, so a mutant's timeout is measured under the same parallelism) `parallelism = max(1, cores / slots)`, and every runner with a threads or workers flag takes it: `cargo test --test-threads`, `go test -p -parallel`, `jest`/`vitest --maxWorkers` already do; `cargo nextest` gains `--test-threads` (its variation stays fixed otherwise: one process per test has no order or seed to vary, ADR-078). A Rust run rebuilds before it tests, and `cargo` builds with one job per core, so the two cargo runners take the share as their build jobs too (`--jobs`, `--build-jobs`): four slots each linking with eight jobs is the same storm in the build; `go test -p` already bounds both. A runner without such a flag (pytest, unittest, Surefire, Cupel's Clojure runner) keeps its default. Chosen: (b): the slots together never run more test processes than the machine has cores.

**Bounding memory.** (a) A resource limit on the child (`setrlimit`): macOS does not enforce `RLIMIT_AS` or `RLIMIT_DATA` on the allocator, a limit is per process and a runner's tree is many processes, and setting one needs `pre_exec`, which is `unsafe` (the workspace denies it). (b) Watch the machine's memory pressure and stop every mutant run when it turns critical: no blame, so healthy mutants of the other slots end with the runaway, and another program's pressure ends mutant runs. (c) A budget per run on the resident set of its process group: the group is sampled while it runs and killed when it holds more than its budget, the way the timeout kills it. Measuring without `unsafe` means `ps -A -o pgid= -o rss=`, which both macOS and Linux print alike (resident set in KiB); one sample serves every running process and is taken at most every 200 ms, so the slots together cost at most five `ps` a second (about 15 ms each on a busy machine). A run can overshoot its budget by what it allocates in one sample interval. Chosen: (c), with the overshoot documented. Windows has no `ps`; no budget is enforced there, as no mutant has run there (ADR-137).

**Where the budget is set.** (a) `[lang.<id>] mutation = { memory = … }` beside `jobs`: a per-language tool table for what is a policy of the check on how much a mutant may cost the machine, the same reasoning as ADR-147. (b) `max_mutant_memory` under `[checks."tests.mutation"]`, declared with `configures = mutation-outcomes` as `max_mutant_timeout` is, reaching the engine through `ProduceCtx::settings` (ADR-147 §2). Chosen: (b). Its value is bytes (`512m`, `3g`) or a share of the machine's physical memory (`50%`): a share makes one default right on a 16 GB runner and a 128 GB workstation. The budget is for the slots together, each run getting an equal part: whatever the setting, the slots cannot hold more than it between them, which is the property that keeps the machine up.

**What a stopped run is.** (a) `timeout`, as a run the cap ends: the finding then says the tests ran past their timeout, and the remedy an agent reads from it (raise the cap) is the wrong one. (b) A new outcome, `out-of-memory`, with its own finding kind and metric, left out of the score as a timeout is: one more enum value in the fact (additive, its version unchanged), one more kind in `describe`, one more gate key. Chosen: (b).

## Decision

1. **The threads.** The engine runs every run of a production (reference, schemata validation, mutants) with `parallelism = max(1, cores / slots)`, where `cores` is the machine's available parallelism and `slots` the slots the production uses (`min(jobs, the widest file)`). `cargo nextest` takes it as `--test-threads` and `--build-jobs`; `cargo test` as `--test-threads` and `--jobs`. Runners without a parallelism flag are unchanged.
2. **The budget.** `tests.mutation` declares `max_mutant_memory`, default `"50%"`, with per-language overrides as any setting: the resident memory the mutant runs of a production may hold together, as a whole number of `k`, `m`, or `g` (KiB, MiB, GiB) or a percentage of physical memory (`1%` to `100%`). Each run gets the budget divided by the slots. A value of neither shape is a configuration error at plan time. The budget is not part of a mutant's cache key, as the time cap is not.
3. **Enforcement.** `RunOptions` gains `memory: Option<u64>`, bytes the run's process group may hold; `Process` gains `memory(bytes)`. While such a child runs, `Process` reads the group's resident set from a sample of `ps -A -o pgid= -o rss=` shared by every running process and renewed when older than 200 ms; a group over its budget is killed as a cancelled one is, and the run is `Error::OutOfMemory { limit }`. *Amended 2026-10-25.* `cargo nextest` runs each test in a process group of its own, so neither the group's sample nor the group's kill reached a nextest test: on serde_json (P9.9 group 1) a survey's mutation run ended with its nextest killed and two `test_deserialize_from_stream` processes reparented to `launchd`, alive an hour later and holding the heavy lock's descriptor, and a test process that allocated would have been outside every budget. A run is now its process group and every descendant of a process in it, whatever group the descendant is in: the sample is `ps -A -o pid= -o ppid= -o pgid= -o rss=` and the run's resident set sums its members; a kill stops every group the run spans (SIGSTOP, so none forks a process the kill misses), lists them again until no new group appears, and kills them all (SIGKILL); a termination's SIGTERM goes to every such group too. Physical memory is `hw.memsize` (macOS) or `MemTotal` (Linux); where neither it nor `ps` is available, no budget is enforced. *Amended 2026-10-28.* A sample is read for a run only when it was taken after the run's spawn returned (`memory::resident_since`). On Linux a `posix_spawn`ed child shares its parent's memory until it calls `exec` (`CLONE_VM`), and `ps` lists it in that window with the parent's resident set: a sample another `Process` took during the spawn, reused within its 200 ms, counted the parent against the child's budget and killed the child before it ran. The ubuntu `check` job of CI runs 40596861632 and 40639818372 lost `a_descendant_in_a_process_group_of_its_own_counts_against_the_memory_budget` to it (the child ended at once and its pid file never appeared); a probe in a Linux container (a 211 MiB parent, `posix_spawn` of `true` in a loop, a thread reading every child's `statm`) saw the parent's resident set on 29 of 59 500 children. A sample taken during a *descendant's* spawn still lists that descendant with its own parent's memory for the window, a double count bounded by one process's resident set; the budgets a slot runs under are gigabytes, so it stands.
4. **The outcome.** `MutantOutcome::OutOfMemory` (`out-of-memory`): a mutant whose run was killed over its budget. `tests.mutation` reports it as `mutant.out-of-memory` (`info`, action `review`, evidence `{mutation}`), counts it in a metric `out_of_memory`, and leaves it out of the score. A reference or validation run (the unmutated file) over its budget is a production error naming the setting, since every mutant of that file would exceed it too.

## Consequences

- Four slots on eight cores run at most eight test processes (and, for Rust, eight compiler jobs) instead of thirty-two, and however many mutants loop while allocating, the slots together hold at most half of physical memory plus one sample interval's allocation each; the machine keeps enough to stay responsive and to kill them.
- A mutant that honestly needs more than its share (a build that links a large crate, a suite that spawns many processes) is `out-of-memory`, not scored, and its finding names the remedy: raise `max_mutant_memory` or lower `jobs`. Cupel's own dogfood runs with four slots within 3 GB each on the development machine.
- Fewer threads per slot make each run slower by up to the thread share; the reference run is measured the same way, so the timeout follows.
- The measurement is a sample: a run allocating at several GB/s overshoots its budget by up to that much per 200 ms. A finer or cheaper measurement (reading `/proc` on Linux, `proc_pidinfo` behind a safe wrapper on macOS) can replace the sample without changing the setting or the outcome.
- On Windows the budget is declared and read but not enforced until a measurement exists there.
- ADR-080 §8 (slots) and §9 (timeouts) and ADR-147 §1 are amended by this decision: a run is bounded by time and by memory, and the slots share the cores.
