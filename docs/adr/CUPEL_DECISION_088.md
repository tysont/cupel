# CUPEL_DECISION_088: Plugin discovery, registration, and selection

**Date:** 2026-10-16 · **Status:** accepted · **Phase:** P5.1

## Context

Design §8.6 says plugins are discovered from "entries under `[plugins]` in `cupel.toml`, plus any `cupel-check-*` or `cupel-produce-*` executable on `$PATH` (disabled by `--no-path-plugins`)", that they "declare the same manifests as native code and enter the same registries" (§8.3.8), and that a producer plugin "is selected by the same rules" as native producers (§8.3.3). It leaves open: the shape of a `[plugins]` entry; the order of discovery and what a name found twice means; which `PATH` is searched (the daemon serves clients whose `PATH` it compares with its own, ADR-085 §5); when discovery runs and what a plugin that cannot describe itself does to a run; where plugins sit in registration order relative to native checks and producers, which decides selection; how plugin IDs avoid colliding with native ones; and what kinds a producer plugin may provide.

## Options

**Entry shape.** (a) A path string only: interpreted plugins (Python, TypeScript) then need an executable wrapper with a shebang, which Windows lacks. (b) A string or an array: a string is one executable (a path relative to the repository root when it contains `/`, else a program on `PATH`), an array is a program and its leading arguments, such as `["python3", "tools/cupel_cov.py"]`. (c) A table with `command`, `env`, `timeout`: more than any plugin here needs.

**A plugin that cannot describe itself.** (a) Drop it with a warning on stderr: a run then silently loses a check or a producer, which design §8.3 forbids ("coverage gaps are visible, not silent"). (b) A usage error (exit 2) naming the plugin and the fix, as a broken `cupel.toml` is: the user fixes the entry, removes the executable, or passes `--no-path-plugins`.

**Registration order.** (a) Plugins before native producers: a plugin would displace a working native producer just by being installed. (b) After them, in discovery order: a plugin serves what no native producer serves, or stands in where the native ones are not ready (tool missing, unconfigured), and a pin chooses it explicitly.

## Decision

1. **`[plugins]`.** `ConfigFile` gains `plugins: BTreeMap<String, PluginEntry>`, a closed section whose keys are plugin names (lowercase letters, digits, `-`) and whose values are a string (one executable: a path relative to the repository root when it contains `/`, else a program found on `PATH`) or a non-empty array of strings (a program and its leading arguments). Plugins run with the repository root as their working directory. The envelope's `run.config` echoes `plugins` only when the table is non-empty, so runs without plugins keep their shape.
2. **`PATH`.** The directories of the invocation's `PATH` (`Environment.path`: the client's, which a daemon serves only when it equals its own, ADR-085 §5) are searched in order for files named `cupel-check-<name>` or `cupel-produce-<name>` with an execute bit, sorted by name within a directory; a name found in an earlier directory shadows later ones, as a shell would; a file whose canonical path a `[plugins]` entry already runs is skipped. The plugin's name is its file name. `--no-path-plugins`, a new global flag, skips this search; `[plugins]` still loads. An invocation built without a `PATH` (the in-process tests) finds none.
3. **Order.** `[plugins]` entries by name, then `PATH` plugins in search order.
4. **When.** Discovery runs once per invocation, after configuration loads and before it is validated against the registries (so `[checks."<plugin-check>"]` and gate rules on plugin metrics validate), for every verb that loads configuration. Each plugin is run as `<plugin> describe` with a 10-second limit under the run's cancellation; nothing is cached between invocations, so a cold run and a daemon request discover the same plugins from the same `PATH` and files. `init`, `doctor`, and `serve` run when configuration does not load (ADR-021, ADR-022, ADR-085); they also run, without plugins, when discovery fails, and `doctor` reports the failure as it reports a broken `cupel.toml`.
5. **Failure.** A plugin that cannot be started, exits non-zero, prints anything but one manifest, describes a manifest that fails validation (ADR-089 §1), describes another kind than its `cupel-check-`/`cupel-produce-` name says, or registers an ID already registered is a usage error (exit 2) from `ConfigError::Plugin`, subject `plugins.<name>`, whose fix names the entry or the executable and, for a `PATH` plugin, `--no-path-plugins`.
6. **IDs.** A check plugin's ID is any valid `<group>.<name>` check ID (ADR-017) not already registered. A producer plugin's ID must start with `plugin.`, so a dry run's `needs`, `describe fact`, and a pin show where a fact came from.
7. **Registration.** Check plugins are registered in `CheckRegistry` after the native checks, in discovery order; producer plugins in `ProducerRegistry` after the native producers (language, tool, engine), in discovery order. A producer plugin reports itself `detected` and `Ready` (it answered `describe`), costs its manifest's cost class, and has no tool probe. Selection is then unchanged (ADR-076, ADR-077): a `[lang.<id>]` pin (`runner = "plugin.my-runner"` for `TestResults`), else detected producers in registration order, the first `Ready` one whose needs can be met. A plugin is never a joint producer (ADR-084); where the fact store would choose a plugin, no joint run stands in for it. The support matrix, `describe matrix`/`fact`/`language`/`<check>`, the budget scheduler's costs and history (ADR-086), and `--dry-run` see plugins through the registries, with no special case.
8. **Kinds.** A producer plugin may provide only a kind whose payload type exists (`schema::fact_version` is `Some`), at that version; others are refused at discovery. Each kind maps to its typed adapter through one table in `cupel-plugin`, so adding a payload type adds one row.

## Consequences

- Installing `cupel-check-foo` on `PATH` adds `foo`'s check to every run in every repository, which is the design's intent; a broken one stops runs with a message that names it and `--no-path-plugins`.
- A plugin can fill a gap the matrix shows (`unsupported`), or stand in for a native producer whose tool is missing, without a pin; it cannot displace a working native producer without one, except for `TestResults` where the pin key exists. Pins for other kinds wait on `FactKind::pin_key` growing (ADR-076).
- Every invocation pays one `describe` process per plugin (milliseconds for a compiled plugin; tens of milliseconds for an interpreter). The daemon does not cache manifests; it could later, keyed by the executable's size and modification time as it keys builds (ADR-085 §4).
- The in-process CLI tests and the golden harness see no `PATH` plugins unless a test adds them.
