# CUPEL_DECISION_121: `serve --mcp`: a hand-written MCP 2025-11-25 server on stdio whose tools are the verbs' cold runs

**Date:** 2026-10-17 · **Status:** accepted · **Phase:** P7.7

## Context

Design §6.5 gives `serve` an `--mcp` switch that "exposes verbs as MCP tools with the same envelope", and §8.10 names the tools (`check`, `survey`, `explain`, `tests_impacted`, `describe`), "the envelope as the result and events as progress notifications". ADR-085 built the socket daemon, left `--mcp` refused as pending, and said only that it would be "one more transport over the same handler" in `cupel-serve`. Neither says which MCP revision is spoken or with what implementation, how the MCP server and the socket daemon relate, what a tool's input is and where its schema comes from, how a call's result, failure, events, and standard error map onto MCP, how a call is cancelled, what happens to the `serve` verb's own envelope when stdout is the protocol, or how parity with the CLI is proved.

The Model Context Protocol has two eras. Revisions up to `2025-11-25` open a session with an `initialize` handshake; the current revision, `2026-07-28`, is stateless: every request carries its version in `_meta`, `server/discover` replaces the handshake, and a "dual-era" client probes with `server/discover` on stdio and falls back to `initialize` on any error that is not a recognized modern one.

## Options

**Implementation.** (a) The official Rust SDK, `rmcp` (3.4.1 is the latest release, and knows both eras): it tracks the specification, but it is async throughout (its dependencies include `tokio`, `tokio-util`, `futures`, `tracing`, `pin-project-lite`, and `async-trait` for the server macros), and Cupel has no async runtime: the daemon is threads and `poll` (ADR-085), and ADR-086 §11 decided against adding `tokio`. Every call runs the synchronous cold path for seconds to minutes, so it would block a runtime worker or need `spawn_blocking` around all of it; the protocol subset Cupel needs (five requests, two notifications in, three out) is a few hundred lines. (b) JSON-RPC 2.0 over stdio by hand with `serde_json`, threads like the daemon, reusing the daemon protocol's line reader: no new dependency and nothing async; Cupel then owns protocol conformance, pinned by its own tests. Chosen: (b).

**Revision.** (a) `2026-07-28` only: today's legacy clients, which have no fall-forward, could not connect at all. (b) `2025-11-25` (and `2025-06-18`, the first with `structuredContent`; the subset Cupel uses is the same in both): every legacy client connects, and a dual-era client's `server/discover` probe gets "method not found", which its fallback treats as a legacy server. (c) Both eras in one process: per-request `_meta` versioning and `server/discover` beside the handshake, before a modern-only client needs it. Chosen: (b); (c) is a later, additive step.

**Process.** (a) The MCP server forwards each call to the socket daemon: two processes to start, and calls fail when the daemon is absent or another build. (b) The MCP server is itself the long-lived process: it holds its own `Session` (the warm parse cache of ADR-085 §3) and runs every call in-process through the same `run` a cold process calls; it claims no socket, so a socket daemon for the same repository runs beside it, and the CLI never auto-connects to it. (c) One process serving both the socket and stdio: one cache for both, but a lifetime (stdin closing versus `serve --stop`) and a flag set that serve two masters. Chosen: (b). `--mcp` conflicts with `--socket` and `--stop`; `--watch` works as for the daemon.

**Input schemas.** (a) Written once per tool by hand: a second description of every flag that drifts from the CLI. (b) Derived from clap's `Command`: types, but none of the registry's text. (c) Derived from the registry's `CommandDescription` (`cupel describe <verb>`), which a unit test already holds equal to clap's tree (ADR-018): one source for flags, help, `describe`, and the tools. Chosen: (c).

**A call's command line.** The tool's arguments must become the very command line a cold run would take, or the envelope's `repro` and `suppress` strings, which quote the command line, differ. JSON objects are unordered and `serde_json`'s map sorts its keys, so (a) building flags in the schema's order gives a command line that is stable but not the one the client meant, while (b) reading the arguments in the order the client wrote them (a `Visitor` over the request's own text) gives the command line the client spelled. Chosen: (b), with `--format json` appended unless the arguments spell it.

**Results and errors.** (a) Every non-zero exit as a JSON-RPC error: an agent would lose the envelope exactly when it most needs it, and a failed gate is a result. (b) Every run, whatever its exit, as a result carrying the envelope; `isError` marks the runs the design's exit codes call errors (§6.6: 2 usage, 3 environment, 4 unevaluable, 6 internal), not 1 (gate failed) or 5 (partial). Arguments that cannot form a command line become a usage envelope (exit 2) too, so the model can correct itself from the envelope's `fix`; only an unknown tool, a missing name, or arguments that are not an object are protocol errors (`-32602`), as the specification asks. Chosen: (b).

## Decision

1. **Transport** (`cupel_serve::mcp`, in the crate ADR-085 reserved for it; it names no verb). JSON-RPC 2.0 over stdin and stdout, one message per line, at most `MAX_MESSAGE` bytes (ADR-009). `initialize` answers the client's `protocolVersion` when it is `2025-11-25` or `2025-06-18`, else `2025-11-25`, with capabilities `{tools: {}, logging: {}}` and `serverInfo {name: "cupel", version}`. Also answered: `ping`, `tools/list` (one page), `tools/call`, `logging/setLevel`. Any other method is `-32601`; a line that is not JSON is `-32700` and one that is not an object `-32600`, both with a null `id`. Notifications other than `notifications/cancelled`, and responses from the client, are ignored; requests are served before `initialize` too.
2. **Concurrency.** The reader is its own thread; each `tools/call` runs on its own thread, so `ping` and cancellation are answered during a run, and messages are written whole under one lock.
3. **Tools** (`cupel-cli/src/mcp.rs`): `check`, `survey`, `explain`, `tests_impacted` (`tests --impacted`, the switch implied), and `describe`, in that order. Each tool's input schema (2020-12, `additionalProperties: false`) has one property per argument of its verb and per global flag, named without dashes (`--no-gate` is `no_gate`; the positional `TARGET` is `target`, marked `x-cupel-positional`, and required when the verb requires it); switches are booleans, integers non-negative integers, enums strings with their values, repeated arguments arrays. Withheld: `--no-color`, `--events`, `--describe`, `--help`, `--jobs` (a process sizes its thread pool once, ADR-086 §11, so the server's first call would fix it for all), the implied `--impacted`, and arguments still pending a plan step. `format` takes only `json`. Titles are `cupel <command>`; descriptions are the registry's summary and a sentence on the envelope. No `outputSchema`.
4. **Calls.** The arguments, in the client's order, become the command line: the command words, positionals, flags as given (a true switch is its flag, false or null nothing, an array its values after one flag), then `--format json` unless given. That command line runs through `run` with the server's session, in the server's root, as a cold process started there would: stdout not a terminal, the server's `CUPEL_*` variables, `NO_COLOR`, and `PATH`. An argument outside the schema or of another type (an enum value outside its values included) is a usage envelope (`cli.usage`, exit 2) naming the property, with the valid names or values.
5. **Results.** The envelope document is the result's text content and, as an object, its `structuredContent`; `isError` is true for exit 2, 3, 4, and 6; `_meta["cupel.dev/command"]` is the command line run (after the program name).
6. **Events and stderr.** An invocation's `Environment` gains `events`, where events go when no `--events` is given; a call sets it to its progress stream. With a `progressToken` in the request's `_meta`, each event line is a `notifications/progress` with that token, `progress` counting 1, 2, 3, …, no `total`, `message` the event's JSON line, and the event itself under `_meta["cupel.dev/event"]`; without a token, events go nowhere. Each line the run writes to stderr is a `notifications/message` (`level: info`, `logger: cupel`, `data` the line), sent unless `logging/setLevel` asked for a level above `info`.
7. **Cancellation and lifetime.** `notifications/cancelled` cancels that call's token (its run ends `partial`, as a client hanging up on the daemon ends a run) and the call gets no response. The server ends when stdin ends or the invocation's token fires (`--timeout`); calls in flight are cancelled and, unless cancelled by the client, answered before it exits. Its envelope reports `serve.mcp-stopped` (info, `evidence.requests`: the calls answered).
8. **Stdout.** Under `--mcp`, stdout carries only protocol messages: `Environment` gains `stdin` (taken once; empty but for a process) and `stdout` (the protocol's destination), and the `serve --mcp` envelope is appended to stderr instead of printed. `serve --mcp` prints `cupel: serving <root> over MCP on stdio (pid N[, watching])` to stderr unless `--quiet`.
9. **Parity proof.** With `MCP_PARITY=1`, the golden harness (`cupel_fixtures::run_cupel`) also runs each invocation of a verb a tool serves as that tool's call: it copies the directory before the cold run, starts `cupel serve --mcp --quiet` on the copy, turns the command line into arguments through the tool's listed schema, warms the server with the same call plus `dry_run`, calls it, and requires the envelope's exit code, the redacted envelope, and the logged stderr to equal the cold run's. A command line the tool's own cannot equal (a flag no tool takes, `--format text`, no `--format` at all) is not compared. `make parity` sets `DAEMON_PARITY=1 MCP_PARITY=1`.

## Consequences

- The tools follow the CLI by construction: a flag added to a verb's registry entry is a tool property, and a check added to the catalog needs nothing here (no check list exists in the MCP code). The README's tool table is generated from the server's own `tools/list` (`make readme`).
- A tool's envelope equals `cupel <command> --format json` byte for byte after redaction, including `repro`; the cost is that argument order is meaningful, which JSON clients rarely expect but which changes only the quoted command lines.
- Modern-only (`2026-07-28`) clients cannot connect until the server answers `server/discover` and per-request `_meta` versions; that, `outputSchema` (the run schema, `cupel describe schema run`, would need trimming to a tool-sized document), `resources` for the run records, and `--jobs` per call are open.
- Cupel owns its MCP conformance: `crates/cupel-serve/tests/mcp.rs` pins the handshake, errors, notifications, and cancellation, and `crates/cupel-cli/tests/mcp.rs` the tools over the real binary. A revision that changes the subset used is a change to one module.
- An MCP server and a socket daemon for one repository keep separate caches; the store's writer lock orders their writes as it does two cold processes' (ADR-045).
