# CUPEL_DECISION_086: The budget scheduler: task cost from the store's history, task value, the knapsack with dependency closure, and `--jobs`

**Date:** 2026-10-16 · **Status:** accepted · **Phase:** P4.3

## Context

`--budget DURATION` has parsed since P0.3 and been ignored since (P3 follow-up (9)). Design §9.6 gives the rule in one line: value per task `tier_weight[tier] × novelty × (changed ? 2 : 1)`, cost from history (p50 of the last 10 runs of that task shape, else the manifest class default), greedy by value per cost with dependency closure, skipped tasks reported with reason `budget` and an `est_ms`. §8.9 adds `--jobs` (CPU-bound work on rayon, process-spawning work on tokio, default cores) and §6.6 maps "timeout or budget hit" to exit 5. The P4 Definition of Done adds that `--budget` never exceeds its wall clock by more than one task's timeout.

None of them says what a task and its shape are, which durations are recorded and where, what `tier_weight` and `novelty` are, what the closure of a check is now that producers have wants and joint runs (ADR-080, ADR-083, ADR-084), when the clock starts, what happens to a task that is running when the budget ends, how `--budget` relates to `--depth`, how a skipped task's `est_ms` appears in an envelope whose key set is fixed (ADR-013), or how a cap on concurrency reaches a scheduler that runs one task at a time.

## Options

**Tasks.** (a) Checks only, each costed with what its facts cost: two checks sharing a coverage run would each pay for it, so the knapsack would refuse the second for a cost already paid. (b) Checks and the producer runs they reach, as nodes of the fact DAG (§8.9 step 3): a check's *closure* is the producer runs it needs that are not yet made; taking a check takes its closure, and a closure member already taken costs nothing again.

**Shape.** The design's "task shape" groups runs whose durations predict each other. (a) The task alone: a check over three symbols and over three thousand would share a p50. (b) Check × language × the order of magnitude of its targets, and producer × language × whether it would run or read a cache: a cached coverage report and a coverage run differ by minutes, and the producer's own `estimate` (ADR-083) already says which it would do.

**Where durations live.** (a) Derive them from stored envelopes (`checks.json` holds `duration_ms`): a check's `duration_ms` includes the facts it waited for and combines its languages, and producers' durations are recorded nowhere. (b) A table of measured durations per run, filled from what the scheduler timed, exclusive of upstream work.

**Novelty.** The design's prose: "novelty prefers survivors from the last run and symbols never scored". Survivors are the mutation engine's own ordering (ADR-080 §11), inside a task. Between tasks, the store can tell whether a check was ever scored here and whether its last result was made at exactly this state of the tree.

**A running task at the deadline.** (a) Let it finish: a mutation run started with a minute left would overrun by its whole length. (b) Cut it with the existing cancellation (`Cancellation::child` with the budget's deadline), which kills a running process and its group within one polling interval (ADR-020 §5).

**`--budget` and `--depth`.** "Overrides depth" (§5.8) could mean that a budget selects among every check up to `exhaustive`. Depth also decides producers' plans (the mutation engine mutates every touched file at `deep`, ADR-080 §5) and which wants are made (ADR-083 §4), which no estimate can price before a run of that depth was recorded. Or the budget can bound the depth's own selection.

**`est_ms` on a skipped check.** (a) An optional property, absent unless set, as `notes` is (ADR-079): a second exception to the fixed key set. (b) A nullable property on `Skipped`, null except for `budget`: every skipped object gains one key.

**`--jobs`.** The scheduler runs one task at a time (ADR-041); concurrency lives inside producers: rayon in the language producers, the mutation engine's slots (ADR-080 §8), the per-test exports (ADR-083 §1), and the runners' own workers. (a) Add a tokio runtime with `--jobs` permits around task execution: tasks would still run one at a time, so the permits would cap nothing. (b) Cap the concurrency where it is: rayon's pool, and the process-spawning producers' worker counts.

## Decision

1. **Tasks and shapes.** A *check task* is a (check, language) the support matrix allows (a family-wide check's task covers its siblings, ADR-051). A *producer task* is one producer run for one language: the producer the fact store would choose for a fact (first ready candidate after pins and detection, ADR-076) or the joint run that would make it (ADR-084). A check task's *closure* is the producer tasks for every fact it reaches (`Deciding::reached`: its needs and wants, through producers' needs and affordable wants) that is not already made. Shapes (`cupel_core::TaskShape`): `check` × check ID × language × size class, where the size class is `0` for no target and `1 + ⌊log₁₀ targets⌋` otherwise; `producer` × producer (or joint) ID × language × `run` | `cached` (the producer's estimate note is `cached`, ADR-083).
2. **Durations recorded.** The scheduler times each successful production (`produce` alone, after its needs and wants were made) and each check run that finished (`Check::run` alone, after its facts were made), never a failed, cancelled, or skipped one, and returns them in `Outcome::durations`; the CLI stores them with the run record (`durations` table, store migration 4: run, kind, task, language, class, milliseconds). The base side of a range (ADR-056) is not timed. `CheckResult.duration_ms` keeps its meaning (the check's wall time, facts included).
3. **Cost.** A shape's cost is the p50 (the lower median) of its last 10 recorded durations when at least 3 are recorded (`MIN_RUNS`; one or two runs are mostly a cold build or a cold cache), else the default: for a check, its plan's `est_ms` (cost class × targets, ADR-041); for a producer, its estimate's cost class per production — `quick` 100 ms, `standard` 30 s, `deep` 5 min, `exhaustive` 50 min — and a `cached` estimate costs what `quick` does.
4. **Value.** `tier_weight × novelty × (changed ? 2 : 1)` with `tier_weight = tier + 1` (1 for a structural metric … 7 for a proof). Novelty is per check, from the store: **2** when the check has no stored result that ran (never scored here); **½** when its latest ran result was made at the current `HEAD` with a clean tree, and the tree is still clean (its findings would repeat); **1** otherwise. `changed` holds for a task when the scope is a range and the task has symbols in scope.
5. **Knapsack** (`cupel_core::budget::choose`, pure). The budget left is the deadline less now when planning ends. Repeatedly take the check task with the highest value per marginal cost (its own cost plus its closure's producer tasks not yet taken) whose marginal cost fits what is left; ties go to the lower BLAKE3 of the run's seed, the check ID, and the language, so a run is reproducible with `--seed`. Stop when nothing fits. Every task not taken is skipped with reason `budget` and `est_ms` its marginal cost when the knapsack stopped. A check is never run without its closure: the closure is in its cost, and the baseline (ADR-076 §5) runs only for the languages the taken tasks reach.
6. **The wall clock.** The budget is wall clock from the invocation's start, as `--timeout` is (`run.budget_ms` already echoes it). Under a budget, every check and production runs under a child of the run's cancellation whose deadline is the budget's. Before a check task starts, its own cost plus its closure's not yet made must fit what is left, else it is skipped with reason `budget` (a task the knapsack took can still be skipped when an earlier one ran longer than estimated). A task running at the deadline is cut by the cancellation: running processes are killed with their group within one polling interval, and the check reports `partial`. So the run ends within the budget plus the time the running task takes to notice the cancellation and stop, which is bounded by that task's timeout (the P4 DoD) and in practice is milliseconds plus the kill. `--timeout` still applies on its own and still skips with reason `timeout`.
7. **Status.** A budget skip or a budget cut makes the run `partial`, exit 5 (§6.6): the envelope is valid and some selected work was not done. `next_actions` already reruns a `budget` skip with `--only <check>` (ADR-061).
8. **`--budget` bounds the depth's selection** and does not widen it: the checks the depth, `--only`, `--skip`, and `--tier` select are the knapsack's candidates, at that depth's plans. Widening to deeper checks under a large budget waits for recorded `deep` runs to price them.
9. **Order.** Without a budget nothing changes: checks run in registry order. Under a budget, checks run in the order the knapsack took them (each check at its first taken task), so the most valuable work per millisecond runs first; the envelope keeps registry order. Inside a task, work keeps its own order: the mutation engine runs last run's survivors and never-scored symbols first (ADR-080 §11). The engine produces its fact only when it finishes, so a mutation run cut by the budget reports `partial` with no score rather than a score over the mutants it reached.
10. **Envelope and plan.** `Skipped` gains `est_ms: u64 | null`, set for `budget`. A check every language skipped for budget carries the sum of its languages' `est_ms`. `--dry-run` plans the same knapsack: `would_skip` lists budget skips with `reason: budget` and `est_ms`, and every planned check's `est_ms` is its own cost plus the closure it brings in planning order, so `est_total_ms` (and the `plan` event's `est_ms`, in a real run too) counts each producer run once, honestly, whether or not a budget is set.
11. **`--jobs N`** (positive integer; default: the cores, as before) caps concurrency where it exists: the CLI builds rayon's global pool with `N` threads before the walk (CPU-bound parsing, hashing, and per-file language production), and `Focus::jobs` hands `N` to producers, so the mutation engine runs at most `N` slots at once (with `[lang.<id>] mutation.jobs`, the smaller wins) and the per-test exports use at most `N` threads (`Focus::workers`). No tokio runtime is added: the scheduler runs one task at a time, and a runtime's permits would cap nothing that the producers' own worker counts do not. Runners keep their own parallelism (a baseline is the suite as the user runs it, ADR-076).

## Consequences

- The first runs in a repository are planned from cost classes; three recorded runs of a shape replace the default with what this machine measured. A producer whose cost depends on what changed (the mutation engine, whose reused mutants cost nothing) is estimated from its recent runs whatever they reused; its p50 can be low after a run of reuses.
- `--budget 1s` on a fixture with a test suite skips every check that reaches `TestResults` and runs the static checks; the plan says so with each skipped check's `est_ms`, and the agent can rerun with more time.
- The store grows one row per production and check per run; nothing prunes it, as nothing prunes `runs`.
- Every envelope's skipped objects gain `"est_ms": null`; goldens changed by that key only. Dry runs' `est_ms` and `est_total_ms` now include producer runs.
- A mutation run cut by the budget loses its completed mutants for that run (they are not stored); making the engine return a partial fact needs an outcome for "not run" and a payload version, left as an open item.
- `--jobs` in a long-lived process (the daemon, P4.2) cannot rebuild rayon's global pool per request; it would need a pool per request. Runners' own parallelism is not capped by `--jobs`.
