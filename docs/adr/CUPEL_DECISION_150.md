# CUPEL_DECISION_150: The mutation engine's phase breakdown

**Date:** 2026-10-28 · **Status:** accepted; §6 (seeding) withdrawn by §8 · **Phase:** P10.2

## Context

On a one-function change in Cupel's own repository at `standard`, the mutation engine takes 285 s for 2 mutants and 412 s for 3 (plan, P4 Notes "P4 — Definition of Done, remeasured"); on a quiet machine, 311 s for 2: "141 s each in parallel slots, the remaining ~170 s the slots' sync with the tree, their schemata builds, and validation" (P3 Notes "P3.6 — measurement on a quiet machine"). Those remainders are inferred from wall clocks, not measured: the store's `durations` table (ADR-086 §2) holds one row per production, `engine.mutation`, and `MutationOutcomes` holds one `duration_ms` per mutant, the test run alone. Nothing records what the slots' sync costs, what the schemata validation costs (its compile and its test run together, ADR-082 §5), how many tests a mutant's selection narrowed to, or what planning and the store's history cost. P10.2's ruling (plan, P10) is to instrument one mutant end to end, confirm schemata and per-test selection on Cupel's own workspace, and fix what dominates; the breakdown is the evidence the rest of the step stands on, so it is decided first.

## Options

**Where the breakdown lives.** (a) Only in the store's `durations` table, as rows the scheduler records: the scheduler times productions as a whole and knows no producer's phases, so each producer would need a channel into the scheduler (`ProduceCtx`) for sub-durations, a mechanism for one producer. (b) In the fact: `MutationOutcomes` carries the phases the production went through, as it already carries each mutant's run time; the CLI, which already indexes the fact's mutants into the store (`record_mutants`, ADR-080 §10), records the phase sums beside the production's duration. The fact is what `--format json` consumers and the goldens see; the table is what `scripts/inner_loop.sh` and the budget's history read. (c) Per mutant only, as fields on `Mutant`: the sync and the validation are not a mutant's; they are a slot's or a file's, shared by every mutant of the file, so per-mutant fields would either repeat them or apportion them.

**How fine.** (a) Per phase totals: five numbers, no way to see that a validation ran in every slot or that one slot's sync was the slow one. (b) One row per phase occurrence, with the file and slot it served and the tests it ran: a timeline of the production, from which totals, maxima, and parallelism are read.

**What the check shows.** (a) Nothing: the fact is not in the envelope, so `cupel check --format json` and `cupel explain tests.mutation` would show no phase. (b) Metrics: `tests.mutation` reports each phase's total as `<phase>_ms`, so the envelope, `explain`, and the gate keys carry them; the goldens redact every `*_ms` metric as they redact `duration_ms`.

## Decision

1. **The fact.** `MutationOutcomes` gains `phases: Vec<PhaseDuration>` (optional, absent from JSON when empty, so the fact's version stays 2 as `excluded` left it, ADR-147 §4): one row per phase the production went through, in the order they ended:

   ```text
   PhaseDuration {
     phase: plan | sync | rewrite | build | run,
     file: Option<String>,      // the file whose mutants the phase served; null for plan and sync
     slot: Option<u32>,         // the slot it ran in; null for plan and rewrite
     tests: Option<u32>,        // the tests the phase ran, when it ran tests; null for the whole suite
     duration_ms: u64,
   }
   ```

   `plan` is the plan of the mutants in focus, their coverage gating and per-test selection, and the store's history (ADR-080 §5–7, §10–11), once per production. `sync` is one slot's reconciliation with the tree (ADR-080 §8), once per slot used. `rewrite` is one file's schemata rewrite (ADR-082 §2), once per attempt. `build` is the run every mutant of a file shares: the schemata validation (ADR-082 §5: the build and the file's selected tests with no mutant) or a file copy's reference run (ADR-080 §9: the rebuild and the same tests), once per slot the file used, with `tests` the file's selection (`null` when it is the whole suite). `run` is one mutant's test run, its `duration_ms` equal to the mutant's, so the phases alone are the production's timeline. A production that runs no mutant has no phases. A wrapped engine (PIT, ADR-110) records none.
2. **The store.** When a run is recorded, each language's `MutationOutcomes` adds one `durations` row per phase present, kind `producer`, task `<engine>.<phase>` (`engine.mutation.build`), class `run`, with the phase's total over its rows; beside the production's own `engine.mutation` row the scheduler records. The budget's cost model (ADR-086) reads shapes by name and never asks for these.
3. **The check.** `tests.mutation` reports `plan_ms`, `sync_ms`, `rewrite_ms`, `build_ms`, and `run_ms`, each the total of that phase over the outcomes in scope; 0 when the phase did not occur. The goldens redact every metric named `*_ms` as `<duration-ms>`, so a fixture's run time never fixes a golden.
4. **The engine** records the phases as it goes (`Phases`, a recorder the production's workers share), and nothing else about how it runs changes under this section. What the breakdown showed on Cupel's own workspace, and what changed because of it, follows in the sections below.
5. **What the breakdown showed** (2026-10-29, the release binary at 71879de, a fresh clone, `cupel check --base HEAD~1 --only tests.mutation --depth standard --no-gate --jobs 4`, no daemon, AC power, load 55 at the start; the cold P10 change, a comment inside `metrics::symbol_coverage`). Wall 2 559 s: the instrumented suite run 1 689 s, the engine 868 s for 3 mutants, all `schemata`, all killed. Phases: `plan` 0.2 s; `sync` 3.7 s over 3 slots; `rewrite` under 1 ms; **`build` 2 506 s over 3 slots, about 835 s each, in parallel**; `run` 66 s, 21–23 s per mutant. Schemata engages on `cupel-checks` (one rewrite of `metrics.rs`, every mutant switched by `CUPEL_MUTANT`), and per-test selection narrows each mutant to 28 of the suite's 2 776 tests, the longest of them `cupel-cli::survey a_standard_survey_protects_the_untested_function_before_simplifying_the_complex_one` (28.8 s in the baseline), which bounds a mutant's run. Each slot's `target` held **14 GB**: the slots of one measurement took 42 GB, more than the clone's own build (16 GB), and left too little free space for the warm run, which `scripts/heavy.sh` refused at 32 GB free. The cold engine is three identical builds of the workspace, each held by ADR-148 §1 to `cores / slots` (2 of 8) jobs, and each costing a full `target` on disk.

## Options (the slots' first build)

(a) **Build only the covering tests' binaries** (`-p <crate> --test <name>` for each selected nextest binary ID instead of `--workspace`): fewer test binaries to build and link, cold and warm. But Cupel's fixture tests spawn `cupel` through `assert_cmd::cargo_bin`, which a build of `cupel-fixtures`' test binaries alone does not rebuild, so the slot would run a stale binary against every mutant and report false survivors; which tests spawn which binaries is P10.3's question. Not here.
(b) **One shared `target` for every slot**: one build and one copy on disk, but cargo names a path package's artifacts by its path relative to the workspace, so slots sharing a directory would run each other's mutants (ADR-080 §8), and cargo's own lock would serialize their builds anyway.
(c) **Seed a slot with no build of its own from one that has one**: the first slot of a file's schemata builds alone, with the whole machine's cores and memory budget (nothing else of the production runs meanwhile, so ADR-148's bounds on the slots together hold), and every other slot with no build directory of its own gets a copy of it, a clone on APFS (`std::fs::copy` is `clonefile` there), before its own validation, which then rebuilds incrementally only what differs: the crates whose compile-time environment names the slot's path (`env!("CARGO_MANIFEST_DIR")`, which cargo tracks per crate) and nothing else, since the artifact names do not depend on where the workspace is. One full build instead of `slots`, with four times the jobs; clones share their blocks until cargo writes over them. Where the filesystem cannot clone (ext4), the copy costs the disk a build would, and still less time.

## Decision (continued)

6. **Slots are seeded** (option c). Before a file's schemata validation, when some slot it uses has none of the runner's build directories (`Runner::outputs`) at its root and another has them or none has: if none has, the first slot validates alone first, with `parallelism` set to every core and the whole memory budget; then each slot without a build directory gets a copy of the first slot's (each regular file copied, a clone on APFS; links kept as links), recorded as a `seed` phase (`slot` the seeded slot, `file` the file whose validation needed it), and the remaining slots validate in parallel as before. A slot that already has a build directory, from an earlier production, is never seeded: its incremental build is the cheaper one. `MutationPhase` gains `seed` (additive; the fact's version stays 2) and `tests.mutation` the metric `seed_ms`. ADR-148 §1 is refined: the runs of a production share the cores, and a run that runs alone has them all.

7. **What seeding changed** (2026-10-29, the release binary at 2d36b8f, otherwise as §5; load 37 at the start). The cold check took 1 921 s (its wall, 4 718 s, includes waiting on the heavy lock): the suite run 1 158 s, the engine 762 s for the same 3 mutants, all `schemata`, all killed. Phases: `plan` 0.2 s; `sync` 3.0 s; `seed` 30 s over 2 slots (15 s each); **`build` 1 195 s over 3 slots**, against 2 506 s; `run` 57 s, 16–21 s per mutant. The build CPU the slots spend fell by half and the engine's cold wall by 106 s (12%), but the seeded slots did not reuse what they were given: their builds took about 470 s each against about 260 s for the first slot's alone (solving the engine's wall and the build total for the two), and each seeded `target` grew to 17 GB against the first slot's 13 GB, so cargo rewrote most of the copy rather than building incrementally on it, and the copies did not stay shared on disk: one cold measurement took the volume from 71 GB free to 3.5 GB. Why cargo rebuilds a copied `target` at another path is not diagnosed (candidates: crates whose compile-time environment holds the workspace path, and everything that depends on them).


## Options (one build for every slot)

Under schemata every slot builds the same program and the mutant is chosen at run time (ADR-082 §3), so the slots' builds are one build made `slots` times. Why seeding (§6) rebuilt the copies: cargo's fingerprint of a path dependency includes its absolute path, so a `target` moved to another workspace path rebuilds every member, which is what §7 measured (17 GB and ~470 s per seeded slot). Sharing one build makes that question moot.
(a) **Run every slot's mutants in one tree**, each its own `cargo nextest run` with its own `CUPEL_MUTANT`: no new runner capability, but each run invokes cargo, whose build lock serializes their fingerprint checks, the runs share one JUnit report path, and two mutants' runs of the same test write the same files in one working copy.
(b) **Build once, run the built binaries from every slot**: the runner builds the suite in one slot and records what it built; every run then executes those binaries without cargo, in its own slot as its working copy. nextest does this itself (reusing builds): `cargo nextest list --list-type binaries-only --message-format json` builds the test binaries and writes their record, `cargo metadata` the workspace's, and `cargo nextest run --binaries-metadata … --cargo-metadata … --workspace-remap <slot>` runs them with the slot as the working directory and runtime `CARGO_MANIFEST_DIR`, its JUnit report in the slot's own `target/nextest`, compiling nothing (probed with nextest 0.9.148: no `Compiling` line, the report in the remapped workspace, `CUPEL_MUTANT` passed through). A reuse run refuses cargo's build options (`--workspace`, `--build-jobs`). Compile-time paths (`env!("CARGO_MANIFEST_DIR")`, `CARGO_BIN_EXE_*`) and `assert_cmd::cargo_bin`, which finds `cupel` beside the running test binary, point at the build slot: tests that spawn `cupel` run the schemata `cupel` of the same build, as the full workspace build makes it, and tests that read fixtures through compile-time paths read the build slot's, which are the tree's unmutated files in every slot.

## Decision (continued)

8. **One build per schemata file** (option (b)); §6's seeding is withdrawn. `Runner` gains `build(ctx, options) -> Result<Option<BuildOutcome>>` (default `None`: the runner always builds in the tree it runs in) and `RunOptions` gains `prebuilt: Option<Prebuilt>`, the runner's record of a build that a run in another copy of the tree runs from instead of building. `cargo-nextest` is the runner that has it, per project root: its record is the two files above, in the build slot's `.cupel/cache`. Before a file's mutants, the engine writes the schemata source in the first slot and asks the runner to build there, alone, with every core and the whole memory budget (the `build` phase, `slot` 0, now the compile alone); a build that fails is the failed validation of ADR-082 §5, its output naming the culprit lines as before. Then the unmutated tests run once from that build in the first slot with a slot's share of the machine (a new phase, `validate`); green, its time sets every slot's timeout (`max(2 s, timeout_factor × validate)`, capped by ADR-147); then the gated mutants run in every slot from the build, each with its `CUPEL_MUTANT` and its slot as the working copy. A slot runs no cargo and keeps no build of its own. A file copy (an excluded gate, or every mutant of a file whose schemata does not build) runs in the first slot alone, after the file's gated mutants, timed by its own reference run as ADR-080 §9 says, so it rebuilds incrementally where the build is: run in another slot it would build the whole workspace there. `Runner::builds_once` says which runners these are. The first `make dogfood` of §8 ran the file copies of `go_test.rs` (whose sites sit inside a `static`) in all four slots, three of them building the workspace from nothing at once beside the first's build; that slot's reference failed a test it passes alone, and its `target` was left without two build scripts' outputs (cause not established beyond that concurrency). A runner without `build` (cargo-test, every other language's) validates in every slot in parallel as before §6. `MutationPhase` gains `validate` and loses `seed`; `tests.mutation` reports `validate_ms` and no `seed_ms`.

9. **What one build changed** (2026-10-30, `make inner-loop LABEL=p10-2-after`: the release binary at 124bb76, `main` at 97a1f62 with this decision, a fresh clone, `--jobs 4`, no daemon, through the heavy lock, AC power, nothing else building; against P10.3's after-row on 02343b4, the same script on the same change). Cold: 1 063 s wall (1 377 s before), the suite run 909 s (953 s), the engine **125 s (393 s)** for 3 mutants: `build` 103 s (one, in slot 0), `validate` 10.7 s, `run` 28.4 s (9.5 s per mutant, 3 slots in parallel), `sync` 1.3 s. Warm: **342 s wall (392 s)**, the suite run 268 s (262 s), the engine **60 s (118 s)**: `build` 41 s (incremental, one), `validate` 9.4 s, `run` 12.4 s for the 2 mutants run (6.1–6.3 s each), 3 reused. Unchanged: 5 s. Every mutant `schemata`, killed, 28 tests. Slots 1–3 held 31 MB each (14 GB before), slot 0 the one 15 GB build. After the build a mutant costs 6–10 s on this change, within P10.2's 15 s.

## Consequences

- The timeline of a mutation production is in its fact and its totals in the store, so `scripts/inner_loop.sh`'s durations query lists `engine.mutation.sync`, `.build`, and `.run` beside the suite run and the engine, and a measurement names the phase that dominates instead of inferring it.
- A deep run with thousands of mutants carries thousands of `run` rows that repeat each mutant's `duration_ms`; accepted for a uniform table (a row is five small fields).
- Five metrics join `tests.mutation`'s `describe` output and the README's generated check table; nothing gates on them.
- One build per schemata file (§8) replaces `slots` builds, cold and warm, and the slots' `target` directories hold only nextest's reports. Building only the binaries the covering tests need (the first option above) stays out of P10.2: it needs P10.3's record of which tests spawn which binaries.
- After the build, a mutant costs its run: 16–23 s on the P10 change for its 28 covering tests, bounded by one `cupel-cli::survey` test that runs the binary (15–29 s in the baseline). That test is an open item, not the engine's.
- Tests run from the build slot's compile-time paths in every slot; a test that writes into its own crate through `env!("CARGO_MANIFEST_DIR")` would write the build slot's tree from every slot at once, as it already does under nextest's own parallelism in one tree.
