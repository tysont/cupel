# CUPEL_DECISION_124: Release archives built by `make dist`, Linux musl through cargo-zigbuild, published from a tag

**Date:** 2026-10-18 · **Status:** accepted; the Windows build amended by [137](CUPEL_DECISION_137.md) · **Phase:** P8.1

## Context

Design §10 names the platforms (Linux x86_64 and aarch64 as static musl binaries, macOS arm64 and x86_64, Windows x86_64 native best-effort), says they are built "with `cargo-zigbuild`/`cross` in CI", and §10 and plan P8.1 say they ship as GitHub Releases on a tag. Neither says which builder serves which target, how an archive is laid out and named (the P8.2 installers download it), where the version comes from and how a tag is held to it, how symbols are stripped, or what a dry run looks like. The binary also carries C: SQLite through `rusqlite`, the seven tree-sitter grammar crates and the tree-sitter runtime, and BLAKE3's SIMD code, all compiled by `cc` build scripts, so whatever builds a target must be a C cross compiler for it as well. `rusqlite` was already declared with `bundled` (ADR-045), which compiles the SQLite amalgamation with the target's C compiler instead of linking a system library.

## Options

**Linux musl: cargo-zigbuild on one x86_64 runner.** `cargo zigbuild --target <triple>-unknown-linux-musl` uses `zig cc` as the C compiler and linker; zig ships musl and its headers for every architecture, so both targets build on `ubuntu-latest` with no Docker, no target sysroot, and no per-target image. The tools are one tarball (zig, checked by sha256) and one `cargo install --locked`. The same command runs on a developer's macOS or Linux machine, so `make dist` reproduces CI. The cost is zig's own `cc` quirks (it rejects some target spellings and lacks a few `compiler_rt` symbols, neither of which these crates hit) and that zig's version must be one cargo-zigbuild supports.

**Linux musl: `cross`.** `cross build --target …` runs cargo inside a per-target Docker image with a GCC cross toolchain. It is well trodden, but each target pulls its own image, the images pin their own C toolchains and musl versions independent of this repository, Docker must be running wherever it is reproduced, and the toolchain inside differs from the one a developer has. It gives nothing zigbuild does not for two musl targets.

**Linux musl: native runners.** `x86_64` on `ubuntu-latest` and `aarch64` on `ubuntu-24.04-arm`, each with `musl-tools` (`musl-gcc`). Each binary could then also be run where it was built. But `musl-gcc` is a wrapper around the host GCC and cannot cross-compile, so local reproduction of the other architecture is impossible, two runner types are needed, and the `cc`-built C must be told to use `musl-gcc` per target.

**macOS: native on `macos-latest` for both architectures.** The runner is arm64; Apple's clang and linker build x86_64 with `-arch x86_64`, which `cc` and rustc pass for `x86_64-apple-darwin`, so both targets are `cargo build --target` on one runner image, and the arm64 binary can be run there. zigbuild can target macOS too but needs the macOS SDK, which zig does not ship and whose licence restricts redistribution to Apple hardware; an Intel runner (`macos-13`) is being retired.

**Windows: native `x86_64-pc-windows-msvc` on `windows-latest`, or `x86_64-pc-windows-gnu` through zigbuild.** MSVC is the platform's own toolchain and what Windows users expect; the GNU target cross-builds from Linux but links against MinGW's runtime. Either way the code does not yet compile on Windows (see Consequences), so the choice only fixes which build is attempted.

**Stripping: `[profile.release] strip = true`, or a strip step per platform.** The profile setting makes rustc strip at link time on every target, including cross targets where the host `strip` does not understand the binary; a step would need `llvm-strip` or each platform's own `strip`. It also strips `make install`'s binary, which nothing needs symbols from.

**Archive layout.** A single top-level directory `cupel-<version>-<target>/` holding `cupel` (`cupel.exe`), `LICENSE`, and `README.md`, as `cupel-<version>-<target>.tar.gz` (`.zip` for Windows), against a flat archive. A directory keeps an extraction from scattering files into the current directory and names the version extracted; it is what ripgrep and most Rust CLIs ship, and what cargo-binstall's `bin-dir` template expects to be told.

**Publishing: `gh release create --generate-notes`, or a third-party release action.** `gh` is on every hosted runner and needs only `contents: write`; `softprops/action-gh-release` would be one more action to pin and trust with a write token.

## Decision

- **`scripts/release.sh`** holds the packaging logic CI and developers share, as subcommands: `version [TAG]` prints `[workspace.package] version` from `Cargo.toml` and, given a tag, fails unless it is `v<version>`; `package BINARY TARGET OUTDIR` writes the archive above (tar with `COPYFILE_DISABLE=1` so macOS adds no `._` entries; zip through `zip`, or `7z` where `zip` is absent, as on Windows); `sums DIR` writes `SHA256SUMS` (`sha256sum` or `shasum -a 256` format) over every archive in `DIR`; `verify ARCHIVE` fails unless the archive holds exactly the three files and, for a tarball, the binary is executable; `static BINARY` fails unless `file` calls it a statically linked (or static-pie) ELF executable.
- **`make dist [TARGET=<triple>]`** builds `cargo build --release --locked --package cupel-cli --target TARGET` (TARGET defaults to the host from `rustc -vV`), with `cargo zigbuild` instead for any `*-linux-musl` target, then packages and verifies `target/dist/cupel-<version>-<TARGET>.<ext>`. The target's standard library must be installed (`rustup target add`); the musl targets need `zig` and `cargo-zigbuild` on PATH.
- **`[profile.release] strip = true`** in the workspace `Cargo.toml`.
- **`.github/workflows/release.yml`**, on a `v*` tag push or `workflow_dispatch`: a `version` job (`release.sh version "$GITHUB_REF_NAME"` on a tag, so a tag that is not the crate version fails the run before anything builds); a `build` matrix running `make dist` per target: `x86_64-` and `aarch64-unknown-linux-musl` on `ubuntu-latest` with zig 0.16.0 (sha256-checked tarball) and cargo-zigbuild 0.23.4, then `release.sh static`; `aarch64-` and `x86_64-apple-darwin` on `macos-latest`; `x86_64-pc-windows-msvc` on `windows-latest` with `continue-on-error: true` and make 4.4.1 from Chocolatey. Where the runner can execute the binary (x86_64 Linux, arm64 macOS, Windows) it must print `cupel <version>`. Each archive is an artifact `dist-<target>`. A `release` job verifies every archive, writes `SHA256SUMS`, uploads all of it as `release-<version>`, and on a tag push only runs `gh release create <tag> --verify-tag --generate-notes`. A `workflow_dispatch` run is therefore the dry run: everything but the release. Actions are pinned by commit (`actions/checkout` v7.0.1, `actions/upload-artifact` v7.0.1, `actions/download-artifact` v8.0.1), and a test holds every `uses:` to a 40-character commit with its release beside it.
- **Version.** `cupel --version`, the envelope's `cupel.version`, the plugin request's `cupel`, and the daemon's build all come from `env!("CARGO_PKG_VERSION")`, which every crate inherits from `[workspace.package] version`; `release.sh version` reads the same line. The first release tag is `v0.1.0`, the current version.
- **SQLite and the grammars** need no change: `rusqlite`'s `bundled` and the grammars' `cc` builds compile with zig for musl and with the platform toolchain elsewhere.

## Consequences

- One command builds a release archive anywhere: `make dist` for the host, `make dist TARGET=x86_64-unknown-linux-musl` (or `aarch64-…`) from macOS or Linux with zig installed. Both musl archives, the x86_64 macOS archive, and the host's were built on an arm64 Mac; the musl binaries ran `--version`, `init`, and a quick survey (tree-sitter parsing, the SQLite store written) in `alpine:3.20` for both architectures. A release build takes two to four minutes per target.
- The P8.2 installers depend on the archive name, the top-level directory, and `SHA256SUMS`; changing any of them changes every installer.
- The aarch64 Linux binary is checked in CI only by `file` (static, aarch64); it is never executed there. The x86_64 macOS binary is not executed in CI either.
- musl's allocator is slower than glibc's under many threads, and Cupel parses with rayon; the musl binaries' speed against a glibc or macOS build was not measured. A faster allocator is a later change if `perf.bench` on the fixture tree shows a gap.
- **Windows, open items.** The Windows job is a release target like the others since [ADR-137](CUPEL_DECISION_137.md), which gives the daemon a named-pipe transport. Probing with `cargo zigbuild --target x86_64-pc-windows-gnu` (every dependency, including bundled SQLite, the grammars, BLAKE3, and `nix`, which compiles to nothing there, builds) shows `cupel-serve` is the only crate that does not compile, with seven errors: the daemon's socket is a Unix-domain socket (`std::os::unix::net`), it polls with `nix::poll` and `std::os::fd`, and it checks the socket file's owner and mode (`MetadataExt::ino`, `PermissionsExt::from_mode`). Making it build needs a Windows transport (a named pipe, or `AF_UNIX`, which Windows 10 supports but std does not expose) or a `cfg(unix)` daemon with `cupel serve` refusing on Windows. Past compilation: (1) producers that run user commands through `sh -c` (the coverage, differential-oracle, linearizability, and per-test coverage producers, `oracle verify`, and `--install`) need `sh` on PATH, as Git Bash or WSL provides, or a `cmd /C` path; (2) timeouts kill only the child, since process groups and `killpg` are Unix-only (`cupel-core/src/process.rs`), so a test runner's descendants outlive a timeout until a Job Object holds them; (3) paths in findings, `--changed` scopes, and goldens are `/`-separated and nothing tests `\` separators or drive letters; (4) overlays and the parity harness use symlinks, which Windows restricts, and plugin discovery has no executable bit to read (`not(unix)` branches exist for overlays and discovery but are untested); (5) the test suite itself uses Unix-only APIs (`cupel-cli/tests/support` sets file modes), and CI runs `make check` only on Linux and macOS. WSL runs the Linux musl binary and is the supported Windows route until these are done.
