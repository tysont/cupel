# P10.1 — Incremental coverage on a `--changed` scope

Branch `p10-incremental-coverage` (worktree `.claude/worktrees/p10-incremental-coverage`). Read `common.md` first (its "Measuring" section is the whole point of P10), then the plan's `#### P10.1` heading, ADR-083, ADR-084 (the suite joint, its cache, staleness by function), ADR-141 §2 (red suite runs uncached), and ADR-077 §5. ADR number: **149**. When P10.1 is merged, continue with P10.3 on the same branch name's successor (`p10-suite-attribution`, ADR **151**, its own brief).

## The owner's ruling

On a `--changed` (or `--base`) scope, run only the tests `tests --impacted` selects, under instrumentation, and merge their per-test coverage with the stored per-test coverage of every unselected test, keyed by the test's structural hash plus the hashes of the files that test covers. Invalidate per test, not per suite. A full instrumented run happens only when the store has no coverage baseline for the current toolchain, or at `--depth deep`. The envelope reports how many tests were rerun versus reused. ADR, fixture, golden.

## Where the time goes today

`tool.llvm-cov-nextest` (the Rust suite joint) reruns the whole workspace under instrumentation on any change under the root (ADR-084 §6: "Any change under the root reruns the suite"): 886 s of the 1 172 s a one-function change costs at `standard` with `tests.mutation` (P4 Notes "P4 — Definition of Done, remeasured"). The per-test cache already knows, per test, which lines of which files it executed and which tests a changed function makes stale (ADR-084 §7); the joint does not use that to run fewer tests.

## What to build

1. **ADR-149** before the code: the joint's *incremental* run. On a range scope with a cached suite entry for the root whose toolchain record matches (record the toolchain the entry was measured with: `rustc -vV`'s release and host for Rust, the interpreter version for Python; a different toolchain is no cache), the joint computes the stale tests by ADR-084 §7's rule *and* the owner's key: a test is stale when its own structural hash (its `Symbols`/`NormTree` hash, through `tests.scm`'s test cases) changed, when a file it covers changed inside a function it executed (§7), or when a file it owns changed (ADR-083); the file rule stands where §7 falls back. Record in the ADR that §7's function-level comparison is how "the hashes of the files that test covers" is read, and why (a file-level key would make every test of a shared module stale). The joint runs *only the stale tests and the new tests* under instrumentation (nextest `-E` with the kept tests excluded, as `tool.llvm-cov-per-test` already does for a refresh), takes their results and per-test coverage from that run, and *keeps* every other test's results and per-test coverage from the entry. The `CoverageMap` is merged: a kept test's lines, moved through the diff as §7 moves them, plus the measured tests' lines; a line is covered when any test executed it (every consumer reads only whether a line ran, ADR-084 §4; record the hit counts as the sum of the tests' counts where known, else 1). `TestResults` are the kept results plus the measured ones; a kept red test still refuses the run (exit 4) as a fresh red one does, since nothing that test depends on changed. A tree scope, `--depth deep`, no entry, a different toolchain, an incomplete entry, or a change the staleness rule cannot place (a new test file, a changed whole-suite file, a changed `Cargo.lock` or build script) runs the whole suite as today. Python (`tool.pytest-cov-contexts`) follows the same rule where pytest's `--deselect`/node IDs allow; Go's joint has no per-test map and is out of scope.
2. **The envelope.** `PerTestMap.measured`/`reused` already exist (ADR-083 §3); surface them per language in the run envelope's `tests` section (`tests.suite[lang] = { rerun, reused, mode: "incremental" | "full" | "cached" }`, names yours but stable) and in the text renderer's `run` block; `cupel describe schema run` and the JSON schema under `docs/schema` (or wherever `make readme`'s schema lives) must show the new fields. `tests --impacted` keeps reporting them as today.
3. **Fixture and golden.** A fixture repository under `crates/cupel-fixtures/repos/` (Rust, small, nextest, three or four tests of which one covers the changed function) with a two-commit history or a scripted change, and a golden for the incremental run: the check table, `tests.coverage` unchanged in value, `rerun 1`, `reused N`. The matrix harness runs fixtures the same way; look at how `coverage/` and `dead-export-range/` fixtures stage a base commit.
4. **Correctness tests before the speed-up**: a test whose covered function changed is rerun; a test whose only change is its own body (structural hash) is rerun; a test covering an unchanged function in a changed file is kept; a kept red test still refuses; a toolchain change (fake the recorded `rustc` release in the entry) runs everything; `--depth deep` runs everything; a new test file runs everything.
5. **Measure** before (on `main` as found) and after (your tip) with `make inner-loop`; the warm row is the one that matters. Record the table in `**P10.1 — measurement**`.
6. **Dry runs and `describe`**: the planned check's `needs` entry says `(incremental: N stale)` beside ADR-084 §8's `(one run)`/`(cached)`.
