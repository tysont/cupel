# P9.F5 — Follow-up fix: the package is `cupel-cli` on every registry

Branch `p9-package-names`. Read `common.md` first, then ADR-125 (the installers), ADR-128 (publishing; its Consequences record that `cupel` on PyPI and `cupel-core` and `cupel` on crates.io belong to other projects), ADR-143 (the P9.10 release items), `dist/targets.toml`, `dist/npm/package.json`, `dist/pipx/pyproject.toml`, `dist/pipx/cupel.py`, `crates/cupel-cli/src/routes.rs`, `scripts/release.sh` (`make version V=X.Y.Z` rewrites the version in the wrappers), `.github/workflows/release.yml`, and the tests `crates/cupel-cli/tests/{installers,release,release_version,readme}.rs` (whichever exist). ADR number: **146**.

## The ruling

The owner's ruling: the package name is **`cupel-cli`** on PyPI, npm, and crates.io. The binary and the command stay `cupel`. The publish jobs run when their secret exists and skip cleanly otherwise (as ADR-128 built them).

## What you do

1. **npm**: `dist/npm/package.json` `name` is `cupel-cli`; the `bin` stays `cupel`. `npx cupel-cli` runs the package's one executable. The route in `routes.rs`, its pending reason, the README's install table, and the installer tests follow.
2. **PyPI**: `dist/pipx/pyproject.toml` `name` is `cupel-cli`; the console script stays `cupel`. `pipx install cupel-cli`. Same follow-through. `python -m build dist/pipx` and `twine check` must pass locally (the dev environment has Python; install `build` and `twine` into a venv under your scratchpad, never globally).
3. **crates.io**: the binary crate is already `cupel-cli`, and `cargo install --locked cupel-cli` is already the route. The library crates it depends on are the open question: `cupel-core` on crates.io is another project's, so `cargo publish --workspace` cannot publish as the crates are named. Do **not** rename the library crates (that is the owner's decision; record the options in ADR-146: a `cupel-cli-` prefix on the seven library crates, or publishing them under another prefix, or vendoring them into the binary crate). Make `publish-crates` unable to fail on the collision: the job runs `cargo publish --workspace --dry-run --no-verify` first and, when the dry run fails because a name is taken, writes a `::notice` and a step-summary line and exits 0 without publishing; test it in `release.rs` the way the `secrets` job is tested. The crates.io route stays `pending` with the reason naming the library crates.
4. **Everywhere the name appears**: `routes.rs` (route commands, `live`/`pending` and reasons), `describe` output and the README's generated sections (`make readme`), the README's install prose, `doctor`'s install routes, `dist/install.sh` if it names a registry, the Homebrew formula (unchanged: `brew install tysont/cupel/cupel`), `scripts/release.sh version` (it rewrites the version in files you rename or whose name field you change: confirm `make version V=0.2.0 && git diff` touches every wrapper and nothing else, then revert), and `.github/workflows/release.yml` comments.
5. **Verify** `npm publish ./dist/npm --dry-run` packs `cupel-cli@<version>`, the pipx build and twine check pass, `make installers` passes (it runs the wrappers against a fake release), and `make check`.

ADR-146 records the ruling, each registry's name and command, the crates.io collision and the options left to the owner, and how the publish job skips on a taken name.

## Leave alone

The binary's name, the archive names in `dist/targets.toml` (they are `cupel-<version>-<target>`), the Homebrew formula's name, the library crates' names, every check, the gate, the daemon, the goldens other than `describe`'s install routes if a golden carries them (then the diff is the route text only, justified line by line).
