# P9.9 — External dogfood

Three briefs, one per group; each runs as its own agent on its own branch. Read `common.md` first, then the plan's `#### P9.9` heading and the owner's track (c) ruling: *pick two mid-size open-source repos per native language (Rust, Python, TypeScript) and one per adapter language (Go, Java, Clojure), run `survey` and `check --depth deep` on each, and triage every finding. A false positive is a check bug and ships with a fixture case; a true positive stays. Record per-repo results in `docs/dogfood/`. Aim for findings an experienced maintainer of that repo would agree with.* ADR number: **138** (group 1 writes it: the method, the repository selection criteria, the triage rubric; groups 2 and 3 follow it and amend only with a reason).

## Selecting a repository

Mid-size: roughly 10k–60k lines of the language, a test suite that runs green from a clean clone with the tools `make dev-setup` installs (no Docker, no services), a permissive license, active in the last year. Prefer libraries over applications. Record the repository, the commit, the line count, and the time to run its suite. Clone into a fresh directory under your scratchpad, never inside the Cupel tree, and never run their build from inside Cupel's checkout.

## Running

`cupel init` in the clone (keep the generated `cupel.toml`; note any key you had to set and why), then `cupel survey --depth standard --budget 30m --format json` over the whole repository, then `cupel check --depth deep --paths <P>... --format json` where the paths are the files of the survey's top ten hot spots (the owner's ruling of 2026-10-24: no full-tree deep mutation on an external repository; the budget is 30 minutes at most). Record which paths the survey chose. (`--no-install`; every tool the language needs is in the dev environment.) Run them through the built binary of your branch (`cargo build --release`, then the path to `target/release/cupel`), one repository at a time, and every run of the repository's suite (its documented test command, `cupel survey`, `cupel check`) through `scripts/heavy.sh`, the machine-wide lock `make dogfood` takes (`common.md`): one heavy command on the machine at a time, released between repositories (one `scripts/heavy.sh` invocation per command, never one around a loop over repositories); the integrator's merge chains have priority over yours. Save the raw envelopes beside the report under `docs/dogfood/<repo>/` only if under 200 KB; otherwise summarize and keep them in your scratchpad.

## Triage

Every finding gets one row: finding id, check, kind, location, verdict (`true`, `false`, `disputed`), one sentence of reasoning a maintainer would accept, and the action. A `false` verdict is a check bug: write the failing fixture case in `crates/cupel-fixtures` that reproduces it (the smallest excerpt that triggers it, in that language), fix the check, regenerate the goldens additively, and rerun the repository to confirm the finding is gone and nothing true was lost. A `disputed` verdict (defensible either way) is listed with both readings and does not count as false. The per-check false-positive rate is `false / (true + false)` with the counts shown.

## The report `docs/dogfood/<owner>-<repo>.md`

Sections: Repository (url, commit, lines, license, suite time); Commands; Survey (the rankings, verbatim); Check (the status line, the gate result if any, per-check counts); Triage (the table); False-positive rate per check; Check bugs fixed (fixture case, commit); What a maintainer would do first (three sentences). Each group also adds a `**P9.9 — group N**` bullet to the plan's P9 Notes with the per-repository rates and the fixes.

## Leave alone

Only the check and fact code a false positive forces you into, and only with its fixture case. Nothing in the gate, the renderers, or the daemon.
