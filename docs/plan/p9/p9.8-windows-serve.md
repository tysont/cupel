# P9.8 — Windows `serve` over named pipes

Branch `p9-windows-serve`. Read `common.md` first, then the plan's `#### P9.8` heading, ADR-085 (the daemon), ADR-121 (`serve --mcp`), ADR-124 (the Windows release job is best-effort), `crates/cupel-cli/src/{serve.rs, connect.rs, session.rs}`, and `.github/workflows/release.yml`. ADR number: **137**.

## Scope (track (a) item 8)

The daemon's transport is a Unix socket. Abstract it behind one transport type with a Unix-socket implementation and a Windows named-pipe implementation (`\\.\pipe\cupel-<hash of the repository path>`), chosen at compile time; the client (`connect.rs`) and `CUPEL_NO_DAEMON` behave the same on both. The workspace must compile for `x86_64-pc-windows-msvc` (`cargo check --target x86_64-pc-windows-msvc --workspace --all-targets`, with the target added through `rustup target add`), which will surface every `std::os::unix` use outside the transport; fix each. Add a `windows-latest` job to `ci.yml` that runs `cargo check` for the target and the unit tests that do not need Unix tools (decide the filter and record it); then remove `continue-on-error` from the Windows build in `release.yml` and the "best-effort" wording from ADR-124's consequences, the README's install section, and `dist/targets.toml`'s comments, so the Windows archive is a first-class release asset. You cannot run Windows here: say exactly what is verified by compilation and CI and what is not, and keep the daemon parity tests (`make parity`) green on macOS.
