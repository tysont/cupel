# P9.F4 — Follow-up fix: Cupel's own test suite is deterministic under load

Branch `p9-flakes`. Read `common.md` first, then the plan's `#### P9 Notes` bullets **P9.8 — dogfood**, **P9.F1 — dogfood**, and **P9.F2 — dogfood** (each records a dogfood or `make check` that failed on a test whose outcome depended on the machine's load, not on the code), ADR-129 (the deep gate in CI), and the README section [Flakiness](../../../README.md#flakiness). ADR number: **145**.

## The problem

Three times this phase a merge waited an hour on a rerun because a test of Cupel's own suite failed under load and passed alone. Known offenders:

- `cupel-core/src/similarity.rs` `ten_thousand_symbols_are_searched_in_linear_work_and_under_a_second`: a wall-clock budget (20 s in debug) on a run that took 22.9 s at a load average of 90–150.
- `cupel-cli/tests/plugins.rs` `a_check_plugin_is_described_planned_and_configured_like_a_native_check` and `a_configured_check_plugin_runs_with_its_facts_as_files`: the plugin host's 10 s `describe` timeout expires while the plugin binary waits for a core under coverage instrumentation at load ~50.
- `cupel-adapt/tests/contracts.rs` `the_rust_contract_run_turns_on_debug_contracts_and_reads_each_violation`: the fixture's `cargo test` reports `completed: false` when its timeout expires under load.
- Every other test that sleeps, polls with a deadline, or asserts on elapsed time: `grep -rl "thread::sleep\|Duration::from_secs\|Duration::from_millis" crates --exclude-dir=repos` lists the candidates (`run_controls.rs`, `server.rs`, `process.rs`, `fresh.rs`, `budget_runs.rs`, `serve.rs`, `mcp.rs`, `settings.rs`, `lock.rs`, `check_host.rs`, `command.rs`, `parity.rs` among them). The daemon tests already know that the first watcher start of a fresh binary on macOS can take 8–30 s.

## What you do

1. **Measure first.** Run Cupel's own `tests.flaky` against Cupel's own suite while the machine is under load. The flake engine does not rerun cargo-nextest (README, Flakiness), so give it a `cargo test` runner through a config copy: write `$SCRATCH/flaky.toml` as a copy of `cupel.toml` whose `[lang.rust]` has `runner = "cargo"` and `test = "cargo test --workspace"`, and run `cupel check --config $SCRATCH/flaky.toml --only tests.flaky --depth standard --seed 1 --format json > $SCRATCH/flaky-1.json` with the dogfood-built `target/debug/cupel` (`eval "$(make dev-env)"` first). Induce the load with an external suite in a separate directory (clone a large Rust project such as `tokio` or `ripgrep` into a fresh directory under your scratchpad and run its `cargo test` in a loop with `nohup`; it is untrusted code, run only its documented test command, nothing else) until the one-minute load average is above 60, and keep it there for the whole measurement. Record the load, the findings, and the seed in the plan notes. Three seeds at least. Each `test.flaky` finding and every test in the list above is in scope whether or not the engine caught it.
2. **Make every timing-sensitive test deterministic.** The acceptable fixes, in order of preference: an injected clock (the code under test takes a `Clock`/`now` it already has, or gains one the production path fills with the system clock), event-based waits (wait for the observable the test wants, a file, a socket, a line of output, with a generous ceiling that only guards against a hang, never a `sleep` whose length is the assertion), or a timeout derived from a baseline the test measures in the same process (run the small case first, allow a fixed multiple). A performance assertion keeps its *work* bound (operations counted, comparisons made, allocations) and loses its wall-clock bound. No retries, no `#[ignore]`, no `flaky` attribute, no loosened constant: a constant that happens to pass today fails on the next slower machine.
3. **What cannot be made deterministic in under an hour** moves to `make check-slow`, a target outside `make check` (so outside the merge gate) that CI runs as its own job and that the plan's dogfood step does not wait on. Record in ADR-145 each test moved there, why it cannot be deterministic, and what would make it so. The target exists only if a test needs it; if every test is fixed, say so in the ADR and add no target.
4. **Prove it.** Repeat step 1 after the fixes at the same load with the same three seeds: zero `test.flaky` and zero `test.order-dependent` findings. Then `make check` three times in a row under that load, all green. Record each run.

ADR-145 records: the tests found, the cause of each, the fix pattern chosen per test, the measurement before and after (load, seeds, findings), and the check-slow list (empty or not).

## Leave alone

Production behaviour. A test that fails because the code under test is wrong is a bug report in the plan's open items, not a fix on this branch, unless the fix is the clock injection the test needs. Do not touch the flake engine (`cupel-core`'s flaky check and the runners' rerun modes) except to report what you found in the open items; your run of it over Cupel's own suite is a user's run. Nothing in `cupel-fixtures/repos`, nothing in the goldens: this branch changes no envelope.
