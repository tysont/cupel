# Development

All automation goes through `make`.

`make dev-setup` installs the pinned tool environment the tests, goldens, and gates need: every runner, coverage tool, analyzer, fuzzer, JVM build tool, and verifier CI installs, at CI's versions, under `~/.cache/cupel/dev-tools` (or `CUPEL_DEV_TOOLS`); a second run only verifies them. `make check` and every other target run with those tools first on `PATH`, and `eval "$(make -s dev-env)"` gives a shell that runs cargo directly the same environment ([ADR-139](../adr/CUPEL_DECISION_139.md)).

In an agent checkout, a linked git worktree, that environment also caps cargo's jobs and nextest's and libtest's test threads at half the cores (`CARGO_BUILD_JOBS`, `NEXTEST_TEST_THREADS`, `RUST_TEST_THREADS`), and `make check` compiles everything it runs in one step under `scripts/heavy.sh`'s machine-wide lock before running its lint, tests, and docs outside it. The main checkout, a single clone, and CI keep every core and take no lock for a check. Each checkout builds into its own `target/`: one target directory shared by checkouts of this workspace lets cargo judge one branch's build fresh with another branch's code ([ADR-156](../adr/CUPEL_DECISION_156.md)). Create and remove agent worktrees with `make worktree NAME=<name> [BASE=<ref>]` and `make worktree-remove NAME=<name>` (`scripts/worktree.sh`), not `git worktree add` and `remove`: removal also deletes the mutation slots the worktree's runs left under `$TMPDIR/cupel-mutate`, one of which holds a whole build.

| Target | Does |
|---|---|
| `make dev-setup` | install or verify the pinned development tools and print each one's version |
| `make check` | fmt, clippy with `-D warnings`, every test, rustdoc with `-D warnings`, and a check that the build left the tree clean; the pre-commit bar. The lint, tests, and docs run under `scripts/tmpdir-guard.sh`, with a temporary directory of their own as `TMPDIR`, and the check fails naming anything they leave in it. In an agent checkout its build step (`make check-build`) runs under the machine-wide lock first |
| `make worktree NAME=<name>`, `make worktree-remove NAME=<name>` | add `.claude/worktrees/<name>` in the main checkout on branch `<name>` (from `BASE`, `main` by default, unless the branch exists); remove it with its build and its mutation slots, keeping the branch |
| `make test` | `cargo test --workspace`; `UPDATE_GOLDENS=1 make test` rewrites golden envelopes |
| `make lint`, `make fmt` | `cargo fmt --check` and clippy; `cargo fmt` |
| `make build`, `make doc` | build the workspace; build its rustdoc |
| `make matrix` | print the check × language support matrix |
| `make readme` | regenerate the generated sections of `README.md` and `docs/guide/` (the install-route, verb, global-flag, exit-code, depth, check, check-settings, and support-matrix tables and the agent guide) from `cupel describe`, and the MCP tool table from `cupel serve --mcp` |
| `make parity` | every golden-harness run again through `cupel serve` on a copy of its directory, which must print the same after redaction ([ADR-085](../adr/CUPEL_DECISION_085.md)), and each run of a verb an MCP tool serves again as that tool's call to `cupel serve --mcp` on another copy, which must return the same envelope and stderr ([ADR-121](../adr/CUPEL_DECISION_121.md)) |
| `make baseline` | after a green tree dogfood, sets the store's baseline to that run and exports it to `.cupel/baseline.json`, the committed reference the tree gate's `base` rules compare with ([ADR-140](../adr/CUPEL_DECISION_140.md)) |
| `make reclaim` | removes the build outputs a checkout regenerates on demand (the coverage build, the incremental caches, the suite cache under `.cupel/cache`), which grow a worktree to 30 to 50 GB; `scripts/heavy.sh` refuses to start a heavy command below 40 GB of free space (`CUPEL_HEAVY_MIN_FREE_GB`) |
| `make dogfood` | Cupel grades itself at `--depth deep`: `cupel check --changed --depth deep --gate` against `main`, which mutates every function of every changed file; `make dogfood DOGFOOD_SCOPE=tree` grades the whole tree with `[gate.tree]`, whose clone ratchets read `<= base` against the committed `.cupel/baseline.json` it imports first, and skips `tests.mutation`. Both skip `tests.flaky`, whose engine reruns the whole suite one test at a time and does not rerun cargo-nextest, and `conc.race`, which Miri cannot run on tests that spawn processes ([ADR-129](../adr/CUPEL_DECISION_129.md)). A local run is bounded by `DOGFOOD_BUDGET` (`--budget 120m` for the changed gate, enough for mutation of an ordinary change, and `45m` for the tree), lists what the budget left out, and exits 5 when it left anything out; CI runs both with `DOGFOOD_BUDGET=`, which runs every check. They need cargo-nextest and cargo-llvm-cov on `PATH`. The run goes through `scripts/heavy.sh`, the machine-wide lock every heavy command takes, so one dogfood (or one external test suite run through the same script) runs at a time on a machine |
| `make install` | `cargo install --path crates/cupel-cli` |
| `make dist` | build the stripped release binary and package it as `target/dist/cupel-<version>-<target>.tar.gz` (`.zip` on Windows) with `LICENSE` and `README.md`; `TARGET=<triple>` builds another target, the Linux musl and Windows GNU targets through `cargo-zigbuild` with `zig` on PATH ([ADR-124](../adr/CUPEL_DECISION_124.md)) |
| `make release V=X.Y.Z` | from a clean checkout of the pushed tag `vX.Y.Z` on a Mac: build all five archives and `SHA256SUMS` and create the GitHub Release ([ADR-238](../adr/CUPEL_DECISION_238.md)); does nothing once the release is complete; `DRY=1` builds and creates nothing |
| `make publish V=X.Y.Z` | `publish-npm`, `publish-pypi`, and `publish-homebrew`, each runnable alone and doing nothing once that version is published; npm and PyPI read their tokens from the environment: `op run --env-file=release.env.tpl -- make publish V=X.Y.Z` ([docs/release/PUBLISHING.md](../release/PUBLISHING.md)); `DRY=1` uploads and pushes nothing |
| `make verify-release V=X.Y.Z` | check the release on every live route: the archives and checksums, `install.sh` on the Mac and in Docker, `cargo binstall`, npm, PyPI, and Homebrew |
| `make version V=X.Y.Z` | write the release version into every file that names it: the workspace `Cargo.toml`, the workspace crates in `Cargo.lock`, `dist/npm/package.json`, and `dist/pipx/cupel.py`; a test holds them equal |
| `make installers` | the tests of `dist/`'s installers against a fake release on a local HTTP server ([ADR-125](../adr/CUPEL_DECISION_125.md)); `make test` runs them too, skipping a test whose tool (ShellCheck, Ruby, Node, npm, Python with `flit_core`) is missing |
| `make test-network` | the tests that need the network, the real `pip install pytest` of `doctor --fix --install` ([ADR-153](../adr/CUPEL_DECISION_153.md)); `make test` reports them skipped, and CI's `installers` job runs them |

The generated sections of `README.md` and `docs/guide/` sit between `<!-- generated:NAME -->` and `<!-- end:NAME -->` markers. A test in `crates/cupel-cli/tests/readme.rs` lists which file holds which sections, renders them from the binary's `describe` output, and fails when the committed text differs, so `make check` catches a stale table. Run `make readme` and review the diff.

CI runs `make check` and `make parity` on Linux and macOS and `make dogfood` on every push: the tree gate on `main` and the changed gate on branches, both at `--depth deep`, on a Linux runner with cargo-nextest and cargo-llvm-cov installed. It runs `make installers` and `make test-network` on Linux and macOS images with only Rust, Node, Python with `flit_core`, and ShellCheck added, and Homebrew's `brew style` on the rendered formula on macOS. A `v*` tag runs `.github/workflows/release.yml`, which builds each platform's archive with `make dist`, writes `SHA256SUMS`, and publishes the GitHub Release; the tag must be `v` followed by the crate version, and a manual run of the workflow builds and uploads the archives without releasing. Cupel's own `cupel.toml` is the example to copy.

The workspace is a set of crates under `crates/`. `cupel-core` holds the output contract, the fact vocabulary, scope, the scheduler, and gates. `cupel-lang` holds the `Language` trait, the query-driven producers, and one `langs/<id>/` directory per language. `cupel-adapt` is the toolchain table of runners and coverage and bench tools per language. `cupel-mutate` is the mutation engine. `cupel-checks` holds the checks, which depend on `cupel-core` alone. `cupel-store` is the SQLite fact store. `cupel-serve` is the daemon's socket protocol, server, client, and file watcher, and the MCP server, generic over what they run. `cupel-cli` is the binary, and the daemon runs requests through the same code a cold invocation does. `cupel-fixtures` holds fixture repositories, conformance inventories, and golden envelopes. Every behavior is built test-first; the implementation plan has the definition of done for each step.

Checks and tool producers register themselves from their own modules ([ADR-074](../adr/CUPEL_DECISION_074.md)), so additions made in parallel never edit the same lines. Adding a check is one module in `crates/cupel-checks/src/` that submits itself with `inventory::submit!`, its `mod` line in that crate's `lib.rs`, its fixture code, and its goldens under `crates/cupel-fixtures/golden/<check-id>/` (the matrix golden per language, `describe.json`, and `survey-<lang>.json`); a check can keep its fixture code in its own `crates/cupel-fixtures/repos/<check-id>/<lang>/` so no other check's goldens change. Adding a tool producer is one module in `crates/cupel-adapt/src/` and its `mod` line. Adding a fact kind ([ADR-123](../adr/CUPEL_DECISION_123.md)) is its payload module in `crates/cupel-core/src/`, which submits the kind's catalog entry with `inventory::submit!`, its `mod` and `pub use` lines in that crate's `lib.rs`, its variant appended to `FactKind` in `crates/cupel-core/src/fact/kind.rs`, its conformance inventory in `crates/cupel-fixtures/conformance/` if it has one, and its schema snapshot, which `UPDATE_GOLDENS=1 INSTA_UPDATE=always make test` writes. Tests derive what must be described, golden, and supported from the registries, so nothing else lists checks; `UPDATE_GOLDENS=1 make test` writes a new check's goldens and `make readme` adds its rows to the check and support-matrix tables.
